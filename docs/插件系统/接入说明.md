# 插件接入说明

本说明对应当前代码的插件接入方式。所有者已授权第二阶段收尾；完整体验和真实环境验收仍在汇总，范围与已知限制见[实施与进度](实施与进度.md)。理论见[插件系统理论](../理论/02-插件系统理论.md)。

## 交付与加载

插件程序位于项目根目录 `plugins/<id>/`，包含 `plugin.json`。侧栏「插件管理」从该根目录发现插件，也可导入 ZIP；ZIP 可以直接以清单为根，也可以包含一层插件文件夹。安装和扫描不执行插件；点击加载才准备环境、启动服务和登记参与能力。新发现或新导入的插件默认不启用。内置自主插件在首次启动且尚无启用记录时会自动加载，以延续迁移前的自主活动；之后是否加载以插件管理保存的状态为准。

清单示例：

```json
{
  "id": "example",
  "name": "示例功能",
  "version": "1.0.0",
  "api_version": 1,
  "description": "功能说明",
  "entry": "backend.py:create_plugin",
  "capabilities": ["context", "page"],
  "pages": [{"id": "main", "title": "管理", "path": "web/index.html"}],
  "settings_schema": {
    "type": "object",
    "properties": {"enabled": {"type": "boolean", "title": "启用增强", "default": true}}
  }
}
```

`entry`、`pages`、服务和上下文等均按需提供。静态页面或设置插件不必启动后端。运行资料与配置写入当前 Nexus 数据目录的 `plugins/<id>/`，卸载默认只移除仓库中的插件程序并保留资料。

入口文件直接加载在 Nexus 解释器中；清单声明 `dependencies` 或 `python_package` 时，加载会在数据目录的 `plugins/<id>/venv/` 创建或复用隔离环境。依赖安装完成并写入标记后才视为准备成功；失败时插件详情显示具体错误。修改清单后再次加载会按变更后的依赖重新准备环境。

数据目录还保存 `plugins.json`（启用状态和插件设置）、`plugin-events.sqlite3`（活动与事件）和 `model-requests.sqlite3`（最近七天的模型请求记录）。插件自有数据库由其代码决定，例如自主插件的 `autonomy.sqlite3` 与 `scheduler/scheduler.sqlite3`。

## 本地入口与共同能力

入口工厂接收 `PluginHost`，返回插件对象。公开作者接口位于 `nexus.plugins.api`，提供 `ToolSpec`、参数模型及 `PluginHost`。

| 插件方法 | 用途 |
| --- | --- |
| `start()` / `close()` | 登记与释放本插件的资源；不影响其他接入 |
| `tools(scope)` | 返回模型工具；同名替换必须在清单 `overrides` 中明确登记 |
| `context(scope)` | 返回本次材料；或返回含 `messages` 与 `materials` 的对象以整理临时历史 |
| `before_tool(name, args, scope)` / `after_tool(name, args, result, scope)` | 参与工具处理，保留既有工具权限 |
| `activity_finished(scope, result)` | 活动执行段结束后的处理 |
| `on_event(event)` | 接收已订阅的宿主变化 |
| `call(action, values)` | 接收插件页面的普通操作 |

`scope` 包含 `kind`、`owner_id`、会话或任务标识等；请求准备还包含本次 `messages`。外部活动附带 `activity`，其中保留事件来源。每次调用只使用当前材料快照。

`context` 材料包含 `content`、`purpose` 与 `source`。其结果不会自动写入聊天。依赖其他提供者时用清单 `context_after` 指明先后；最终模型格式和容量由 Nexus 处理。本次必需来源来自活动归属或 `scope.required_plugins`，不因插件自行声明而让普通聊天全局依赖它。

插件可使用 `host.query()` 查询 `state`、`tasks.list/get/messages/operations/notifications`、`sessions.messages`、`activity.current/runs`。读取不会改变任务。`host.command()` 提供明确的任务控制与活动结束操作；`work.*` 调用沿用当前灵工具上下文。

`host.subscribe()` 登记 `message.saved`、`task.notification`、`task.owner_control`、`activity.finished` 等变化。通知与查询保留各自含义；历史消息可另行查询，首次订阅不默认把全部历史当新消息投递。

插件内的 `skills/` 按现有 Skill 格式登记，停用后从后续模型请求和读取目录中撤下。

## 独立 MCP 服务

清单 `services` 或入口中的 `host.connect_service(name, config)` 可登记服务。命令支持 `{python}`、`{plugin}`、`{data}`，分别表示本插件解释器、插件程序目录和资料目录。

清单 `dependencies` 和可选 `python_package` 用于准备服务的隔离 Python 环境。本地入口运行在宿主解释器中，使用标准库和宿主公共接口；需要额外运行依赖的功能放在独立服务内。

服务 `model_tools` 明确列出供模型使用的工具；默认不公开内部管理接口。宿主用 `host.call_service()` 仍可调用内部能力。插件服务由插件管理，不在普通 MCP 配置页重复编辑。

自主插件的调度服务使用插件内的 `plugins/autonomy/services/scheduler/`，启动命令由插件在加载时登记，并随插件停用而释放。仓库中另保留旧独立调度服务与 `nexus/automation/` 的源码；它们不在当前启动流程中，不能按旧方式手工安装或用作当前验收路径。

纯 MCP 插件也可以通过清单 `context: {"service": "服务名", "tool": "工具名"}` 参与请求准备，该工具接收 `scope`；通过 `subscriptions` 与 `event_handler: {"service": "服务名", "tool": "工具名"}` 接收变化，该工具接收 `event`。

## 页面与消息

页面资源从 `/plugins/<id>/<资源路径>` 取得，在插件管理内打开。页面业务调用：

```text
POST /api/plugins/<id>/call
{"action":"snapshot","values":{}}
```

页面需要打开原任务时，可向父页面发送 `{type:"nexus.open_task", task_id:"..."}`；返回灵用 `{type:"nexus.open_ling"}`，消息目标使用当前页面来源。关闭页面不停止后台插件。

独立服务向 `host.event_url`（`POST /api/plugin-events/<id>`）发送：

```json
{"id":"来源内稳定标识","type":"changed","text":"发生了什么","data":{},"reply_required":false}
```

接口保存并返回事件编号及状态。相同接入与来源标识重复发送返回已有记录；接收不等于处理完成。停用期间记录为暂停，重新加载后恢复未处理项。中断与已完成项不会当成新活动自动重做。

活动结束通过 `host.complete_activity(reply=..., summary=...)` 交回结果；明确要求回复的活动不能仅保存静默记录。宿主保存回复或内部经历，插件决定业务表达。

请求记录从插件管理的“请求记录”查看，保留七天。实际发送内容、准备失败和插件参与记录分别说明；认证请求头不进入记录。

模型提供商编辑页中的每个模型还有可选的 `context_window_tokens`。它只进入本地预算，用于上下文裁剪和摘要压缩；全局 `context_limit` 优先，留空时回退到 64,000，不会改变 API 请求中的模型上限。
