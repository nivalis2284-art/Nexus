# 插件系统理论审视与方案比较

日期：2026-10-23。

**性质：研究过程与方案比较。** 本文保留审视时提出的问题和建议，末节记录随后采纳的对应关系。[插件系统理论](02-插件系统理论.md)已结合所有者于 2026-10-23 的确认完成定稿，当前结论以该文为准。下文“待定”“候选”“需讨论”描述研究时的状态，不代表定稿后仍需重新选择总体路线；也不表示当前源码存在对应缺陷或已批准代码开发。

研究依据为本轮讨论，以及下文链接的官方规范与官方项目文档。结论区分可核对的案例事实与针对 Nexus 的推导；未进行插件运行实验、真实模型测试或现有实现的全量审计。

## 一、总体判断

现有方向能够形成一套可演进的插件体系。主要缺口不是缺第六、第七套系统，而是需要把“谁提供、谁调用、何时参与、读写什么、结果归谁”补充清楚。

建议以 **统一注册与扩展契约 + 宿主管理的活动过程 + 可替换的能力实现** 来组织理论。MCP、事件、上下文、宿主信息与界面是不同角度的参与方式，不应直接建成五套彼此独立的平台。

这里“契约”就是双方共同遵守的输入、输出和行为说明；不是指商业合同，也不意味着所有规则都必须写成一门配置语言。

## 二、官方案例能支持什么

| 来源 | 本轮核实的事实 | 对 Nexus 的启发与限制 |
| --- | --- | --- |
| [MCP 架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture) | MCP 明确关注上下文交换协议，不规定应用如何使用模型或管理收到的上下文 | 可作为能力通信基础，不能据此省略宿主的请求装配和运行约定 |
| [VS Code 清单](https://code.visualstudio.com/api/references/extension-manifest) | 插件版本、宿主兼容范围、扩展依赖和贡献内容是分别声明的概念 | 插件自身版本不能代替它所依赖的宿主接口版本 |
| [pluggy](https://pluggy.readthedocs.io/en/stable/) | 宿主声明可参与的钩子，插件实现对应能力，宿主收集结果 | 值得借鉴“明确时机与输入输出”；它是进程内调用机制，不是独立服务管理平台 |
| [LangChain 上下文工程](https://docs.langchain.com/oss/python/langchain/context-engineering) | 本次请求中的临时信息与持久状态明确区分 | 自动召回与永久写入应分别定义 |
| [LangChain 自定义中间件](https://docs.langchain.com/oss/python/langchain/middleware/custom) | 活动前后、每次模型调用前后、工具调用周围有不同参与点，并有执行顺序语义 | “请求前参与”需要明确每次请求还是整段活动一次；顺序不可含糊 |
| [Koishi 生命周期](https://koishi.chat/zh-CN/guide/plugin/lifecycle)、[服务与依赖](https://koishi.chat/zh-CN/guide/plugin/service) | 提供插件停用与所登记资源的清理机制；服务可由不同插件提供，依赖影响其运行 | 可借鉴资源归属和必需／可选依赖；不能把清理监听等同于撤销已发生的外部行动 |
| [Backstage 插件安装](https://backstage.io/docs/frontend-system/building-apps/installing-plugins/) | 插件加入应用依赖后可以被自动发现；该发现机制依赖其 CLI 构建流程 | 自动登记不代表任意目录里的新页面都能运行时热装入 |
| [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) | 通过工具引用 UI 资源，宿主获取并显示界面，双方另有交互消息约定 | 可复用工具结果中的交互方式，不能自动取代 Nexus 的导航、设置与页面生命周期 |
| [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) | 统一事件描述，区分来源、类型、标识与业务内容；来源与标识可用于辨认重复事件 | 可参考事件信封，不必为此引入消息总线，也不能从格式标准推导出处理成功或投递保证 |

上述项目解决的范围不同，不能把某个项目的存在当成 Nexus 整体方案已经得到验证。建议只借鉴与当前关系直接对应的机制，不整体迁入这些框架。

## 三、具体缺口与简化建议

### 1. 五类参与能力不在同一层

**问题：** MCP 是通信协议，上下文编排是运行中的处理步骤，宿主信息是数据访问能力，界面则是展示与交互。若把每类都当成一套必须独立部署的系统，会重复处理注册、启停、错误和配置。

**建议：** 保留五类分类帮助理解，用同一个插件登记和身份贯穿它们；具体调用可复用 MCP 或普通宿主接口。上下文编排拥有明确职责，不必独立成进程。

### 2. 需要区分插件定义与使用实例

**问题：** 同一种记忆插件以后可能连接不同资料库；同一个服务也可能被多个功能使用。“这个插件的设置”若没有归属，后续很难解释切换来源或停用的影响。

**建议概念：**

- **插件定义：**这一种功能提供什么，由什么版本实现。
- **接入实例：**Nexus 实际配置和使用的某一份接入，关联其服务、设置和数据来源。
- **本次参与：**某次处理实际使用了这个实例中的哪些能力。

这是区分关系，不要求立即提供多个实例的界面、运行池或多租户能力。第一版即使每种插件只允许一份接入，也能把这些含义分清。

### 3. 可用性不能用一个开关或一条状态链包办

**例子：** 记忆插件已经启用，后台查询可用，但管理页未打开；或者管理页能打开，某个记忆来源连接失败。

**建议：** 分开描述登记、用户是否启用、相关能力是否就绪，以及某次活动有没有实际使用。页面可见不代表服务可用，服务可用不代表工具被调用，工具返回也不代表所有结果都被装进请求。

不要求为所有组合再建立一套复杂状态机。状态说明应能回答具体问题，而不是不断增加“已准备／已装载／半就绪”等同义词。

### 4. 注册声明不是另一门编程语言

**问题：** 若试图把搜索算法、条件分支、重试和所有行为都写进登记资料，最终会产生一门更难维护的自制语言。

**建议：** 声明表达能力与关系，复杂算法保留在插件中。宿主调用“自动召回”，不需要了解插件怎样改写问题、搜索和挑选候选内容。

这也避免承诺“注册就会自动实现功能”：插件仍必须实现对应行为。

### 5. 依赖与顺序需要分开

**问题：** “先注册 A，再注册 B”不能表示 B 的服务已经可用；“把记忆放在历史前面”也不能表示召回先于历史压缩执行。

**建议区分：**

- **运行依赖：**没有某项服务，这项能力无法工作。
- **数据依赖：**B 需要 A 的输出，执行上有先后。
- **可选增强：**存在时使用，不存在时仍能完成另一部分功能。
- **呈现顺序：**材料最终在请求或界面中的位置。

依赖能力而非某个实现名称，能够方便替换；若确实依赖某个插件的特定功能，也可以明确声明，不强制抽象成通用服务。先定义关系，不据此预设大型依赖求解器或可视化流程图。

### 6. 请求材料需要共同格式与明确归属

**例子：** A 交来相关记忆，B 压缩旧历史，C 整理工具结果。若都能直接改整份请求，后执行的插件可能覆盖前者的内容，来源也会丢失。

**建议：** 普通提供者返回带用途和出处的材料；修改现有材料的处理者明确自己修改的范围。宿主统一完成装配、容量安排和模型格式转换。

可进一步讨论一种“上下文材料单元”，表达内容、用途、来源、原文引用及适用活动。它不是文档中的长期事件记忆块：前者供本次请求使用，后者属于长期资料；两者可以关联，不能合并为一个概念。

具体字段、大小或优先级没有在本轮锁定。也不允许插件自行声明“我是最高指令”就获得改变所有者要求的作用。

### 7. 本次快照、完整历史与最新状态是三种视角

**问题：** 插件需要理解当前问题，但如果直接读取随时变化的“全部上下文”，可能把后来到达的消息当成原调用的问题；若拿最终请求作为召回输入，又会形成循环依赖。

**建议：**

- 本次准备过程取得明确归属的已知材料，作为召回输入。
- 需要补充过去时，通过稳定的信息接口查询原始记录。
- 需要了解最新情况时，明确读取当前状态，不悄悄更换原问题。

完整历史不等于本轮模型能看到的历史。查询接口和本次请求应说明各自范围；不要求插件读取 Nexus 内部数据库来猜测。

### 8. 请求增强与永久写入必须分开

**例子：** 每轮召回同一段记忆，如果又把召回内容写成新聊天，并在活动结束后当成新经历收录，可能反复累积同一材料。

**建议：** 区分“仅本次使用的材料”和“已经发生并保存的记录”。记忆写入使用明确的后续处理约定，保留资料来源，不把召回展示本身当成又发生了一次经历。

这是从召回与记录关系直接推导的问题，不要求引入复杂评分、永久反思循环或重复检测平台。

### 9. 事件、查询和行动请求不应混成一种消息

三者含义不同：

- **查询：**现在是什么情况？
- **行动请求：**请执行某个操作。
- **事件：**某件事已经发生。

“网页发生变化”不等于“必须立即执行某项工作”。消息入口可以接收材料，但触发怎样的处理仍要依据来源、既有要求和宿主运行约定。用户的明确安排也不能在转成事件后丢掉原本的要求。

**可选简化：** 参考 CloudEvents 的事件信封，用共同方式表达来源、类型、标识、时间和内容。是否采用完整规范尚未决定；它不负责 Nexus 的业务目标、处理对象选择或执行策略，不需要配套消息中间件。

### 10. 接收、投递、处理与结果不是同一个成功

**问题：** 插件发来事件获得“已接收”，不代表模型已经读到；模型读到以后也可能等待回答或发生错误。订阅“消息到达”与订阅“实际处理完成”会产生不同后续行为。

**建议：** 理论上说清楚这些阶段的含义，以及插件有需要时怎样关联处理结果。编号关联、重复投递和重启后待处理项的行为应在消息契约中决定。

事件格式本身不能保证一次且仅一次执行。当前不据此增加自动重放、通用重试队列或新调度框架。

### 11. 上下文编排不能承担所有运行职责

**问题：** 若把插件启停、任务恢复、模型调用、外部事件、界面加载全放进编排器，它会成为一个新的巨大核心，复杂度只是换了位置。

**建议：**

- 注册管理负责认识插件与接入关系。
- 通用运行过程负责活动、请求和工具执行的时机。
- 上下文编排负责某次请求的材料准备。
- 宿主信息接口负责读取和订阅约定资料。
- 界面宿主负责容纳插件界面。

这些职责可以在同一个程序中实现，不要求分别建设平台。插件需要参与活动结束等时机时，使用明确的过程扩展点，不伪装成“向请求里加一段文字”。

### 12. 停用、关闭与数据保留需要资源归属

**具体问题：** 服务由谁启动和关闭？关闭页面是否只释放页面资源？插件停用时已登记的监听是否撤销？一项已经开始的工作是否还能完成？服务被其他接入复用时是否一起终止？

**建议：** 记录必要的资源归属，停用时清理属于这份接入的参与关系。监听或连接的清理，不表示撤销已经发送的消息或已经完成的写入。

数据另按来源区分：宿主记录、插件原始资料、可重建索引与临时缓存。需要决定移除后的保留、导出和引用有效性；不要求把所有资料强行搬进 Nexus 或另一套中心数据库。

已经开始的工作是完成、等待、失败还是停止，保留为需确定的产品行为，不在本轮替所有者作决定。

### 13. 前端的三个选择不能混为一个承诺

需要分别确定：

1. **挂在哪里：**导航页面、设置、详情栏目或工具结果。
2. **怎样显示：**宿主组件、独立嵌入页面或混合。
3. **怎样交付和更新：**随应用构建，或宿主运行时读取外部资源。

Backstage 的自动发现并不说明可以免构建热安装；MCP Apps 的交互页面也不会自动登记一个永久侧栏入口。这些是官方案例职责范围的差异。

**候选组合：** 普通设置由宿主生成；复杂插件页面使用独立资源和稳定的宿主交互约定；需要深度融入现有界面时再使用原生组件。是否采用此组合，仍需讨论界面体验与发布方式。

不强制所有插件使用同一种前端框架，也不先建设复杂的远程组件分发系统。

### 14. 版本、配置生效和能力缺失必须可解释

插件代码版本、MCP 协议版本、Nexus 扩展契约版本、插件自己的数据格式，是不同层次。只检查“插件版本更新了”不足以说明还能配合。

**建议：** 登记使用的共同能力与所需兼容范围；界面说明当前哪些部分可用。每次请求准备过程中，配置和参与范围应有明确归属，已经发出的请求不悄悄换内容。

何时刷新配置、长活动怎样接纳更新、已有数据是否需要迁移，继续保留为待定。不能因此预建永久兼容所有旧版本的框架。

某项能力失败后是否继续，也由用途决定：可选资料缺失可以明确提示；若用户要求必须取得该资料，不能在没有材料时仍宣称已经完成。是否等待、由谁重试和何时停止需要明确，不用一套全局重试次数代替业务判断。

### 15. 多个入口可以复用能力，但调用含义不能丢失

**例子：** 用户在管理页搜索记忆、灵主动查询记忆、编排器自动召回，都可以复用相同的搜索实现。若三个入口分别实现一套搜索和返回格式，会重复维护；若把管理页所有按钮都直接公布为模型工具，也会把“提供界面操作”和“提供给灵使用”混为一谈。

**建议：** 插件登记共同能力，再分别说明供哪些入口使用。调用保留当前活动、发起方式和结果用途；普通页面操作不必请求模型，自动召回也不应额外伪造一条用户消息。

读取与修改继续分开。可调用的能力仍沿用其实际操作要求与既有权限处理，不能因为插件在声明中写了“自动执行”就自行扩大授权。也不应因引入注册机制，给用户已经明确发起的普通界面操作额外增加一套重复确认。

这是一项共享约定，不必新建“万能动作中心”；可以复用实际实现中已有的调用与控制能力。MCP 是一种接入途径，不要求所有只用于界面的内部操作都出现在模型工具目录里。

## 四、可以采用的更简洁组织方式

建议用下面四个概念组织前述关系。它们是逻辑职责，不是四个新服务：

| 概念 | 解释 |
| --- | --- |
| 注册与扩展契约 | 插件声明提供与需要的能力，宿主说明调用时机、输入输出和兼容范围 |
| 本次调用范围 | 说明这次为哪项活动处理什么问题、依据哪些材料、使用哪些设置 |
| 明确的参与时机 | 模型请求前、工具结果后、活动结束等，不将事件订阅当成所有处理的替代品 |
| 资源与数据归属 | 说明接入拥有的监听、连接、页面及资料，便于启停和替换 |

围绕这些关系，继续保留现有五类能力。需要通信时优先复用合适的已有协议，需要业务实现时由插件负责，不为每类职责都新造一套完整协议。

## 五、替代方案比较

| 方案 | 收益 | 代价与适用边界 | 本轮判断 |
| --- | --- | --- | --- |
| 纯 MCP 加消息入口 | 工具与外部事件容易独立 | 缺请求前参与、宿主信息和界面装入约定 | 可作能力基础，不足以单独覆盖全部目标 |
| 任意位置自由改写宿主 | 初期自由度高 | 内部结构改变会牵动插件，难说明多插件覆盖关系 | 不作为共同默认方式 |
| 所有功能独立进程 | 功能可单独运行 | 简单设置也要处理通信与生命周期，重复成本高 | 允许独立，不要求全部独立 |
| 全部做成可视化流程图 | 适合明确的复杂工作流程 | 容易让所有者承担接线，且不自动解决数据归属 | 不作为普通插件使用前提 |
| 整体迁入现有 Agent 或前端框架 | 可以复用一部分实现 | 框架范围与 Nexus 目标不同，迁移会引入新的耦合 | 本轮没有足够依据选定 |
| 统一声明、明确扩展点、可替换服务、按次装配 | 同类功能可以独立迭代，共同规则可理解 | 需要认真写清契约及少量共同处理逻辑 | 当前最值得继续细化的候选 |

“完善理论”应表现为关系闭合、边界明确、变更有去处，不以采用协议和框架的数量衡量。

## 六、用完整过程检查理论

以下是理论走查场景，不是已运行的测试，也不是强制新增功能清单：

1. **自动召回：**当前问题与近期材料交给插件，返回记忆，装入正确请求；中途新消息不更换原问题。
2. **主动查询：**灵调用同一记忆能力，取得结果并继续；不重复装入或自动当成新经历写回。
3. **变化订阅：**插件只订阅所需的已保存记录，清楚区分消息保存、处理完成和工具行动的事实。
4. **独立管理页：**用户浏览和搜索，无须模型；关闭页面后后台状态仍可解释；浏览不自动改变请求。
5. **服务不可用：**登记和设置仍在，界面显示哪部分不可用；是否继续当前处理依据该能力的必要性。
6. **停用与更新：**未来调用、正在进行的活动、排队事件、界面和数据分别有明确去向，不把停用当删除。
7. **替换服务：**查询约定可以复用，但旧记忆数据与原文引用是否能迁移需要另外验证，不能因接口一致就假定数据兼容。
8. **多入口使用：**同一查询通过页面、模型和自动召回得到含义一致的结果，各自保留发起方式；界面专用操作不因注册而自动成为模型工具。

这些走查用于发现关系是否遗漏；后续落地时才根据实际范围制定验收，不把本轮静态研究写成工程验证通过。

## 七、后续需要作出的决定

建议按关系先后继续讨论，而非立即选框架：

1. 插件定义、接入实例、能力声明与本次参与之间怎样对应。
2. 宿主开放哪些信息与时机；哪些结果仅本次使用，哪些操作会改变持久状态。
3. 上下文材料的共同表达、依赖与最终装配规则。
4. 消息接收与变化订阅的处理含义，以及与活动的关联方式。
5. 停用、在途工作、更新生效、数据保留与迁移规则。
6. 前端页面的交付和加载方式，以及需要多深的宿主界面融合。

只有这些关系确定后，才适合选定具体 API、包格式和实现路径。新建议仍需所有者确认，本文不宣布理论已经最终冻结。
