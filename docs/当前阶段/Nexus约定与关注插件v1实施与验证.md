# Nexus「约定与关注」插件 v1 实施与验证

日期：2026-11-04。

## 交付

独立插件位于 `plugin-dev/followup/`，插件 ID 为 `followup`，版本为 `0.1.0`。构建产物为该目录下的 `nexus-followup-0.1.0.zip`。源码与 ZIP 随仓库交付，未安装或启用到日常实例。

实现时间触发和指定工作事件触发，后台运行、按需汇报，聊天工具与宿主渲染管理页共用业务逻辑。模型决定执行方法、如何处理普通问题、是否值得汇报及关注是否已经完成；没有固定业务条件引擎。

## 已实现的行为

- 单次日期／相对延迟、固定间隔、每日、工作日（周一至周五）、每周、每月指定日期／最后一天。31 日严格表示该日，无该日期的月份跳过。
- 指定后台工作完成、挂起、失败、中断、取消、等待决定或受阻时触发，可一次或持续监听。失败／中断在界面和工具中归入 failed。
- 新建只保存，不立即运行；首次成功汇报基线，之后按每次汇报或模型判断执行。停机、休眠、插件停用期间的触发不补跑。
- 同一安排不并发；运行期间多个触发合并为一个待执行。等待决定或最终受阻后暂停未来调度，保留本轮。
- 项目、模型和思考强度在创建时固定，后续单独修改；日历时间跟随当前 Windows 系统时区。带偏移的单次日期是固定时刻；间隔按经过秒数计算。
- 暂停／删除请求停止当前执行并清除待执行。恢复时显式继续仍关联的暂停工作，不创建替代工作；重启后保留中断工作关联，等待明确继续。
- 删除保留历史；已错过的单次安排可明确立即执行。页面提供新建、编辑、暂停／恢复、立即运行、删除、分页记录和本轮工具详情。

调度器在插件独立 Python 进程的可停止线程运行，空闲时不调用模型。时间模块使用标准库与 tzlocal，数据为插件目录内的 SQLite。安排与运行关联在同一事务保存，防止记录只保存一半。超过 30 秒未获得调度视为服务恢复，跳过积压时间并重新对齐事件位置；这不是后台工作的执行超时。

## 宿主和 SDK 变更

新增 `work` v1：defaults、list、get、events、start、control、report，供宿主内 Python、独立 Python 和 Node 插件使用。读取可以选择现有工作作为事件源，控制与关联汇报校验工作所属插件。插件来源和汇报策略保存在既有插件运行资料中。

工作仍由原有 TaskStore、TaskController、TaskAssembler 执行，沿用权限、审批、项目写入协调和原始工具记录。`report=False` 只抑制常规完成时自动唤醒；审批、受阻及中断仍使用现有通知。需要说明的结果通过 work_report 进入主交流，不伪装成用户发言。

真实进程验收复现了共享 Python stdio SDK 的 Windows 编码问题：中文响应在系统编码下无法输出，客户端表现为超时。已在共享 SDK 明确 stdin/stdout 为 UTF-8，新插件未复制或分叉 SDK。

## 公共插件能力正式接入：SDK 1.2.0

本次将 `work` v1 作为 Nexus 公共插件接口维护，不绑定 followup。宿主能力描述、Python SDK 常量及 MCP 初始化版本、Node SDK 常量及 MCP 初始化版本统一为 1.2.0；`api_version` 与各能力的 v1 不变。后续插件可以组合已有 work、models/dialogues、jobs、页面及存储能力，不因增加业务插件而必然修改宿主。

安排、调度、关注判断与业务页面继续留在插件。work 负责标准工作的创建、查询、事件、所属工作控制及按需回报，复用现有 TaskStore/TaskController，没有另建 Agent 执行器或事件存储。旧 query/command 入口保留兼容，SDK 说明旧入口的上下文依赖和返回格式，新插件统一使用 work。README 与 SDK 增加独立 Python/Node 用法和跨电脑更新步骤。

新版宿主的清单检查与运行时 require 共用校验，错误列出缺失能力及宿主实际版本，并说明更新、重启宿主的要求。旧宿主无法因为导入新 ZIP 而获得 work v1，也不会自动获得新的错误提示；需要先更新其实际运行的源码或发行包，保留该电脑自己的数据和配置。

正式接入时修正两处工作控制问题：control 请求编号按插件隔离，避免两个插件使用相同编号时冲突；停用时的暂停请求加入工作控制版本，避免同一工作恢复后再次停用时误用旧暂停请求。start/control/report 的请求编号共用非空和长度校验，已有 start/report 的请求键格式保持不变。

结果 **67 passed**。涵盖旧 SDK 示例和聊天接入、能力版本与缺失提示、Python/Node 独立进程经实际 HTTP 桥启动标准工作、状态/消息/事件查询、请求去重与归属、重复停用、权限审批，以及 followup 的打包加载和调度。模型响应使用可控本地模拟；本轮未重复真实模型或浏览器验收。

新增工作接口与测试的 Ruff 检查通过；其余修改的既有 Python 文件与 HEAD 相比没有新增 Ruff 问题，未扩大范围清理旧告警。`git diff --check` 通过。重建 followup ZIP，校验共享客户端与 SDK 文档为最新源文件、版本为 1.2.0，未安装到日常实例。

### 真实模型

使用本地已配置的 **glm-5.3-flash / openai_responses**，在独立临时 home、插件目录和只有测试文本的工作区运行。没有读取日常会话、修改日常项目或启用日常插件。验证了：

1. 后台实际调用 read_file 读取 status.txt，并提交首轮基线结果。
2. 后一轮重新读取相同文件，利用上次摘要，提交 notify=false，主交流保持静默。
3. 指定源工作完成后触发后续工作，带入事件与实际工作结果，一次性安排结束。
4. 时间触发的后台报告执行完成；另对单次定时任务等待到主交流回报处理完成，确认实际交付。

本地结构化证据为 `Cache/followup-real-validation.json`；不包含模型密钥。验收脚本首轮在临时目录清理阶段遇到已有宿主 runtime SQLite 连接仍打开的问题；功能记录已核对，后续单次交付检查在脚本中显式释放临时连接后正常结束，未借此改造宿主通用数据库生命周期。

**模型质量限制**：首轮把工具原文版本 `1.0` 转述为 `1.0.0`；下一轮重新读取后识别原文为 `1.0`，并判断无实质变化。调度、上下文传递和通知路径通过，不代表模型转述永远准确。保留原始工具记录供核对，未增加版本号专用校验或宣称已经解决通用语义准确性。

## 使用边界

不包含外部 webhook／邮件／GitHub 事件、系统或手机通知、高级 cron、每轮自主改下次时间、旧定时数据迁移及关机执行。完整网站登录、网页搜索与浏览器插件的所有组合未逐一做真实服务验收。新增工作复用其实际启用的工具；现有权限测试已验证，创建安排不替代授权。
