# Nexus 内核边界收束与 Web 解耦计划

日期：2026-10-28。

状态：已按所有者 `$stop-that-shit change -- 开始执行` 完成工作区实现与限定验证，实施记录见第七节。当前需求来自所有者明确收束：先整理内核与 Web 的职责，使未来更换 Web UI 不必大幅改动内核；CLI 不是本轮目标。未提交、推送或部署。

## 一、目标与交付边界

本轮交付是对现有代码职责的整理：运行资源由应用层持有，业务操作不依附 HTTP Handler，当前网页通过原有接口继续工作。保留当前数据、功能和交互语义，不借此重做 Agent 系统。

目标依赖方向：

```text
当前 Web UI → HTTP／SSE 适配 → Nexus 应用层 → 现有 Agent／任务／工具／存储
```

应用层是普通 Python 代码，不是新增的独立服务平台。现有 HTTP 服务仍可同时提供网页和接口，继续默认只监听本机；不要求拆进程、拆仓库或独立部署前端。

交付包含：

1. 内核资源初始化、运行和关闭的集中入口。
2. 从 Web 层迁出的现有主交流输入处理、模型历史转换、设置及工作目录变更逻辑。
3. Web 适配层对这些能力的调用，以及维持现有 HTTP／SSE 行为所需的接线调整。
4. 必要的调用方和测试 fixture 更新、少量直接行为测试、README 中的职责说明和本文实施记录。

不包含：CLI／TUI、EXE／APK 打包、远程连接、认证或跨域方案、前端框架迁移、页面重设计、前端独立仓库、通用 SDK、插件协议升级、数据库格式升级、新事件总线或 RPC 框架。上一轮真实模型流错误继续作为已知未解决问题记录，本轮不扩大为模型兼容性修复项目。

## 二、已确认的耦合与处理方式

| 当前路径 | 当前承担的职责 | 本轮处理 |
| --- | --- | --- |
| `web/server.py::serve`、`_ling` | HTTP 之外还负责存储、任务、主交流、MCP、插件、事件资源的创建及关闭 | 将运行资源所有权与主交流组装移入应用层；HTTP 服务持有并调用应用实例 |
| `web/server.py::STATE/BUSY/RESOURCES` | Web 模块持有应用运行状态和锁 | 由应用实例持有；Web 接线可引用现有状态映射，不另存一套权威状态，也不强制把所有字典逐项改成类 |
| `web/server.py::_internal` | 从保存的交流恢复 Agent 输入，包括附件、检查点与原生续接 | 移入现有交流运行时，由应用和 Web 共用；保持历史语义 |
| `/api/ling/input` 分支 | 同时做 HTTP 解码、业务校验、停止短语处理、附件归属和输入入队 | HTTP 保留请求解析；现有提交、停止和入队业务集中到应用层，保留 request_id 去重及原有控制语义 |
| `web/settings_api.py`、`Handler._workspace_effect` | 设置校验、写入回滚、工作目录切换、MCP 与技能刷新 | 将无 HTTP 依赖的实现迁到应用／运行时层，保持校验、锁和回滚行为 |
| `web/task_api.py` | HTTP 适配中夹有工作业务操作和状态投影 | 实际业务判断复用 `WorkService`、`accept_input`、控制器与存储；残留于 Handler 的业务迁入应用层，不另造一套任务服务 |
| `runtime/stream.py`、`LingInbox` 的状态与记录 | 已有不依赖 DOM 的事件、持久状态和交流能力 | 直接复用；HTTP 只负责 SSE 编码和连接，界面展示函数可继续留在 Web |
| `plugins/manager.py::start(base_url)` | 插件启动依赖服务已绑定的地址 | 保留现有契约，由宿主绑定端口后交给应用启动对应插件资源；不新增无 HTTP 插件模式或改写插件协议 |

静态页面、CSS、DOM 渲染、HTTP 状态码、请求头检查、上传传输、静态资源路由和 SSE 连接管理继续属于 Web 层。设置验证、输入授权与归属等业务校验不能因迁移而删除，也不能只留在浏览器。

## 三、代码范围与实现约束

预计主要改动：

- 新增一个简洁应用入口，建议 `nexus/application.py`，负责现有资源及业务入口；模块名可依实际代码调整。
- `nexus/web/server.py`、`web/settings_api.py`、`web/task_api.py`：替换组装和业务接线，保留 HTTP 契约。
- `nexus/runtime/conversation.py`：承接模型历史转换，并从应用侧取得运行资源。
- `nexus/ling.py`：只做应用接入和复用现有工作操作所必需的调整。
- 测试中的原入口、全局状态 fixture 和 patch 位置，必要的 README 及文档索引。

`web/instructions_api.py`、`web/mcp_api.py`、`web/plugin_api.py`、`web/attachments.py` 仅在切换资源访问方式确有必要时改动，不顺手重写这些模块。设置迁移可落在独立的运行时模块，避免将全部实现塞入一个应用大类。

不改模型协议解析、Agent 推理循环、上下文压缩算法、子代理调度算法、任务状态机、数据库 schema、权限策略或工具实现。若实施中发现必须改动这些机制才能完成解耦，先说明具体依赖与范围影响，不悄悄扩大本轮。

其他约束：

- 先复用现有函数和状态映射；不为每个存储和工具创建接口、代理或抽象基类。
- 不做与职责移动无关的重命名、格式化、死代码清扫或全仓整理。
- 搬移实现后同步调用方，避免 HTTP 和应用各保留一套业务实现。只有实际调用者仍需要时才保留薄转发入口，不为省事长期堆叠兼容层。
- `python -m nexus`、`start.bat`、启动参数、默认网页入口、HTTP 路径、响应字段和 SSE 事件保持现有行为，不要求用户换启动方式。
- 原始历史、检查点、原生续接、审批、附件和插件数据照旧读取，不迁移实际运行数据。
- 前端源码默认不改；如果发现必须改变某个既有响应字段才能接入，应先检查应用适配是否足以保持契约，不能将后端整理转化为 UI 重构。

## 四、实施顺序与阶段完成点

### 1. 先移动资源所有权

抽出创建与关闭应用的入口，将任务控制器、主交流、事件、MCP、插件和进程资源接到该入口。Web 仍负责绑定端口、接收请求和打开浏览器；宿主将实际服务地址交回应用，保留插件需要的启动顺序。正常退出及现有关闭路径的清理保证必须保留。

完成点：创建应用不必构造 HTTP Handler 或启动浏览器；实际运行内核不通过反向导入 `nexus.web` 取得业务能力。使用普通方法即可，不为本轮新增可选宿主协议、依赖注入容器或统一资源管理框架。

### 2. 收回留在 Web 中的业务处理

依次迁移模型历史恢复、主交流输入与控制、设置／工作目录变更和工作业务操作。复用当前权威存储与控制器，调整现有 Web 调用。界面专用的展示转换保留在 Web，不以“完全无 Web 代码”为目标搬空整个目录。

完成点：相同操作从应用入口执行和经 HTTP 执行遵循同一业务逻辑；当前 Web 没有被迫适配新的业务契约。

### 3. 运行限定检查并交付

只运行第五节列出的受影响检查。更新 README 和本文实际变更、验证及限制记录后结束。不以 CLI、独立部署、模拟新前端或真实模型跑分作为本轮完成条件。

## 六、交付验收

1. 应用入口能在不构造 HTTP Handler、不加载网页的情况下初始化，并通过现有模拟模型完成输入、状态读取和停止／关闭。
2. 生产应用／运行时不依赖 `nexus.web` 才能取得模型历史、提交输入或变更设置；HTTP 层调用应用／现有业务模块。
3. 前端展示和连接代码不进入内核；更换布局、组件或整套 Web UI，继续使用现有 HTTP／事件契约即可，不需要改动 Agent、调度器和存储算法。
4. 当前启动、网页、审批、停止、父子协作、设置、附件及恢复语义保持；本轮不改变三执行位、同项目写入串行或 ask／yolo 边界。
5. 验证报告只列实际执行及沿用的证据、条件追加项和未验证部分，不用旧全量结果宣称当前全量通过。
6. 交付限于工作区代码与文档；提交、推送、运行副本同步和部署等待届时明确授权。

本轮完成后具备的是更清晰的可替换界面边界，不承诺已支持远程客户端、CLI 或 Android 本地运行，也不把本次职责整理宣称为上一轮真实模型问题已经解决。

## 七、实施与限定验证记录（2026-10-28）
