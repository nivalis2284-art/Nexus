# Nexus 业务收敛与优化计划

更新：2026-10-26。

状态：阶段 1—3 的关键选择已确认；所有者通过 `$stop-that-shit change -- 开始执行` 授权实施。阶段 4 实施与资料迁出已完成；阶段 5 的自动化、浏览器和真实模型验证已完成，所有者日常使用体验待本人确认。此次授权不包括提交或推送。

## 一、依据与目标

[《01-概念与原则》](../愿景/01-概念与原则.md)是最高标准；[《02-具象理想》](../愿景/02-具象理想.md)提供体验方向，不自动转为本阶段任务清单。

本阶段以做减法为主，重新划清 Nexus 的业务责任，收敛到一个由所有者掌握、能够自然交流并承接即时后台工作的底座。现有代码、框架和历史投入均可被调整或替换，不默认保留旧“持续性系统”这一整套业务。

所有者保留对发展方向、核心数据和外部行动的最高裁量权。排除采用整个 Hermes 或其他 Agent 产品作为底座、再给 Nexus 套壳的路线。可以借鉴成熟产品的具体体验、流程与局部实现；局部复用须保持边界清楚、可理解、可修改和可替换，不把核心资产及运行裁量交给不可控的平台。

本阶段的结果不等于已经实现记忆、自主学习、人格演化或个体连续性。它为以后单独研究这些问题提供可用的承载条件。

## 二、所有者已确认的产品范围

| 内容 | 本阶段决定 |
| --- | --- |
| 主交流入口 | 以一个长期交流的“灵”为中心；工作作为关联事项查看。普通会话退出主要入口。本次核实仅有一个 AI 互聊测试主会话，所有者已明确同意连同输入队列及独占附件清空，从新主交流开始；研究资料不在删除范围。 |
| 即时后台工作 | 保留并打磨：从交流中派发、查看、补充、干预，以及获得结果或阻碍说明。 |
| 时间与监听业务 | 全部定时、重复安排、网页监听和长期交代暂时退出。包含旧任务的一次性定时恢复业务。 |
| 自主活动研究业务 | 自由唤醒、每日自我回顾、静默经历等暂时退出。 |
| 专门人设业务 | “人设与自我”管理、专门条目注入、摘要生成与请求预览退出；保留所有者设置基本原则和交流偏好的简单方式。 |
| 静态长期记忆 | 原型与历史接管退出当前日常业务；原始数据、版本和研究成果保留。 |
| 迁出的含义 | 从当前 Nexus 业务中移除，允许暂时缺席；不以隐藏页面、换名或继续默认挂载插件代替退出。不要求先将旧业务产品化为另一个插件或服务。 |
| 无价值实现 | 经核实无用途的代码可在实施阶段删除；有研究价值的业务保留资料，未来再决定是否接回。 |

一个长期交流入口不要求一个永不切换、无限增长的模型上下文。必要的会话保存、历史读取、上下文容量管理及模型替换能力继续按实际用途设计。

时间安排业务退出不包括为了当前工作正常运行所必需的超时、重试等待、界面刷新或内部事件处理；这些机制分别按已有需求和实际缺陷判断。

## 三、必须保留的基础闭环

目标体验：**交流交代工作 → 后台实际执行 → 前台继续交流 → 按需查看或调整 → 交回结果，或明确提出需要所有者处理的事项。**

1. **自然交流与接收工作**：普通交代不要求填写任务管理表格；请求是否收到、工作是否开始应清楚。
2. **独立推进**：后台工作实际调用模型和工具推进；不以只生成计划代替执行，也不要求用户反复发送“继续”。运行环境仍需在线。
3. **交流与工作并存**：工作细节不淹没主交流，目标、结果、重要变化和待处理请求可以回到主入口；必要过程可查。
4. **补充与控制**：能向明确的工作补充要求，查看实际状态，停止后续行为，并在明确的条件下继续。具体交互在第一阶段确定，不从旧接口继承含糊语义。
5. **可靠回报**：工作完成、受阻或等待所有者时，有可理解的回报；不依赖自由唤醒、长期交代或每日规划才能交回结果。
6. **数据与主权**：会话原文、任务记录、必要操作结果和附件归属能够保存、查阅和按需导出；不以退出业务为理由清空历史资产。不自动重放结果未知的外部操作。
7. **必要能力接入**：现有模型接入、文件与命令、附件、Skill、MCP及插件能力按真实用途保留、精简或局部替换。不在本轮建设新插件市场、通用工作流平台或多 Agent 组织框架。

## 四、推进顺序与阶段交付

各阶段的研究、决定与验证结果在本文增补，按需要链接证据；不为同一事项重复创建研究、进度和验收文档。已经确认的范围内，常规实现选择由 Agent 自主判断；新增功能、关键交互变化或重大产品取舍再向所有者提出具体选择。

### 阶段 1：确定交流与后台工作的行为

工作：

- 还原当前“灵／普通会话／持久任务”各自承担的责任，形成精简后的主流程。
- 用具体情境确定：直接回答与后台工作如何分工，派活后如何反馈，工作详情怎样进入，用户如何指向某项工作。
- 研究运行中消息的含义：新话题、补充当前工作、改变目标、停止。界面需让用户知道消息会影响什么，不预设实现旧系统的全部队列模式。
- 明确主交流与后台工作各自的停止、等待和继续行为；区分页面关闭、服务退出及工作取消。
- 结合实际场景判断串行或有限并行，不为未来集群预建调度体系。

交付：一份简短的行为说明及代表性对话示例，覆盖普通交流、一次后台工作、运行中补充、需要决定、停止、结束回报。

完成条件：所有者能够通过示例判断日常如何使用；关键语义已明确，仍需取舍的点以具体选项提出。此时才确定界面和运行方案。

### 阶段 2：明确业务退出与数据保留边界

工作：

- 对第二节已确认退出的业务，逐项标出入口、模型提示和工具、自动触发、运行依赖与资料位置。
- 明确独立于自主插件的工作回报如何承接，避免迁出自主业务时丢掉已接受工作的结果。
- 清点主入口与普通会话的历史、任务、附件及归属；核实实际使用的数据目录。退出普通会话主要入口不等于删除其历史。
- 保留人设原件及备份、记忆原文与版本、调度规则与网页基线、长期交代、活动记录及相关关联信息。停用后的旧安排不再触发，旧资料仍能查找并重新解释。
- 为旧代码选择必要的留存方式，优先利用现有 Git 历史与已有研究材料，不在日常源码树复制一套旧系统，也不要求为迁出能力另建框架。

交付：具体退出清单、依赖关系、数据保留与查看办法，以及实施前后运行行为的差异。

完成条件：每项退出业务的影响和替代承接清楚；不会仅删除入口而留下自动运行，也不会连同资料、停止能力或工作回报一起删除。涉及破坏性数据处理或无法保留的资产时先说明并取得明确决定。

### 阶段 3：比较保留、精简与局部替换方案

工作：

- 以阶段 1 的行为为问题逐项比较，而非先选框架。重点是工作派发、上下文分工、补充控制、状态与回报，以及必要接入能力。
- 使用 Dot 研究交互和工作组织，使用 Hermes 等公开资料与源码研究局部机制；公开行为不作为其内部实现或可靠性的证明。
- 比较三类局部方案：保留并简化现有实现、借鉴流程后由 Nexus 自主实现、采用边界明确的库或局部代码。明确适用范围、实际减少与新增的维护责任、Windows 与当前模型工具的适配、历史资料能否承接。
- 核实异步派发、结果投递和跨重启恢复的不同含义；不把某项“后台能力”直接视为全部工作生命周期的替代。
- 选择能完成当前闭环、总复杂度更小且由所有者掌握的方案。不因外部项目有某个功能就引入，也不因已有代码而拒绝必要替换。

交付：按业务列出的方案比较与建议，说明替换哪些部分、保留哪些保证、尚需什么验证。采用整个第三方 Agent 套壳不进入候选。

完成条件：得到能够进入实施的具体方案；影响体验和范围的取舍由所有者决定，其余技术细节按实际需求自主选择。

### 阶段 4：实施业务退出与代码精简（已授权）

在所有者明确要求开始实施后执行，以必要的基础闭环为单位交付：

1. 先落实已选定的工作接收、运行、干预和结果回报路径，承接退出业务中仍需保留的基础能力。
2. 按已确认清单移除旧业务及运行接线，完成必要的数据保留安排；已有暂停和停止效果在切换期间继续有效。
3. 收敛主入口、工作详情与历史入口，统一必要的交互、状态呈现和运行装配。
4. 清除失去用途的路径、无调用代码和已完成交接的一次性兼容；根据实际依赖收紧配置、导出、测试和文档。
5. 复现并修复本阶段触及的真实缺陷。保留必要的模型协议兼容、错误提示、权限、取消与数据保护，不以删除历史补丁为指标。

交付：范围内的实现、必要检查、资料保留说明和真实使用结果。具体拆分依据方案，不提前决定必须大重写或必须沿用某种结构。

完成条件：保留的业务形成可用闭环，退出的业务不再参与日常运行，相关界面、提示、配置和说明一致。没有必要为迁出的研究原型先做内部重构。

### 阶段 5：验证第一版日常体验并收尾

验证以个人实际使用为准：保留的逻辑运行适当自动化检查；模型行为用少量范围清楚的真实任务核对，并如实记录模型、工具、是否有真实调用及其限制。只有涉及当前可证问题时，才扩展压力、兼容或长期运行测试。

| 场景 | 应看到的结果 |
| --- | --- |
| 普通交流及一次可执行工作 | 自然回答；需要工作时实际推进，成果或明确阻碍能返回。 |
| 后台工作进行时继续交谈 | 主入口可继续使用，工作不会因新话题无说明地丢失或重复启动。 |
| 给工作补充或调整要求 | 补充送到正确工作，何时生效及对既有目标的影响清楚。 |
| 工作需要批准或回答 | 请求有明确归属；回答后作用于正确对象，草稿与必要上下文不丢失。 |
| 停止与后续继续 | 后续行为符合已选定的控制语义；完成、取消、等待和收尾如实呈现。 |
| 关闭网页后回来 | 已接受工作的状态、必要历史和结果可查看，服务运行期间不因页面关闭而终止。 |
| 服务重启或真实工具失败 | 中断和结果未知可识别，有明确继续方式；不将失败说成完成或盲目重复操作。 |
| 旧业务退出 | 无定时／监听／长期交代、自由活动、人设专门注入或静态记忆接管继续生效；旧资料仍可定位、查看或按保留办法导出。 |
| 基本原则、模型与能力接入 | 所有者可以简单设置原则与偏好，确认实际生效；选定模型、工具与必要扩展可用且可停用。 |

交付：以场景为单位的结果和限制、未解决事项，以及更新后的启动与使用说明。基础闭环应能在已退出的研究插件不参与时成立，不以删除数量、测试数量或模型自评宣称通过。

完成条件：所有者实际使用后确认核心体验达到本阶段目标；未完成事项明确留存。本轮不安排记忆、自主学习或 RSI 的后续开发。

## 七、阶段 1—3 确认结果与实施约束

### 交流与工作行为

- 唯一主交流入口；工作作为关联事项，详情只读，补充或控制回到主交流，可明确选择目标工作。灵判断直接答复或派发后台工作；接收后及时说明。
- 主交流运行中的新消息先保存，在下一模型请求边界应用；新话题不取消工作。明确指向某个工作才转交，多个候选含糊时询问。
- 三个后台执行位，主交流独立。更多工作排队；等待用户或暂停释放执行位。同一 Git 根目录或非 Git 工作目录的修改串行，只读工作可并行；潜在副作用按写入处理。共享现有目录，不自动建工作树。
- 无目标的“停一下”只停止主交流；选中工作则暂停该工作。取消独立，暂停全部须明确。暂停后只补信息仍暂停，明确继续才恢复。
- 待审批/待回答请求持久保存并保留归属，普通聊天不当作答复；等待期间主交流可聊其他话题。
- 完成、受阻、待决定交给灵作上下文回报；完整成果在工作中。不建设独立通知中心，也不靠自由唤醒或长期交代回报。
- 完成后的修改沿用同一工作开始新一轮，保留原结果。关网页不停止服务端工作；服务重启须明确继续，结果未知不自动重放。
- 灵可从所有已配置可用模型中为工作选择和调整模型/思考强度，在下一请求生效；所有者明确指定优先。主交流模型由所有者选择。历史、工具结果和原始附件保留，不能以换模型丢弃必要输入。
