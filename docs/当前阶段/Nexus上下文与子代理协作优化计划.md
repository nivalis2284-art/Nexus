# Nexus 上下文、子代理协作与提示词优化计划

日期：2026-10-27。

状态：所有者已通过 `$stop-that-shit change -- 开始执行` 授权实施，范围内代码已落地；自动化验证与真实模型未通过部分见第七节。本轮不宣称已完成真实复杂任务验收。子代理采用本文推荐的异步协作方向；审批粒度和跨目录授权保持现有行为。本次授权不包含运行副本同步、部署、提交或推送。下文各阶段为目标和验收要求，完成状态以末尾实施记录为准。

## 一、目标与边界

本轮目标是提高 Nexus 作为个人 Agent 宿主的实际工作能力：让模型持续收到正确、完整且容量合适的上下文；让父代理能委派独立工作并继续推进；让提示词、工具接口、权限和控制行为相互一致。

依据 [《01-概念与原则》](../愿景/01-概念与原则.md)、所有者当前指令和已确认的主交流／即时后台工作体验实施。[《02-具象理想》](../愿景/02-具象理想.md)提供长期方向，不自动增加本轮需求。

保留所有者数据主权、原始历史与附件、可追溯外部行动、停止权、必要审批和未知操作核查。不以更强自主性为由扩大已有授权，不把所有者偏好升级为额外硬限制。

本轮围绕现有 Python、SQLite、JSONL、Agent、任务运行时及网页实现改进。DSH 作为局部机制参考，不引入整个 DSH、Cordis 或其他 Agent 底座，不预建团队、集群或分布式调度。不恢复已退出的定时、自由活动、人格或长期记忆原型，不把上下文摘要称作长期记忆，不把子代理上下文快照称作意识分支。

## 三、实施顺序与阶段产物

### 阶段 1：统一上下文容量，完成可恢复压缩

**要达到的行为：长交流、长需求和长工具结果在容量管理后仍能承接目标、约束和执行事实；同一旧历史不在每轮被重新摘要。**

1. 以当前实际请求为准，统一计算模型窗口、系统文本、工具 schema、消息、图片和有效输出预留。继续区分估算与提供商实测；有可用且口径一致的 usage 时校准估算，不把不同协议或不同模型的 usage 直接混用。不引入费用预算。
2. 压缩触发、摘要请求和最终发送共用容量口径；避免到消息选择阶段才无摘要丢弃旧目标。摘要调用本身也应容纳其输入和输出；遇到单条超大需求或无法形成合法输入时，明确说明容量问题及可行的分段方式，不无提示断尾，也不直接发送已知超限请求。
3. 删除摘要前统一 `[:4000]` 截断。对可重新读取的长工具材料，保留来源、必要标识和分页读取路径；用户要求、最新纠正及授权不得按普通日志处理。对确实超过容量的材料，以能覆盖其内容的有界分段摘要等直接方案处理，不引入通用检索平台。
4. 保存检查点内容、所覆盖的稳定消息范围和必要来源；模型输入由“有效检查点＋未覆盖历史＋当前事实”构成，界面及导出仍保留原始历史。成功摘要之后才提交替换关系；失败保持旧状态，不能保存半成品检查点或将截断摘要当作完成。
5. 主交流、后台工作及子代理使用相同的语义，各自保留历史边界。插件补充材料是当次请求的可丢弃投影，不得无意写入永久摘要或覆盖原始历史。摘要仍须保留完整工具调用／结果配对。
6. 模型切换后按目标模型重新预算，原始附件继续保存；检查点不能伪装成用户新指令，旧摘要不能覆盖最新用户纠正和任务权威状态。

主要触及：`core/agent.py`、`core/compaction.py`、`core/prompt.py`、`core/effort.py`、`session/store.py`、`task/store.py`、`runtime/conversation.py`、`runtime/callbacks.py`、`web/server.py`；按实际调用调整插件请求投影和统计显示。

**验收：** 长消息末尾的指定约束进入摘要输入并在下一次请求中可用；连续两轮和重启后使用已保存的检查点；高系统／工具占用下先正确压缩；每种 effort 的本地预留与有效请求一致；失败摘要不破坏旧历史；多工具批次、图片与插件投影不串入或丢失。请求容量错误明确可见。

### 阶段 2：承接模型原生状态，打通停止链路

**要达到的行为：充分使用当前支持协议提供的合法延续信息，停止操作能终止当前请求及后续派发。**

1. 将现有解析层的 continuation 接到 Agent、历史保存和下一请求转换。保存后续请求所需的原生元数据及来源，不默认把全量重复 SSE 原文再存入每条消息。
2. 按提供商路由、协议、模型和消息对应关系恢复可用的思考签名、推理项或响应标识；遵循具体接口对保留范围的要求。不得把裸思考文本随意拼回其他协议，也不能把未知签名当作合法签名。不同模型间保留通用内容，原生状态是否可用由实际接口能力决定。
3. 摘要覆盖旧消息时相应处理原生状态边界；未被摘要覆盖的合法尾部继续可用。旧数据缺少原生元数据时继续按原有通用历史运行。
4. 取消信号贯通 Agent、HTTP 流、摘要请求、工具等待及子代理；保留已产生的可确认输出和执行事实。文件原子写入、未知外部结果和停止进程树的既有保证继续保留。
5. 修复 `interrupted` 回报过滤；核对等待用户时仍有进程的中断说明。重启保留记录并等待明确继续，不自动恢复进程或重放结果未知的操作。

主要触及：`model/types.py`、`model/gateway.py`、`core/agent.py`、`core/protocol.py`、`core/thinking.py`、会话及任务历史、`runtime` 和 `ling.py`。

**验收：** 三类协议分别覆盖适用的原生状态、旧历史、跨模型切换再切回及压缩后尾部；流中停止、摘要中停止、工具待执行时停止均不继续派发；中断事实回到主交流。真实接口不具备的能力如实记为不支持，不以模拟通过宣称真实供应商全覆盖。

### 阶段 3：把同步子代理扩展为异步协作

**建议的第一版能力：父代理派出子代理后立即获得标识并继续工作；按需发送补充、读取状态和结果、等待结果或停止；子代理能选择已配置模型和思考强度。**

1. 为每个子代理建立明确的父归属、独立输入、历史、状态、结果与运行记录。复用现有 Agent、消息存储和任务事实机制，选择总复杂度更小的接法；不把子代理简单伪装成无归属的顶层工作。
2. 将模型工具契约改为“启动返回标识”，补齐读取、发消息、等待和控制的必要操作。具体工具拆分由实现决定，不预先要求通用消息总线。补充在子代理下一请求边界生效，不能串到父输入队列。尚未启动时先排入该子的输入；已完成子代理允许明确续聊，沿用同一标识开始新一轮并保留旧结果；已取消对象不因普通消息隐式恢复。
3. 结果或待决定事件按稳定标识回到正确父代理；父代理运行时在请求边界采用，空闲时由运行时接收并继续汇总。父代理不需要反复轮询维持活动。子代理结果属于工作事实，不能作为新的所有者授权。
4. 为每个子代理分别创建 `ToolContext`、回调、调用标识和进程归属；修正当前串行路径共享子代理 context 的接线，避免并发时覆盖回调、附件集合或调用标识。MCP 的关闭责任按资源实际拥有者保留，不能在父轮次结束时关闭仍在使用的连接。
5. 默认新上下文，父代理必须传递完整目标、必要背景、约束和附件。建议同时提供显式的父上下文快照选项：复制当时可发送的合法历史，之后相互独立；不共享可变列表，不继承可消费的审批凭证，不承诺跨模型缓存复用。该选项的首版范围见第四节。
6. 子代理可从已配置且可用的模型中选择 provider/model/effort；所有者明确指定优先。建议默认快照启动时父代理的当前模型与强度，父后续切换不改变已经运行的子代理；对子代理的明确调整在其请求边界生效。每次请求读取当前有效凭据，原始材料和既有工具事实不重放。
7. 子代理审批和问题带子代理、父工作及具体操作归属。一个子代理等待决定时，父与其他子代理继续处理不依赖该决定的工作；父不能替所有者批准，也不能让兄弟子代理消费同一决定。
8. 保留同项目写入串行，初版允许独立只读子任务并发。父等待子任务时不能占住子任务所需的执行位或写入资格；需要改变当前写入归属的部分，在实施前完成具体调度设计与死锁场景验证。首版不默认建设工作树，不宣称多个子代理可以安全并写同一文件。
9. 父任务暂停或取消后，所属子代理停止后续行为并清理各自进程；父代理普通一轮回答结束不等于取消已接受子任务。父工作不能在必需子结果尚未收齐时无说明地宣称全部完成。父结束、子等待、子失败和迟到结果均有明确状态。
10. 服务重启后保留父子关系、历史、已完成结果和待决定请求；中断运行等待明确继续，不盲目重放操作。界面在现有工作详情内展示父子关系、状态、结果和必要控制，不新增独立“团队管理中心”。

主要触及：`core/subagent.py`、`tools/subagent_tool.py`、`runtime/conversation.py`、`runtime/assembly.py`、`runtime/callbacks.py`、`runtime/controller.py`、存储、输入／决定／回报、相关网页与测试。旧同步工具调用记录继续可读；新调用采用新契约，不为历史记录长期维持两套执行器。

**验收：** 两个独立子任务和父工作能重叠推进；追加消息仅送到指定子代理；可选择模型和强度；父只接收结果及必要事实，完整轨迹按需可查；单子等待审批不阻塞其他工作；取消一个子不误杀兄弟，取消父能停止所属子；父等待不造成执行位／项目锁死锁；重启后不丢结果、不重复副作用，晚到结果不复活已取消的目标。

### 阶段 4：按真实能力打磨提示词与约束

**要达到的行为：模型清楚任务目标、授权、工具与控制方式，在范围内持续推进，在确实缺少决定或权限时准确请示。**

1. 按“所有者原则与偏好、角色职责、环境与有效权限、项目指令、技能、当前工作事实、工具”整理现有组装函数。清楚标出来源和性质；保持简单拼装，不为形式引入提示词插件框架。
2. 区分不可逾越的项目底线、所有者当前明确需求、长期偏好、项目具体约定和通用工作建议。当前明确指令可以覆盖一般偏好和建议，不能因模板措辞把“优先使用某工具”等同于硬底线。只有真实冲突或重大取舍才请求所有者决定。
3. 修正 bash 参数、Windows 执行方式等矛盾；说明实际可用的文件、命令、网络、MCP、子代理和控制能力，只声明本次挂载且可用的能力。提示中的权限模式、目录限制、停止与恢复语义应与实际运行一致。
4. 强化任务推进策略：行动完成已授权工作、常规实现自主选择、局部失败先调查并推进不受影响的部分、结果实际核对后再汇报。将“不重复相同调用”改为“无新信息时不机械重复；环境或依据变化后可以重试”。保留真实错误提示，不制造统一次数门槛或强制尝试表单。
5. 为主交流、后台工作、子代理分别明确职责。主交流派活后保持可交流；后台持续推进；子代理聚焦委派范围、说明发现或产出，不替父完成总目标。委派只用于能独立推进的子任务，不把当前关键推理交出后空等，不为满足并发指标硬拆任务。
6. 完善项目指令来源、目录适用范围和更新采用：在实际涉及子目录文件时加载相应规则，覆盖主交流及子代理文件工具路径；指令变化在后续请求生效，旧规则不重复累积。按实际来源读取范围控制容量，不能因超过单文件阈值静默遗漏整份指令。
7. 精简重复规则和已经由运行时保证、无需模型反复判断的细节；保留用户需要知悉的权限、结果未知及控制信息。不自动修改所有者原则文本，不把项目宪章或愿景改成角色设定。
8. 任务授权粒度和跨目录访问先按第四节确定，再改程序与提示。只改措辞不能解除程序审批；修改程序边界也不能只靠模型自行遵守。

主要触及：`core/prompt.py`、`core/workspace.py`、`ling.py`、`runtime/callbacks.py`、工具描述、`core/permission.py` 及对应设置／授权路径。是否改权限路径取决于明确采用的方案。

**验收：** 拼装出的请求没有互相矛盾的工具说明；存在来源和优先级；不同权限模式描述正确；用户指定例外不会被一般建议无依据否决；子目录规则可用且更新后生效；普通实现选择不反复提问，超出授权和会改变目标的取舍仍准确请求决定。用真实行为测试，避免只断言提示词含某个句子。

## 四、实施前需要确定的产品行为

下表保留拟订时的方案与取舍。开始执行后，本轮采用异步协作、新上下文与显式快照、共用三个执行位和父子停止语义；审批粒度与跨目录访问保持原状。实现细节由 Agent 在这些边界内自主判断。

| 选择 | 推荐方案 | 取舍与影响 |
| --- | --- | --- |
| 本轮子代理能力 | 异步启动、并发只读协作、消息、结果回收、控制、模型选择；同项目修改继续串行 | 能完成协作闭环，不扩成通用团队系统 |
| 父上下文快照 | 本轮在新上下文之外提供显式快照；必要事实由父补充，快照后互不共享变更 | 提高背景较多任务的委派质量；新增历史及协议投影验证工作，不预定 fork 的内部实现 |
| 并发执行位 | 建议复用当前三个后台模型执行位，父等待子时释放；主交流独立，调度保证父子能取得执行机会 | 控制当前本机实际并发而非费用配额；若不适合现有调度，先给出同等可解释的具体替代，不让子代理无限绕过执行上限 |

## 六、执行组织与完成标准

主代理负责上下文投影、父子生命周期和授权边界的整合判断；适合独立进行的协议适配、存储、工具／界面、测试任务按 disjoint 写入范围委派给 DeepSeek 子代理。涉及共享运行时的阶段先确定契约，再并行；服务不可用及时接手，不空等。

优先次序为：容量与摘要保真／持久化 → 原生状态与停止／中断 → 异步子代理闭环 → 依据最终能力打磨提示词和约束 → 真实任务对照与收尾。明显错误的接口文案可以随所触及阶段修正，无需等到最后。

完成标准是上述已选范围在实际任务中闭环、数据与控制保证保留、已知缺陷有回归证据。不能以测试数量、子代理数量、提示词长度或模型自评认定完成，也不以尚未开展的长期记忆、自主学习等愿景否定本轮交付。
