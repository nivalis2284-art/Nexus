## 最新补验：加权输入额度与真实修复闭环（2026-10-21）

所有者澄清上一轮“100 万”指输入 Token，缓存命中输入按 1/10 计算，并为补齐缺口再次授权 **1,000,000 加权输入 Token**；输出不计入这项验证额度。上一轮按输入加输出的更严格口径执行，旧账本没有缓存明细，保留原始数字，不追溯虚构折扣。

本轮透明转发器保留提供商实际 `input_tokens_details.cached_tokens` 等用量字段。使用整数十分之一计数，公式为 `输入 − 0.9 × 缓存命中输入`；缺缓存字段不给折扣，未完整成功的请求保留输入预留。测试驱动是显式运行的收费程序，不随 pytest 调用模型；同一账本只允许一个收费转发器持有写入租约，异常用量超过预估时停止后续准入。当前实际验证协议为 `openai_responses`；不宣称任意供应商的隐藏输入与本地估算严格等价。

### 真实行为与核验者的边界

沿用 `deepseek-v4.1-flash` 和真实 Responses、Agent、文件工具及 Edge，建立新的隔离复盘 fixture；复制上轮真实失败的稿件/日志和独立合成传感器资料。旧目标仍保持已撤回，不恢复旧任务或抹掉撤回。铺垫交流没有指定目标 ID、工具返回或逐项任务，由灵自行提出 `sensor240-indep-verify`。

1. 前两次内部审议遭提供商模型错误而中断，没有提交成功决定；保留未知用量并有界重试。实际界面中还拒绝了不必要的目录命令并停止反复列目录的铺垫交流。
2. 灵自主委派第一项修复，真实工作 Agent 读取原资料、写出脚本与说明、通过具体持久审批运行错误表达式和 AST 语法检查，并登记任务证据，最终 `task_finish` 成功。
3. 主 Agent 最初误说标准差/中位数从未算过。独立核验者指出原失败日志的崩溃前输出，并提供新的真实核验文件；灵读取后明确纠正消息与认识，目标从 v1 修订为 v2，进行中的委派保持有效。
4. 独立 Coding Agent **实际执行**生成脚本：240 行原资料 exit 0，但两行 A 超限反例在另一个字符串符号格式处 exit 1。原错稿、stdout 和 traceback 保留。新增资料通过三次明确标记的所有者“审议机会”进入本轮，而非伪称由本轮 MCP 监听自动触发。
5. 灵读取完整反例，根据真实结果自行追加第二行动，只修 A 分支与说明；独立再执行后，原数据与同一反例均 exit 0，缺失文件仍 exit 2。独立 DeepSeek 另行计算的均值、标准差、14 个异常 ID、13 个恒为 17 的 ID 间隔，与完整 stdout 一致。另测 3.85/4.15 的精确两位小数边界，A/B/2 均未误判超限，exit 0。
6. 灵实际读取修补后的完整日志，核对具体数值，取消旧等待安排，自主把目标收束为 completed，并在真实 UI 保存第六条正式消息，明确说这是独立核验者运行，不是委派任务或自己执行。第二项工作已写入修补，但目标结束时仍在等待额外 AST 命令审批，因此任务由目标控制取消；**不能将它记为第二次 task_finish 成功**。行动已结束，原有完成/取消状态和来源均保留。

本轮形成 1 个目标、2 个行动、4 项未来回顾记录、6 条正式消息。没有模型时钟加速或循环间隔覆盖。本轮没有新建监听规则，也没有实际到期的计划触发，三源/MCP 证据仍引用上一轮真实监听与明确披露的加速计划场景。首次新目标并非预写，后续纠错有人工提供的真实测试反馈，不夸大为无人干预的长期自主研究。

### 补验发现的工程修正与剩余边界

- 运行中工作原来只收到初始委派。现按每次模型请求刷新所属目标的最新事实与认识，父任务和子代理均适用；原任务目标、行动 key 与已接受权限不随认识修订改变。新增真实 Agent/脚本化提供商回归验证第二请求收到修订，而任务目标未改变。
- 实测模型把两条已批准 AST 命令改写成等价新命令，导致额外审批。任务上下文已澄清“只对原工具与原参数允许一次派发，批准不代表已执行”；shell 工具说明同步澄清接收命令字符串，避免 JSON 参数数组字符串。没有放宽精确审批或添加隐式通用 shell 授权。
- 独立复核复现了全局暂停延迟落定后恢复遗漏。已在请求控制器前持久保存暂停意图，并按既有命令账本核对自主暂停和真实 Worker/资源停止的具体记录；用户明确恢复早于执行完全退出时，后续对账仍能接续。同一版本差的用户另行暂停不能被认领，任务编辑、待答审批、未知效果和任务删除也不能被绕过。35 项 runtime 回归覆盖真实控制器及延迟落定场景。
- 重开实际 UI 又确认已取消任务仍显示、接受旧审批。终止任务现在同事务退休待答决定和未消费批准；旧终止记录也不再展示为可答请求，服务端拒绝作答。暂停/恢复保留待答决定的既有行为不变；21 项 task store/runtime 回归通过。实际 Edge 重开确认取消请求不可处理，最终通过 UI 终止隔离自主实例，6 条消息、completed 目标与来源仍保留。
- 当前闭环依然暴露模型的判断错误与过早肯定，三十秒测试联系窗口下消息较密；默认联系等待仍为 24 小时。正确读取反例并修订是已观察行为，不证明后续长期自主联系质量、时间判断与语义去重已经稳定。

## 实现边界与运行说明

- Nexus 服务存活即可运行自主循环，不依赖网页轮询启动。关闭网页后仍可保存消息，退出服务会中断；不会部署额外守护服务或站外推送。
- 保底间隔默认 6 小时、联系等待默认 24 小时、单次输出上限默认 2048 Token、审议最短间隔默认 30 秒。都是可调整的工程默认值，不将到时等同必须联系。模型可以形成/修改/取消有明确时区的未来回顾，不要求每天填满计划。
- 每轮审议最多 8 个 Agent 步骤，读取真实资料与提交提案；较长工作委派现有单 Worker 任务执行器。初始 6 步上限在真实多资料场景中留下过少的纠错与提交机会，已据实调整，但保留有界步骤和 Token 准入。多个工作可以并存和排队，本轮未增加多个任务模型同时执行。
- 自主读取限于明确目录，写入限于成果目录，并与行动接受时的授权取交集；缩小范围暂停旧工作，扩张范围不会悄悄扩大已接受动作的权限。外部或越界调用仍需要具体持久审批。MCP 名称/只读声明均不替代审批。
- 自主工作不虚构用户指令，不隐式携带所有者最近一次附件。附件必须明确属于该任务；技能只从当前与已接受授权交集内的工作区技能目录发现。工具能力仍由真实执行路径与授权共同决定。
- 重启将未完成审议标记中断、未知请求保留额度；已提交行动在任务创建/提交间隙复用稳定 ID 恢复，不盲目重放未知外部效果。全局暂停只恢复自己暂停且版本未变的工作；人工单独暂停、未知操作和待决策任务须核查。
- 目标认识修订不会自动取消有效工作；灵可提交带版本和原因的 cancel_actions，停止无效行动后用新 key 重新委派。目标完成/放弃会停止相关行动、计划和监听。任务目标/目录绑定变化不能沿用旧自主授权。删除关联工作不会让自主循环卡死或重建同一工作；已保存的关键结果不因任务删除而级联消失。
- 监听首版支持 UTF-8 `.txt`/`.md`/`.markdown`，轮询快照有覆盖间隙；单文件读取 2 MiB、单项监听 512 文件、证据前 64 KiB，服务存储有上限。缺失、截断、覆盖不足和实现替换的间隙必须作为事实保留。
- 不建设完整插件框架。高级 owner API 的 `observer_command` 可替换兼容的 stdio MCP 参数列表，主 Agent 无权修改启动命令。换实现时保留 `tasks.sqlite3` 和旧监听日志；新 epoch 重新建立基线，并报告无法还原的观察间隙。

## 2. 各缺陷的修法与依据

### A · 请求来源校验（`nexus/web/server.py`）

绑定 `127.0.0.1` 不构成授权边界：任何页面都能访问 loopback，DNS 重绑定也能把恶意域名指向这里。
在路由之前依次校验三层：

- **Host**：只接受本服务实际端口的 loopback（`127.0.0.1` / `localhost` / `::1`）。重绑定域名不再匹配，请求在进入路由前被拒。
- **Origin**：存在时必须同源。浏览器在跨站写上一定会带它。
- **Content-Type**：带 body 的写操作必须是 `application/json`。浏览器无法在不触发 CORS 预检的情况下发送该类型，而 `text/plain` 正是攻击者能发的形状。

缺失 `Origin` 的请求放行——`curl` 与既有测试不发它，浏览器也无法在跨站写上省略它。

**明确不属于沙箱分级**：`docs/参考/暂缓项.md` 一暂缓的是"Agent 技术上能碰什么"的强制隔离；
本项是"请求是否来自本机用户"的应用层校验，不需要引入沙箱，也不预设权限边界。

### B · 双面板批准错位（`nexus/web/ling.js`）

单一 `notificationDraft` 改为按通知 id 的 `Map`：每个面板持有并提交**自己那条**通知的交互。
选择 Map 而非"同时只允许一个面板"，是因为后者会在用户对照两条通知时反复丢失已展开的详情，
且每秒轮询重绘时还需额外维护"当前唯一面板"。提交时优先使用调用方传入的面板状态；
无参调用仅在恰好一个面板打开时解析，多个打开则拒绝——绝不猜"最近打开的那个"。

### C · 挂起后审批失效（`nexus/task/store.py`）

根因是 `control_version` 前进后，`pending` 交互仍停在旧版本，而作答要求版本严格相等，
于是该交互**既不能作答也不能被清除**，任务无法 `finish`，唯一出路是删除任务。

抽出 `_advance_control_version()`，让**每一个**推进 `control_version` 的写入都在同一事务内
把仍存活的记录带到新版本，覆盖 `command()`、用户生命周期操作、`recover_interrupted`、
`hold_queued_at_startup`、`confirm_wait` 等全部入口。

关键区分：

- **状态变化**（挂起、恢复、重新启用、归档、重启恢复）→ 用户没改目标，旧授权**保持有效**；
- **目标变更**（goal / effective_goal / workspace）→ 旧授权**显式失效**（标记 `expired`），
  作答时返回明确提示要求重新授权，而不是静默复用或悬空。

### D · 审批语义（`ling.js` / `tasks.js`）

审批改为「拒绝」/「允许」两个明确按钮，提交 `false` / `true`。
删除"允许 / 拒绝，或说明"这类引导用户写字、但语义不明确的占位符。
`question` 类型保持自由文本不变。**未新增"允许并附条件"的语义**——那是新需求。

### E · resume 丢队列（`nexus/runtime/controller.py`）

`pause()` 等待超时后 `_active` 未清，此时 `resume()` 的入队被 `_enqueue` 静默丢弃，
worker 退出后队列为空，任务永久 `queued`。

修法：`_active` 期间**仍然绝不入队**（这是不并发执行的关键）；resume 只把持久状态改为
`queued`；唯一 worker 在 `finally` 释放 `_active` 后读一次持久状态，若仍是 `queued` 就重新入队。
无轮询、无额外锁嵌套，`request_id` 幂等与关闭语义均保持。

### F · 旧授权跨目标复用（`nexus/task/store.py`）

`answered_approval()` 只按 `tool + arguments` 匹配，不看目标。
现在目标变更会把该任务的旧审批标记 `expired`，因此只有"当前目标下取得的授权"能被复用。
另有反向用例保证**未变更目标时旧授权仍可复用**（防止修过头）。
