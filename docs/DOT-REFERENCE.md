# Dot 对 LingNexus 的参考价值

资料核对日期：2026-10-22。本文在持续性简化与代码验证完成后编写。官方事实根据公开产品文档；LingNexus 现状根据本仓库代码；后续建议属于本次分析，不代表已实现或已批准的新增需求。

## 判断

Dot 与 LingNexus 的契合点很高：持续交流入口、独立工作、跨轮次推进和主动唤醒，都可以围绕同一个长期协作者组织。值得借鉴的是长期职责与一次工作之间的关系，以及用户如何理解、干预工作。当前已有任务库、工作工具、唤醒队列和独立 MCP 调度服务，适合逐步补齐体验。

公开文档没有披露 Dot 的内部调度器、数据库结构、记忆算法或完整执行架构。本文的职责划分是对 LingNexus 的建议，不能据此断言 Dot 内部采用同样方案。

## 1. 长期职责与一次工作分开

**官方事实。** Dot 可以跨会话跟进持续职责、调整下一步，并自行决定暂停与再次唤醒。官方软件反馈示例是连接反馈来源和代码项目，调查报告的问题并准备修改供代码审阅。该示例支持“持续观察—调查—准备修改”的方向，但没有证明存在某种固定的重复问题判定算法。[Meet dots](https://learn.chatgpt.com/docs/dots)

**项目现状。** 灵已有持续交流入口，能够通过 `work_start` 发起独立持久任务、查询结果和干预执行。定时与网页监听已经由独立 MCP 服务管理，Nexus 接收唤醒并执行。此次重构让单次任务能够持续推进；任务完成后依然结束，不会因此自动成为一个长期职责。

**建议。** 将“持续维护某个项目”作为可修改的目标与说明保存；每次唤醒时读取目标，决定继续已有任务、发起一次工作、等待或沉默。一次修复完成后，长期目标仍保留。最初只需少量可编辑信息：目标、相关来源、当前工作引用和下一次检查安排；不必先做通用工作流引擎。

可先验证一个具体场景：“持续关注指定反馈源，发现需要处理的问题后调查，准备修改并汇报。”外部来源能否读取、是否能获得事件，需要按实际工具能力确定；不能把公开网页监听说成任意账号和私有服务的完整监控。

## 2. 权限落在具体行动上

**官方事实。** Dot 对影响账户或分享信息的动作进行审核，可执行、请求批准或交还用户。自定义规则列出四种处理方式：无需询问、明确要求时执行、执行前询问、交给用户。官方也说明规则不等同于绝不出错的硬保证。[Control your dot](https://learn.chatgpt.com/docs/dots/controls)

**项目现状。** `nexus/core/permission.py` 已有按工具及目标匹配的 `allow/ask/deny`；文件路径与命令是已有匹配对象，持久任务复用审批交互。因此无需再给“自主 Agent”另造一套授权系统。当前 MCP 工具在该目标提取函数中没有细粒度参数映射，不能声称已能按某个服务的具体账号、资源或收件人精准制定规则。`yolo` 模式直接放行，不是自定义规则编辑器。

**建议。** 后续有明确需求时，先把现有规则做成用户能理解的行动设置，例如“允许调查和准备本地修改，提交外部系统前询问”。需要对某个 MCP 动作细分时，再补该动作的目标识别。技术问题的解决应复用现有审批链路，不以研究 Dot 为理由增加第二套审查、风险等级或强制验收手续。

## 3. 用户能看懂的任务管理

**官方事实。** Dot 的 Activity 可查看任务进展、文件、结果和待输入请求；Scheduled 管理定时工作。暂停当前主体工作、停止委派工作和取消定时安排是分别管理的动作，暂停后可以恢复。[Control your dot](https://learn.chatgpt.com/docs/dots/controls)

**项目现状。** Nexus 已有待开始、排队、执行中、暂停中、已挂起、等待用户、完成、取消，以及独立的一次性安排和交互记录。用户示例中的展示可以由这些现有信息组合，而不必立即增加一套状态机：

| 用户看到的任务 | 主要说明 | 当前数据可以如何表达 |
|---|---|---|
| 插件系统重构 · 执行中 | 正在处理业务边界 | `running` 加当前摘要 |
| Memory 模块优化 · 已挂起 | 无限期挂起，手动恢复 | `paused` 加挂起理由，无恢复安排 |
| 依赖更新 · 定时恢复 | 明天 09:00 再检查 | 挂起状态加既有一次性安排；显示实际时区和执行方式 |
| 生产部署 · 等待确认 | 需要用户批准 | `waiting_user` 加真实审批请求 |

**建议。** 界面主要展示标题、当前说明、状态/下一次安排和可执行动作；过程记录进入详情。本次只补充摘要、挂起说明与消息不自动恢复的行为，没有交付以上完整任务管理器。以后做界面优化时，应保持暂停任务与取消未来安排的区别清楚可见。

## 4. 上下文、任务记录与记忆各司其职

**官方事实。** Dot 的任务有自己的会话，获得与该工作有关的指令和上下文；记忆和自存笔记用于延续偏好、决定与职责，不是每次携带全部对话。[Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

**项目现状。** 灵的主会话与独立任务已有分离的历史、摘要和工具结果，任务状态也持久保存；这仍不等同于完整长期记忆。独立任务目前由一个 Worker 串行执行，不能把多个待执行任务的存在描述为多个任务模型并行推进。

**建议。** 长期目标读取少量稳定信息；单次工作使用自己的任务上下文；完成后向灵返回结果摘要和工作引用。只有确实需要长期记住的偏好与决定才进入可查看、可修改的笔记。初期可以复用文件、Skill 与现有读取工具，不必预设向量数据库、自动人格演化或复杂的记忆评分机制。

## 5. 等待期间不必反复调用模型

**官方事实。** Dot 支持保存的定时安排和支持的事件触发；主动事件监听需要明确指定来源与事件。连接某个服务本身不会自动创建监听。[Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

**项目建议。** Nexus 保存工作状态、接收唤醒、执行模型与工具并保存结果；独立调度 MCP 服务决定时间和监听变化、发送唤醒。灵在被唤醒后判断是否需要工作或回复。等待期间交给定时器或监听，不需要让模型持续输出“继续等待”。Skill 可以说明某类工作的处理方法，MCP 提供实际动作，二者不替代 Nexus 的运行与状态管理。

当前仍有两条安排路径：独立 MCP 服务负责灵的定时/监听唤醒；`nexus/runtime/scheduler.py` 负责持久任务的一次性恢复。未来如要统一管理，应先决定如何把“恢复某个任务”接到已有唤醒链路，并保留用户选择的自动/确认语义；本轮没有迁移这条路径。

另一个实际缺口是结果反馈：任务事件已经持久保存，灵可在后续交流或唤醒时读取，但“任务完成事件”尚不等于立即触发灵的新一轮处理。需要时可让该事件复用现有唤醒请求，而不另建消息编排系统。

## 6. 运行环境决定持续性的边界

**官方事实。** Dot 拥有云端计算机，可在用户个人设备离线时继续云端工作；使用连接的个人计算机时仍依赖该设备在线。[Connect computers and apps to your dot](https://learn.chatgpt.com/docs/dots/computers-and-apps)

LingNexus 当前由本地服务运行。关闭网页后服务端任务可以继续，电脑关闭或 Nexus 服务退出后不会继续执行。本轮没有引入云端托管。若以后确实需要全天运行，可先部署现有服务到常开环境，不必把云电脑、多端同步和远程接管一并列入持续性的前置条件。

## 后续建议的顺序

以下仅供所有者决定下一轮需求：

1. **先优化现有任务管理呈现。** 用现有状态、理由、结果和安排表达用户示例；验证能否一眼判断“在做什么、为什么等、何时继续”。
2. **用一个长期职责做最小实验。** 保存可编辑目标，复用 MCP 定时/监听与现有独立任务；验证一次工作结束后职责仍能继续维护，不把有限任务永远保持运行。
3. **按需打通工作结果与灵的唤醒。** 复用已有事件和唤醒队列，让灵及时理解结果，并决定汇报或等待。
4. **遇到具体需求再细化行动规则和长期笔记。** 从已有工具权限和文件/Skill 起步，避免先建完整平台。

最适合作为后续验收场景的是一条可观察的闭环：给定长期目标和来源 → 定时或变化唤醒 → 调查/推进一次工作 → 保存结果 → 按要求反馈或等待 → 用户能暂停、补充并明确恢复。一次成功闭环后，再根据实际体验选择扩展点。
