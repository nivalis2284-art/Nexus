# PRD｜Nexus 现有系统优化与功能业务关系图

> 状态：待交付阶段四（需求复核与技术研究）
> 建议位置：`docs/PRD.md`
> 本文档规定本阶段的交付目标与边界，不预设具体技术方案。验收以当前项目真实运行情况和已确认的产品需求为依据。

## 1. 需求

在**不新增产品功能**的前提下，对 Nexus 现有代码进行一次面向实际问题的整理与优化，重点包括：

- **架构与可维护性：** 梳理真实模块职责、依赖和调用关系，修复有证据表明影响理解、修改或维护的结构问题。
- **性能与资源使用：** 查找并优化有实际影响的性能瓶颈、无效开销或资源管理问题；避免为了理论指标而牺牲可靠性或引入复杂度。
- **技术债务与缺陷清理：** 清理确认无用、重复、过时或容易造成问题的代码，修复在清理中发现且与本阶段相关的真实缺陷。
- **功能业务关系图：** 以现有源码和可验证的运行行为为依据，梳理项目当前实际具备的功能、模块及其联系，交付一份可在浏览器中打开的 HTML 可视化关系图。

## 2. 背景与目标

Nexus 已具备可运行的 Agent 基础能力。当前阶段不以继续扩充功能为目标，而是先降低现有实现的复杂度、消除影响维护的技术债务，并明确各功能之间的真实关系，为后续开发建立更清晰可靠的基础。

本阶段的成功不是代码量变少、模块数量变多或技术看起来更先进，而是：**现有功能保持可用，实际工程问题得到合理改善，项目结构更易维护，同时让非技术人员能够直观看懂现有业务与功能如何协作。**

## 3. 我的原话摘要

> “下一步是对代码进行优化，这一步无需引入新的功能，而是优化架构和性能以及清扫技术债务，并画出功能业务路线图，以 HTML 的形式呈现。这一步比较简单，需求也比较明确，直接产出 PRD 即可，然后进入阶段四。”

结合此前明确的开发原则：**不立假想敌；没有现实需求时不提前预设技术或增加基础设施；不为形式主义而解耦；避免 Agent 因局部问题无限试错。**

以上为当前需求与既有偏好的归纳；如与实际意图不一致，应在阶段四复核，不将摘要中的理解当作额外授权。

## 4. 对原话的理解

- “优化架构”指改善**已存在的实际维护问题**，不是强制重构、分层、插件化、服务拆分或更换技术栈。
- “优化性能”指先识别有意义的问题，再按证据选择优化方向；不预先设定任意加速百分比或要求所有路径都做微优化。
- “清扫技术债务”包括冗余逻辑、失效代码、不合理耦合、维护成本高的局部设计与相关真实缺陷；不等同于无差别重写。
- “功能业务路线图”理解为**功能/业务关系可视化图**，用于展示当前功能树、关键模块和它们之间的调用、数据流或依赖关系，**不是按日期排列的研发排期图**。
- HTML 是本次**交付物的呈现形式**，不是要求新增到 Nexus 产品里的功能或导航入口。

这些理解用于帮助阶段四开展调查；具体技术判断仍以源码、实测和必要讨论为准。

## 5. 功能范围

### 本阶段必须交付

1. **现有代码优化：** 对识别出的实际结构问题、可维护性问题和技术债务进行合理清理与改进；优先处理高价值、低风险的事项，必要时保留合理的现有设计。
2. **有依据的性能改进：** 对发现的真实瓶颈或明显无效开销做针对性优化，并提供适当的前后对比或可复核证据；若没有发现值得优化的瓶颈，应如实说明，不制造工作量。
3. **回归与兼容性：** 尽量维持现有已确认功能、用户操作路径、对外接口、配置和重要数据的兼容性；修复真实缺陷可以改变错误行为。重大兼容性或产品行为调整须先确认。
4. **HTML 功能业务关系图：** 交付 `docs/BUSINESS-MAP.html`（可调整文件名，但统一存入 `docs/`）。覆盖当前实际存在的主要功能与有意义的子功能，按业务/模块组织，清晰标出跨模块关系并说明连线含义；可直接在本地浏览器查看，重点保证**完整、易读、可追溯至现有实现**。对尚未实现或仅在愿景文档中出现的功能应明确区分，不得混为已交付能力。
5. **结果说明：** 简要整理具体优化点、依据、验证结果、已知限制及未解决的技术债务，放在 `docs/` 下的相应研究或交付文档中。

### 本阶段明确不做

- 不新增产品功能、额外业务能力或超出整理需要的 UI 功能。
- 不因假想风险而增加沙箱、插件系统、复杂架构、抽象层或其他尚无真实需求的基础设施。
- 不为统一风格而大规模重写正常工作的代码，不以追求模块数量或代码行数为目标。
- 不将愿景、历史讨论或参考项目中的未确认能力误认作本阶段的开发要求。
- 不将关系图变成新的项目管理系统；它只用于理解**当前功能与业务关系**。

## 6. 验收标准

1. **现有功能不退化：** 相关既有功能和关键用户路径经过与修改范围相称的测试或实测；未出现未获确认的功能削减或重大行为变化。
2. **优化有实际依据：** 每项重要重构、债务清理或性能优化能说明解决了什么真实问题，以及如何验证效果；不得用代码量变化代替成效。
3. **性能结论可信：** 有性能改动时，提供可复核的测量或对照；没有可靠数据时注明，不虚称提速。
4. **关系图真实完整：** HTML 文件可在浏览器中打开；主要已实现业务/功能能被找到，关键模块及跨模块关系可辨识，连线意义清楚；图中的已实现能力可与实际源码或操作对应。
5. **文档与结果一致：** 交付物统一存放 `docs/`，报告区分已完成、未验证和暂缓事项；不将尚未解决的问题伪装成完成。
6. **范围受控：** 未擅自引入新业务功能或无需求的基础设施；若确需扩大范围，已经获得明确确认。
