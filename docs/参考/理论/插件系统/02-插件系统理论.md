# Nexus 插件系统理论

更新：2026-10-23。

**状态：理论方案已确认。** 本文汇总已确认的系统关系、共同规则与使用行为，作为后续落地规划的依据。理论定稿不表示能力已经实现，也不等于代码开发授权或工程验收通过。具体接口、包格式和技术选型由实施方案落实。

长期方向服从 `docs/愿景/` 与所有者的明确要求。自主性业务、主干与分支、记忆算法等不在本文中确定。[理论审视与方案比较](03-插件系统理论审视.md)保留研究过程与采纳对应说明；当前结论以本文为准。

## 一、目的与边界

插件系统服务于现有功能打磨，以及复杂功能的频繁迭代。希望功能能够独立开发、调整和替换，减少每次增加同类功能都修改 Nexus 共同部分的需要。

它应成为可持续使用和演进的设计，而非一次性演示；同时不要求现在预测并建设所有未来扩展能力。

核心方向是：**插件自带接入声明，Nexus 按共同约定自动接入。** 所有者负责选择、配置和管理功能，不需要每次手动连接流程、安排材料或拼接页面。

“不修改核心”的适用边界是：使用已有扩展方式增加同类功能。出现新的参与时机、内容类型或交互方式时，允许演进共同约定，不承诺任意未来功能都无须修改 Nexus。

## 二、基本概念

| 概念 | 大白话说明 |
| --- | --- |
| 插件 | 一项可管理的扩展功能，可以带有能力、接入声明、规则、设置和界面 |
| 独立服务 | 实际执行功能的程序；可以独立于 Nexus 核心运行 |
| MCP | 发现、调用和交换外部能力与资料的共同协议 |
| 扩展点 | Nexus 约定允许插件参与的位置或时机 |
| 注册声明 | 插件说明自己提供什么、需要什么、怎样参与的登记资料 |
| 宿主 | 承载、管理和使用这些插件的 Nexus |
| 扩展契约 | 双方共同遵守的参与时机、输入输出和行为约定 |
| 接入实例 | 实际配置的一份接入，关联具体服务、设置和资料来源 |
| 本次调用范围 | 说明这次为哪项活动处理什么问题，依据什么材料、采用什么设置 |

插件与独立服务不要求一一对应。插件可以使用一个或多个服务，服务也可以被复用；只提供规则或简单设置的插件，不必因此启动独立程序。

具体采用怎样的目录、包格式和进程组织，留待实施方案决定。

插件定义说明“这种功能是什么”，接入实例说明“实际使用哪份配置和资料”，本次参与说明“这次用了什么”。区分这三者不等于现在要求提供同一种插件的多实例管理功能。

## 三、五类按需选择的参与能力

以下是职责分类，不是要求建设五套独立协议、服务或数据库，也不要求每个插件全部具备。

| 能力 | 负责什么 | 例子 |
| --- | --- | --- |
| MCP 接入 | 灵或 Nexus 使用外部功能与资料 | 主动查询记忆、展开原文 |
| 消息接收入口 | 插件把新情况交给 Nexus，保存、排队并安排投递 | 外部条件满足后发送事件 |
| 上下文参与 | 在约定时机为模型请求提供或整理材料 | 请求前自动召回相关记忆 |
| 宿主信息使用 | Nexus 向插件提供消息、记录和运行状态 | 召回所需的当前问题与近期交流 |
| 界面接入 | 插件提供设置、页面或交互内容，由 Nexus 装入 | 记忆设置和记忆管理页 |

MCP 与消息入口的细分职责见[专项说明](01-MCP与消息接收入口.md)。MCP 支持哪些能力，以双方实际实现为准；接入 MCP 不自动获得灵的全部历史，也不自动获得请求前执行、事件投递或界面挂载能力。

## 四、注册与自动接入

插件提前说明需要的参与方式。Nexus 读取声明，登记相应工具、上下文能力、信息需求和界面入口。

登记资料需要能够表达以下关系，具体字段未定：

- 插件的身份、用途和版本。
- 提供哪些能力，分别如何使用。
- 需要哪些设置、服务或其他能力。
- 在什么场景、什么时机参与。
- 接受哪些输入，返回哪些结果。
- 如何呈现设置、状态和操作界面。
- 启停、更新与数据处理的相关说明。

**注册、启用、实际可用、本次参与是不同概念。** 已注册的插件可以尚未启用；已启用的服务可能尚未可用；可用的插件也不一定适用于每次请求。

调用插件不要求总由模型主动提出。普通程序也可以按照接入约定调用能力，例如请求前自动使用记忆查询功能。

### 4.1 声明能力与关系

声明负责说明能力、输入输出、适用场景和依赖；搜索算法、复杂判断与业务流程由插件实现。Nexus 无须理解记忆插件内部如何搜索和挑选资料。

区分没有它就不能运行的依赖、需要前一步输出的数据依赖、存在时使用的可选增强，以及最终展示顺序。执行顺序不能靠插件安装顺序或页面位置猜测。无依赖的同类结果按共同约定稳定组合，具体排序与容量规则在实施方案中说明。

插件代码版本、Nexus 扩展契约版本、MCP 协议版本及插件数据格式分别表达。说明所需能力和兼容范围，不承诺永久兼容所有旧版本。

### 4.2 多入口共用能力

灵主动查询、编排器自动召回和用户在页面中搜索，可以复用同一项搜索能力；每次调用保留发起方式、所属活动与结果用途。

插件分别声明能力供哪些入口使用。界面专用操作不会因登记而自动成为模型工具，普通界面操作也不需要先请求模型。读取与修改分别定义，沿用实际操作要求与已有授权，不因注册自行扩大权限或重复要求用户确认。

### 4.3 共同职责

注册管理认识插件及接入关系；通用运行过程管理活动、模型与工具调用的参与时机；上下文编排准备请求材料；宿主信息接口提供约定资料；界面宿主容纳插件界面。

这些是同一系统内的职责，可以在同一个程序中实现。上下文编排器不接管插件启停、整个活动调度和全部界面管理。

## 五、上下文编排

### 5.1 职责

上下文是这一次模型请求能够使用的材料，包括指令、消息、相关资料、工具结果和可用工具说明等。

上下文编排器是负责准备这些材料的共同机制，不以所有者手动编辑或接线为使用前提，也不预先规定它必须成为独立服务。

它依据当前活动与插件声明，安排：

1. 本次哪些插件参与，需要什么输入。
2. 取得和处理哪些材料。
3. 材料的用途、来源与放置位置。
4. 多个来源怎样组合，容量怎样分配。
5. 最终本次实际使用了什么。

记忆插件负责记忆查找等具体算法；编排器负责共同的请求准备，不接管每个插件的业务。

### 5.2 接入位置与参与方式

插件可以声明将结果提供给“相关记忆资料”等有明确含义的位置，由编排器转换成当前模型可接收的形式，不要求插件直接修改整份原始 API 请求。

提供材料、整理已有内容、参与某个处理时机，是不同作用。普通提供者返回材料；整理者声明可修改的材料范围；宿主统一组合、安排容量并转换为模型格式。插件之间通过约定结果协作，不以任意改写整份请求作为共同默认方式。

本次请求使用共同的材料表达，能够说明内容、用途、来源、适用活动及需要时的原文引用。这是临时请求材料，与长期记忆中的记录分别管理。执行先后依据数据依赖，最终放置依据材料用途，两者分别说明。具体字段、可用位置和各处理者的范围由实施方案列明。

指令、观察材料与历史事实应保留各自含义和来源，不因插入位置改变就被混成所有者的新要求。

插件不能仅靠给内容标记“最高优先级”改变已有指令关系；具体行为规则仍服从所有者已确认的要求。

### 5.3 请求与历史

为本次请求临时提供材料，不等于将它永久写入对话或记忆。召回、记录新经历和更新记忆是不同操作；各自在何时发生、是否留存，需要明确约定。

召回内容不会因为进入请求而自动记成一段新经历。永久写入走明确的写入能力或后续处理时机，并保留实际来源。

编排按每次模型请求发生，不仅限于每条用户消息开始时。同一段活动可能包含多次模型请求；有机会参与不等于每次都需要重复检索。

### 5.4 可理解与可核对

**提供按需查看能力，日常聊天保持简洁。** 所有者能核对本次材料来源、各插件是否参与、选取结果、缺失或未采用原因，以及实际发给模型的内容。

区分编排规则、本次准备过程和实际发出的请求。只准备但未发出的材料不能标作模型已经看到；外部服务未返回的内部细节不能伪装成已知事实。查看的是宿主实际发送和取得的资料，不承诺展示模型未公开的内部思考。

查看不要求手动编辑请求。具体入口、记录范围和保存期限在落地规划中确定，不因具备查看能力而默认永久保存所有请求。

## 六、宿主信息出口

### 6.1 三种取得信息的方式

| 方式 | 用途 |
| --- | --- |
| 随调用提供 | 宿主调用插件时，直接交付约定的当前问题、近期材料和活动信息 |
| 按需查询 | 插件需要补充资料时，读取相关记录、原文或当前状态 |
| 订阅变化 | 有相关变化时，Nexus 向插件提供通知，例如消息已保存、活动结束 |

针对请求前的记忆召回，随调用提供材料是主要方式；需要更多信息时再查询。不因使用自动召回，就要求插件持续监听全部消息。

Nexus 向插件发送变化，与插件向 Nexus 的消息接收入口发送事件，是两个方向，可以共享表达约定，但不能混淆职责。

### 6.2 信息范围

信息可以包含当前活动说明、消息和原始记录、工具结果、运行状态，以及本次请求的条件。具体需要哪些信息，由功能需求和接入声明决定。

既不预设只提供最后一句话，也不默认把整个系统的全部资料传给所有插件。独立服务依赖共同的信息约定，而非 Nexus 内部数据库或页面结构。

读取信息与修改状态分别定义。读取一项工作的状态，不隐含修改或恢复它；收到上下文材料，不隐含改写原始聊天记录。

### 6.3 本次材料与最新状态

提供本次处理的材料快照，即明确“这是截至哪个时刻，供哪次处理使用的材料”。之后到达的新消息，不应悄悄改变原调用正在解决的问题。

按需查询时，需能区分查询本次依据的记录，还是此刻最新状态。具体标识与一致性实现方式未定，不据此要求一套复杂事务系统。

用于召回的是本次已知材料，不是已经包含召回结果的最终请求；先取得补充，再完成装配，避免循环依赖。

### 6.4 明确参与时机

一次活动与一次模型请求分别标识：一项活动可以包含多次模型和工具调用。插件按约定参与请求准备、工具处理或活动完成等具体时机，不能用含糊的“消息发生了”代替这些区别。

变化通知说明发生的是消息已保存、工具已完成还是活动已结束。消息通知、同步参与和异步后续处理有各自含义；需要结果才能继续的处理，必须明确作为依赖。实际提供的时机清单在实施方案中列出。

## 七、前端扩展

### 7.1 插件自带声明，宿主自动装入

Nexus 提供稳定的界面扩展位置。插件随自身交付界面或设置描述，并声明显示位置、所需信息和操作方式，由宿主登记和呈现。

所有者不需要每装一个插件就修改页面结构。具体目录组织和前端加载技术未定。

### 7.2 简单设置与自定义界面并存

- 简单开关、选项和参数，由插件描述，Nexus 自动生成常规设置界面。
- 专门的数据浏览、编辑和复杂交互，由插件提供自定义界面。
- 某次工具结果中的交互内容，可参考 MCP Apps；它不自动替代固定导航、设置与长期管理页面的注册机制。

候选扩展位置包括插件设置区、独立页面、详情栏目和工具结果区域；具体开放哪些位置尚未确定。

### 7.3 界面与运行分开

界面负责展示和接收操作，后台功能通过相应接口运行。页面上的普通搜索或设置保存，不必先请求模型思考。

界面可使用插件服务及宿主共同接口。查看一条资料、修改未来设置、把资料交给灵，是不同动作。

关闭页面不等于停止后台活动；停用插件、停止已有工作和删除数据也分别处理。主题、字号和布局条件可以由宿主共同提供，具体外观约定未定。

### 7.4 交付与生效要求

**使用已有扩展方式安装或更新插件，不需要修改或重新构建 Nexus，允许刷新页面或重启 Nexus 生效。** 插件放入约定位置后，宿主能发现其声明并完成登记；登记不等于自动启用或已经可用。

插件自己的代码与界面可以在交付前构建好。这与要求使用者重新构建 Nexus 是两件事。复杂页面随插件提供独立资源，使用稳定的宿主交互约定；简单设置继续由宿主生成。

不要求运行中无缝热安装、热更新。加载技术由实施方案选择，但必须满足上述使用要求；新增共同扩展类型时，仍允许演进 Nexus 本身。

## 八、生命周期与数据关系

需要区分两类过程：

- **插件生命周期：**添加、配置、启用、可用、停用、更新、移除。
- **一次活动的过程：**收到输入、准备请求、模型返回、工具执行、等待、活动结束等。

前者管理功能，后者决定功能何时参与。具体状态名称和各类插件的行为不在本文中统一锁定。

### 8.1 停用与停止

**停用后立即停止安排新的调用和新的订阅投递，已经开始的一次操作允许收尾，并显示收尾状态。** 收尾以已开始的操作为边界，不能据此让整段长活动继续安排新的插件工作。已经返回的结果可按原用途交付和保存，不再启动该插件的后续处理。

停用发生在请求准备期间时，已开始的插件操作可以结束；尚未开始的调用不再发起。原本必需的能力因此缺失时，按必需能力缺失处理。已发给模型的请求不回改，后续请求和工具调用遵守新的停用状态。

停用本身不终止灵的整个活动。若后续步骤必需使用已停用能力，应说明相关步骤为何暂停。需要立即中止已有工作时，使用单独的停止操作；停止须如实说明结果，不能把中止本地等待当作撤销已经发生的外部行动。

尚未处理的已接收消息保留，因该接入停用而受影响的待处理项标明暂停，不自动丢弃或改投其他对象。未受影响的其他来源继续按各自约定处理。恢复后的投递规则由消息实现明确，已完成处理的内容不因启用而当成新消息重做。

### 8.2 配置与更新

每次调用明确采用的材料、设置和版本。已开始的调用不在途中更换；后续调用采用已生效的新设置。修改涉及重新连接或重启时，应显示待生效状态及需要的操作，不能在界面上宣称已经生效。

更新在已开始的插件操作结束后切换，或通过明确提示后的重启生效；正在进行的操作不混用两个版本。无需为此实现热迁移，长活动的后续调用使用切换后可用的能力。

### 8.3 资源与数据归属

登记这份接入拥有的监听、连接、页面和运行资源；停用后不再接收新工作，允许用于已有操作收尾的资源结束后再释放。关闭页面释放页面资源，不自动停止后台服务。

独立服务可以由插件启动，也可以由外部管理。只处理本次接入拥有的资源，不因停用一份接入就默认终止所有共享服务。

区分宿主记录、插件原始资料、可重建索引和临时缓存。**停用或移除插件默认保留历史与资料，删除数据是明确的单独操作。** 清理运行资源不等于删除资料，也不等于撤销已完成写入。

更换插件或服务时，接口兼容不代表资料和原文引用自动兼容。资料归属、导出迁移方式及引用去向应在对应插件落地时说明，不强制所有数据存入同一数据库。

### 8.4 失败与必要性

**按该能力对当前处理是否必需决定能否继续。** 普通补充资料失败，可以明确提示后继续；活动明确要求取得的资料或某一步必需的能力缺失，则暂停受影响的处理并说明原因。

必要性来自已确认的活动要求及真实依赖。插件描述依赖，Nexus 根据当前活动执行；插件不能任意把自身失败扩大成整个系统停止。

说明哪项能力失败、影响哪些步骤、是否已发送请求或完成行动。失败不能伪装成“没有相关资料”或“已经成功”。具体等待、超时与恢复方式在实施方案中制定，不预设通用重试框架。

### 8.5 查询、行动请求与事件

查询问的是当前情况；行动请求要求执行操作；事件说明某件事已经发生。共同通信可以承载不同内容，但应保留这些含义、来源与所属活动。外部观察不会自动升级成所有者命令，所有者已有的明确安排也不能在转发后丢失。

消息接收、等待投递、进入模型请求、处理结束和实际行动结果分别表达，有需要时通过关联标识追溯。入口返回已接收，只承诺已保存并排队。重启后的待处理项仍应可识别，不把未知的外部执行结果直接判作成功或失败。

消息表达借鉴成熟事件信封的来源、类型、标识、时间和内容关系；是否采用 CloudEvents 的具体字段留给实施方案，不要求另建消息总线，也不由格式推导一次且仅一次执行的保证。

## 九、记忆插件的完整示例

以下示例说明各能力怎样配合，不决定记忆算法、后端选型或自动写入策略：

1. 插件登记主动查询工具、自动召回参与方式、所需宿主信息、设置和管理界面。
2. 灵可主动调用 MCP 工具，查找记忆并展开原文。
3. 每次准备模型请求时，编排器依据约定判断是否需要召回，并提供本次相关材料。
4. 插件结合材料查找候选记忆，必要时经宿主信息接口补充读取。
5. 插件返回相关资料及出处，由编排器放入约定位置并完成请求准备。
6. 用户可通过插件界面浏览和管理记忆；浏览不自动将其送入灵的请求。
7. 若以后包含积累新经历的功能，可另行使用相应处理时机或变化订阅；不与召回混为一件事。

普通查询和召回不要求主动向 Nexus 发送消息。自动召回可以复用 MCP 查询能力，不必为相同的数据读取再建设一套重复协议。

## 十、定稿结论与落地边界

采用 **统一注册与扩展契约、明确参与时机、本次调用范围、资源与数据归属** 组织系统。保留五类可选能力，复用合适的协议与业务实现。宿主管理共同运行关系，插件实现具体功能。

所有者于 2026-10-23 明确确认：

| 决定 | 已确认行为 |
| --- | --- |
| 安装与更新 | 允许刷新或重启，不需要修改或重新构建 Nexus |
| 能力失败 | 按本次是否必需区别处理，说明影响 |
| 停用 | 停止新工作，允许已开始的一次操作收尾，待处理消息保留并标明暂停 |
| 请求查看 | 按需查看材料来源、插件参与与缺失情况，以及实际模型请求内容 |

本次已确定理论结构与上述共同规则。后续落地规划负责确定：

- 注册声明、消息、材料与宿主信息的具体字段、版本和通信方式。
- 实际交付的扩展时机、上下文位置、界面位置及各自输入输出。
- 具体材料排序、容量安排、整理范围与依赖执行算法。
- 插件发现、服务启动、前端资源装入与兼容检查的实现方式。
- 等待超时、停止能力、恢复投递、重复消息识别及重启衔接的具体行为。
- 请求查看的页面入口、保存范围和期限，以及具体插件的数据迁移办法。
- MCP 各项能力及可选扩展的交付范围和验收方法。

这些是依据已确认原则制定的实施事项，不表示存在另一套尚未选择的总体路线。具体方案若涉及改变已确认体验、扩大范围或新增重大产品取舍，再交由所有者确定。当前没有开始代码实现。
