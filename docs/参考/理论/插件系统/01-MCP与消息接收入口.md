# 插件系统理论：MCP 与消息接收入口

日期：2026-10-23。

本文记录本轮讨论中已经形成的基础认识，只涉及 MCP 与消息接收入口的职责和关系。它是后续讨论的依据，不是开发计划、接口规范或已实现能力的说明；具体落地另行确定。后续认识变化时可以修订，长期方向仍以愿景文档为准。

后续讨论已将注册、上下文、宿主信息与前端接入纳入整体理论，见[插件系统理论](02-插件系统理论.md)。整体理论现已定稿，生命周期与已确认使用行为以该文为准。本文继续作为 MCP 与消息接收入口的专项说明；“一出一进”不再代表插件系统的全部组成。

## 一、基本关系：一出一进

插件系统的雏形可以建立在两部分之上：

- **MCP 接入：**让灵发现和使用独立服务提供的能力，并取得结果或资料。
- **消息接收入口：**让外部服务把新情况交给 Nexus，由 Nexus 接收、保存、排队，并安排交给灵处理。

这里的“一出一进”描述的是两种用途，不代表通信只能单向进行。MCP 调用本身也会返回内容。

```text
灵 → 通过 MCP 使用独立服务 → 取得结果
外部服务 → 消息接收入口 → Nexus 保存、排队 → 交给灵处理
```

同一个独立服务可以同时提供 MCP 能力和发送消息，也可以只承担其中一种职责。

## 二、MCP 负责什么

MCP 是 AI 应用与外部服务沟通的共同规则。它约定如何说明服务提供的能力、提出请求，以及返回结果或资料。

一个功能可以作为本地独立服务，通过 MCP 接入 Nexus。独立服务可以自行维护具体功能的规则和所需数据，便于独立调整和替换。MCP 也支持网络服务，但本轮不据此扩大部署范围。

需要区分：

| 概念 | 含义 |
| --- | --- |
| Agent 工具 | 灵能够使用的一项能力，例如查询、计算或保存信息 |
| MCP | Nexus 与外部服务发现、调用和交换内容的协议 |
| 独立服务 | 实际提供功能的程序；MCP 是它可以采用的接入方式 |

MCP 的 Tools（工具）是协议的一部分，但 Agent 工具不必通过 MCP 提供。MCP 除工具外，还能提供资源、提示模板，并通过可选扩展支持其他能力。

支持 MCP 不等于支持它的全部功能。实际能使用什么，取决于 Nexus 与服务双方已经支持的部分。

MCP 不自动决定灵何时思考、怎样理解消息或采取什么行动，也不自动完成插件的安装、更新、启停和设置管理。这些问题不能仅凭“接入 MCP”就视为已经解决。

## 三、消息接收入口负责什么

入口面向外部服务提供通用的收件能力：

1. 接收一条消息及其来源说明。
2. 保存并排队。
3. 返回已经接收的结果。
4. 由 Nexus 的通用运行过程安排后续投递。

入口不解释某个具体功能的业务规则，也不替灵决定应该采取什么行动。外部服务负责说明发生了什么，灵在获得消息及必要资料后判断如何处理。

“已经接收”只表示消息已被收下，不表示灵已经读到、处理完成或执行了某个动作。

具体功能如何判断值得发送哪些消息，由相应服务负责；Nexus 如何把已接收消息交给灵，属于共同的运行能力。

## 四、消息需要共同的表达约定

外部服务发送消息时，需要遵循共同约定，至少能够表达：

- **来源：**这条消息由哪个服务发来。
- **基础消息：**发生了什么，需要灵知道什么。

详细资料可以保留在原服务中，通过引用让灵按需读取，不要求每次把全部内容放进消息。

来源应当在后续处理中保留，使灵能够区分外部观察材料与所有者的要求。外部材料不会仅因进入同一个入口，就自动变成所有者的新指令。

这里尚未固定字段名称、完整格式、版本方式或其他必填项。事件编号、发生时间、事件类型、资料引用等可以在后续确定格式时讨论，不在本文中提前定为接口要求。

## 五、入口不只在灵休息时使用

“唤醒”只是消息到达后的一种处理情况，因此本轮使用更一般的名称：**消息接收入口**。

- 灵没有正在处理的事情时，消息可以触发一次处理。
- 灵正在处理事情时，入口仍然可以收件，消息等待后续交给灵。

外部服务不必先知道灵是否正在思考，再选择另一套发送方式。具体投递时机由 Nexus 的通用运行过程安排。

## 六、到达 Nexus 与进入模型思考是两件事

需要分清三个时刻：

1. Nexus 收到消息。
2. 消息被放进下一次模型请求的材料。
3. 模型依据这份材料进行思考。

对于目前讨论的一轮轮请求模型的方式，已经开始的那次请求，其输入通常不能在途中追加。外部消息到达 Nexus，不等于正在生成中的模型已经看到它。

但消息也不必只能由灵主动查询。应用可以在下一次请求模型前，自动把待处理消息加入材料。这是接收与投递机制需要支持的方向，不代表当前 Nexus 已经实现了这种行为。

同样，MCP 的两类内容需要分别理解：

| 内容 | 怎样进入灵的思考 |
| --- | --- |
| 调用 MCP 工具后返回的结果 | 应用将结果加入后续模型请求，灵继续处理 |
| 外部服务主动发来的新消息或通知 | 应用先接收，再安排进入后续模型请求 |

MCP 的通知或订阅能够帮助应用获知变化，但不会自行把内容插入正在进行的模型请求，也不会自动规定是否启动一次新的思考。

## 七、本轮尚未确定的落地细节

以下事项保留给后续讨论，不作为本文的既定方案：

- 消息入口的具体通信方式与地址。
- 消息格式的完整字段与扩展方式。
- 消息投递、合并、处理结果查询，以及是否允许打断当前处理的具体规则。
- Nexus 对 MCP 各项能力的支持范围。
- 插件安装、启停、更新的具体技术与管理界面；允许刷新或重启但不重建 Nexus、停用后单次操作收尾、保留受影响的待处理项等共同原则已在整体理论中确定。

本文不确定自主性业务、主干与分支的组织方式，或灵的思考过程应部署在哪里，也不据此要求修改现有实现。
