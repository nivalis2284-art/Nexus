# 外部接入、主干分支与记忆块：设计设想

更新：2026-10-23。状态：**讨论稿，未批准实施**。本文记录讨论中形成的四个方向，供后续取舍；不构成当前开发任务，也不改变 `docs/愿景/01-概念与原则.md` 或根目录 `AGENTS.md`。截至本文更新，未安装 QQ 接入方案，未修改自主性相关代码。

当前路线图把下一阶段定为局域网内用手机访问灵，先积累真实使用数据；这四个设想顺延到取得数据、能够对照实际经历再评估时。

## 一句话概括

灵继续生活在 Nexus 中，QQ 等外部服务只是它可以使用的工具；外部事件通过一个统一的唤醒入口交给灵；灵可以由主干和按需运行的分支共同表现；经历被整理成可追溯的记忆块，需要时再展开原文。

四个设想的关系可以表示为：

```text
外部服务（QQ、邮件、网站……）
        │  工具调用：查看、发送、执行
        ▼
      灵在 Nexus 中
        ▲
        │  统一唤醒：外部事件提醒灵
        │
主干（日常交流、整体协调）
        │
        ├─ 分支 A：处理 QQ 对话
        ├─ 分支 B：推进一项工作
        └─ 分支 C：调查一个长期问题
                │
                ▼
        事件记忆块 + 原始记录
```

## 一、QQ MCP：让 QQ 成为工具，而不是另一个灵

### 目标

灵的主体、身份、人设、主体会话和长期状态继续留在 Nexus。QQ 是外部通信渠道，灵可以查看、搜索和发送 QQ 消息，但不因为进入某个群或私聊就变成另一个独立角色，也不把 QQ 当作自己的运行环境。

需要保持的体验：

- 灵知道消息来自哪个联系人、群聊或私聊，以及对方说了什么。
- QQ 上的话是外部材料，不自动变成项目所有者的新指令。
- 灵可以先看消息，再决定回复、暂不回复或稍后处理。
- 灵在 Nexus 中的普通回复不会自动转发到 QQ；向 QQ 发送消息必须是一次明确的工具动作。
- 多个联系人和群聊可以共享同一个灵，但各自保留独立的聊天记录。

### 推荐的结构

```text
QQ 客户端
   ↕
QQ 协议端（NapCat 或 SnowLuma）
   ↕
独立 QQ 工具服务
   ├─ MCP 工具：查看消息、读取聊天、发送消息等
   └─ 新消息提醒：调用 Nexus 的统一唤醒入口
   ↕
Nexus 中的灵
```

QQ 工具服务不需要另配一个模型，也不需要保存另一套灵的人设。它可以同时提供“灵主动调用 QQ”的工具，以及“QQ 有新消息时提醒 Nexus”的通知。

### 一个 MCP 能不能完成

需要区分两件事：

| 目标 | 一个 QQ MCP 是否足够 |
| --- | --- |
| 灵查看消息、读取聊天、发送消息 | 可以，属于 MCP 工具调用 |
| 灵在日常唤醒时顺便检查 QQ | 可以，复用已有唤醒后调用 QQ 工具 |
| QQ 来消息后主动提醒灵 | 可以放在同一个服务里，但还需要连接 Nexus 的唤醒入口 |

MCP 的资源更新通知本身不会让宿主自动运行模型。MCP 解决“灵怎样调用外部工具”；外部事件何时叫醒灵，仍要由 Nexus 接收并安排。

### 候选方案

| 方案 | 特点 | 当前判断 |
| --- | --- | --- |
| **NapCat + 小型 QQ MCP 服务** | OneBot 接口成熟，生态较大；QQ 操作集中在外部服务 | 如果已经使用 NapCat，可以沿用，只需补 MCP 和唤醒转接 |
| **SnowLuma + 官方 MCP** | 官方提供 `@snowluma/mcp`，可查询动作并执行读写；项目仍标注早期开发 | 尚未安装任何方案时值得先评估；仍需确认新消息事件怎样进入 Nexus |
| **QQ 官方机器人 API + MCP** | 官方身份和接口更规范 | 它是独立的机器人身份，不等于操作个人 QQ；主动推送能力受限，暂不作为首选 |
| **直接操作 QQ 窗口** | 接近人工点击界面 | 适合少量特殊操作，不适合作为稳定的消息收发基础 |

本文只记录候选，不替所有者选定 NapCat 或 SnowLuma。第一版只接一种协议端，先把基本读写跑通，不同时维护多套接入。

### 第一版建议的最小工具

- 查看哪些聊天有未读消息。
- 读取指定聊天的一段消息及前后文。
- 查看联系人、群或会话的基本信息。
- 向指定联系人或群发送文本消息。

图片、语音、文件、群管理等能力按实际需要再加。每次工具结果都要能指向原始消息或记录，方便以后核对。

### 尚未确定

- 使用个人 QQ 账号还是官方机器人身份。
- 哪些消息值得提醒灵，哪些只保存不唤醒。
- 灵是否可以对某些会话自动回复，还是每次发送都要明确动作。
- QQ 原始记录的保存位置、保留范围和“忘记”的含义。

## 二、统一唤醒接口：外部服务共用的“提醒灵”入口

### 为什么需要

QQ、邮件、网站监听、日程服务都可能发现值得灵处理的事情。如果每个服务各自实现一套唤醒逻辑，就会重复保存、排队、执行和记录；以后修改灵的运行方式时，还要逐个平台改。

更合适的边界是：

> 外部服务负责发现事情和管理自己的规则；Nexus 负责接收提醒、排队，并让原来的灵处理。

这延续了现有自主性的分工：调度规则留在外部 MCP 服务，Nexus 保留唤醒接收和执行能力。现在需要把已有能力整理成明确、通用的对外约定。

### 现有基础

当前代码已经有可用的底座：

- `/api/automation/wake` 接收带 `reasons` 的请求；
- 请求可以标记来源、唤醒类型、提示文字和是否要求回复；
- Nexus 把请求保存到唤醒队列，轮到它时使用原来的灵会话执行；
- 执行结果和活动记录会保存。

但它目前主要服务于定时与监听，还不是面向其他外部服务的正式接口约定。因此，不能简单宣称“现在任何 MCP 都能主动叫醒灵”。

### 建议的接口职责

统一入口只做很少的事：

1. 接收来源、事件类型、简短说明和相关资料引用。
2. 保存并排队；灵正忙时等待，不丢事件。
3. 轮到处理时，沿用灵的身份、人设、工具和主体会话。
4. 返回“已接收”和请求编号。

它不负责理解 QQ 的群聊结构、网页的差异或日历的规则；这些由各外部服务负责。

### 最小事件格式

不必现在就固定成庞大协议，但应让调用方知道至少填什么：

| 字段 | 作用 |
| --- | --- |
| `source` | 事件来自哪个服务，例如 `qq`、`scheduler` |
| `event_type` | 发生了什么，例如新私聊消息、网页变化、定时到达 |
| `summary` | 一两句话说明为什么值得看 |
| `occurred_at` | 事情发生的时间 |
| `details` | 必要的结构化信息 |
| `references` | 原始记录、会话、任务或消息的定位方式 |
| `notify` | 是否明确要求灵回复；没有要求时可以保持沉默 |

具体字段名可以由实现时统一，不要求现在就锁定。关键是：**简短材料进入唤醒，详细资料留在外部服务。**

### 返回值的含义

“已接收”只表示 Nexus 保存了请求，不表示灵已经处理完。调用方需要区分：

- 已接收、排队中；
- 正在处理；
- 已完成，并附结果；
- 处理失败或等待用户处理。

这样 QQ 服务不会因为一次 HTTP 请求成功，就误以为灵已经回复了对方。

### 需要避免的复杂化

第一版不需要：

- 新的消息中间件或消息总线；
- 新的调度器；
- 每个平台一套执行循环；
- 通用插件注册中心；
- 复杂的优先级和重试体系。

可以复用现有唤醒队列和记录，只补一个对外入口、统一事件说明和少量转接。具体代码要等另一个会话的自主性改动稳定后再整合。

### 尚未确定

- 统一入口是否保留现有路径，还是增加一个更通用的别名。
- 外部服务如何确认某次唤醒已经处理完成。
- 同一来源短时间内大量事件是否合并，以及合并的粒度。
- 哪些事件可以要求“必须回复”，哪些只能作为观察材料。

## 三、主干与分支：灵作为系统状态，而不是唯一 Agent

### 基本想法

不把灵限定为某一个唯一的 Agent 进程，也不要求它模仿人类只有一个意识流。灵可以由以下内容共同表现：

- 预设的人设与自我理解；
- 持续保存的经历和关系；
- 当前正在进行的活动；
- 主干和多个分支的运行过程；
- 这些活动之间可查询的记录和必要的汇合。

这里的“主干”“分支”是工程上的活动组织方式，不声称系统因此具有人类意义上的意识。

### 主干

主干承担：

- 与所有者的日常交流；
- 对当前活动和长期交代的整体协调；
- 接收分支的结果、未完成事项和需要决定的问题；
- 维持灵的身份、语气和当前状态。

主干不必携带所有分支的详细过程，但应当知道自己有哪些分支正在活动，并能查询它们的近况。

### 分支

分支是为一段相对独立的活动建立的执行上下文。它可以：

- 携带灵的身份、必要记忆和这次活动的材料；
- 使用工具、查看外部服务、推进工作；
- 与主干交换必要信息；
- 暂停后保留现场，之后继续；
- 结束时留下结果、承诺、未完成事项和原始记录引用。

分支不必等于一个 QQ 群、一条消息或一个临时子代理。它可以对应一段持续的话题、一项工作或一次调查。一个长会话也可能包含多个事件。

### 分支的生命周期

第一版可以只用少量状态表达：

```text
创建 → 进行中 → 等待（等回复、等条件或等主干决定）
                 ↘ 完成
                 ↘ 失败或取消
```

“等待”不等于结束。需要继续的分支应保留可接续的上下文和原始记录；只有确实结束的活动才整理成简短经历。

### 结果怎样回到主干

建议回传的不只是“已完成”，而是：

- 实际做了什么；
- 是否已经对外产生影响；
- 答应了什么、还在等什么；
- 有没有需要主干决定的分歧；
- 详细记录保存在哪里，怎样继续。

例如：

> 我已向小明说明当前进度，并答应周五提供更新；部署时间尚未确定。后续需要继续这段 QQ 对话，原始记录见对应分支。

这比“我和小明聊过了”更能维持连续性。

分支在外部世界已经发出的消息、已经执行的工具，都是已经发生的事实，不能等主干读完摘要后才生效。主干接收的既有分支的认识，也有分支已经采取的行动，两者要分开记录。

### 分支之间怎样协调

第一版不必让所有分支自由互联。可以保留：

- 主干查询分支状态、读取最近记录、补充要求；
- 分支向主干报告结果或请求决定；
- 必要时由主干把一个分支的结论转给另一个分支。

是否允许分支之间主动打断、互相协商，属于后续产品选择；当前没有足够需求时不必先建一套协商协议。

### 与现有子代理的区别

现有临时子代理适合完成边界清楚的执行任务，例如检查代码、整理资料。它们不一定都是“灵的分支”：

- 临时的文件转换、格式检查可以只是工具或普通子代理；
- 需要携带灵的身份、持续一段时间、产生经历并回到灵的历史中的活动，才更适合作为分支。

这样不会把现有所有子代理都改造成人格分身，也不需要现在就实现完整的多 Agent 平台。

### 上下文与并发

分支提供的是多个活动上下文，不是无限上下文。Nexus 仍需根据模型容量控制每次请求带入的内容；分支自己的工具结果也应支持分段读取。大量历史留在记录中，主干只保留当前协调所需的活动概览。

分支可以并行，但并行的数量应由实际任务和成本决定。第一版优先让少量分支可靠运行，再考虑更大规模。

### 尚未确定

- 分支的最小创建条件：哪些事件自动建立分支，哪些只在主干决定后建立。
- 分支能否主动打断主干，还是只能留言等待主干查看。
- 同时运行多少分支，以及资源不足时怎样排队。
- 分支的“完成”与“长期保留”如何区分。

## 四、记忆块：压缩经历，同时保留可展开的原文

### 基本想法

长期记忆不必是一长串不断增长的文本。可以把一段完整经历整理成多个事件记忆块，每个块保存：

- 标题；
- 时间范围；
- 简短摘要；
- 涉及的人、项目或主题；
- 已经发生的关键行动和承诺；
- 尚未完成的事项；
- 指向原始消息、工具过程或工作记录的引用。

记忆块不是原始记录的替代品。它是帮助灵快速理解过去的索引；需要核对细节时，仍能展开当时的原文。

### 与 Letta 的 Memory Blocks 的区别

Letta 的 Memory Blocks 主要是常驻请求前部的核心资料，例如人格、用户信息和当前项目状态；大量历史资料则放在按需检索的归档记忆中，过去的实际消息可以另外搜索。

本文借用“分块、共享、按需检索”的思路，但把重点放在**经历事件**上：

| 层次 | 内容 | 是否常驻 |
| --- | --- | --- |
| 常驻认识 | 人设、少量长期重要信息、当前活动概览 | 按用途常驻 |
| 事件记忆块 | 一段经历的摘要和原文引用 | 相关时召回 |
| 原始记录 | 当时的消息、工具调用、结果和文件 | 需要时展开或搜索 |

这三层不是三套独立系统，应共用同一套来源标识和引用方式。

### 一个记忆块的例子

> **事件：与小明讨论项目部署**  
> **时间：2026-10-23 晚**  
> **摘要：**小明询问部署进度。我说明修改已完成但尚未实际部署；我答应周五提供更新，没有承诺周五一定上线。  
> **相关：**小明、LingNexus、部署  
> **未完成：**周五向小明更新进展。  
> **原文：**QQ 对话中的相关消息范围，以及关联工作记录。

摘要要保留会影响后续行为的内容，尤其是已经做过的事、答应的事和未定事项。不能只写“聊过了”。

### 召回与展开

第一版至少需要三种操作：

1. **找记忆**：根据当前问题找到相关事件，返回标题、摘要和编号。
2. **展开记忆**：按编号读取对应原文中的相关片段。
3. **搜索原始记录**：跨主干、分支和会话搜索实际消息，再读取附近上下文。

第三种操作很重要。摘要可能没有记录后来才显得重要的细节；如果只能搜记忆块，就会丢掉重新发现过去的机会。原始记录应当可以被直接搜索。

展开应当是读取原文，不是让模型根据摘要重新编故事。摘要已经丢掉的细节，不能可靠地从摘要中恢复。

### 记忆块何时产生

不是所有消息都要变成永久记忆。可以考虑：

- 普通问候、重复通知只保留原始记录；
- 有持续影响的事件、关系变化、承诺、工作结果和重要认识，整理成记忆块；
- 正在进行的活动保留足够现场，不能过早只留摘要；
- 事件记录与后来形成的理解分开保存，避免用新结论覆盖当时发生的事。

记忆块可以由灵在活动结束时主动整理，也可以由一次专门的整理活动生成。第一版不必建立永不停歇的反思循环。

### 与长期记忆、人设和进化的关系

- **人设**回答“现在以怎样的身份和倾向交流”。
- **记忆块**回答“过去发生了什么，哪些值得影响现在”。
- **进化**才负责“经历是否改变人格、价值观和长期行为方式”。

记忆负责取回和引用，不应自动改写预设人设。人格如何生长，仍留给后续阶段讨论。

### 与分支的关系

分支结束时可以留下一个或多个事件记忆块，并把完整过程归档。主干收到的是结果和引用，不必把详细工具过程全部带入。

以后主干或其他分支需要这段经历，都查询同一份记忆块和原始记录，避免各自保存不同版本的摘要。

### 上下文控制

最终发出模型请求的是 Nexus，因此 Nexus 负责根据模型容量控制带入量，而不是让每个外部服务猜测“灵还能装多少”。工具结果应支持分页，记忆检索应先返回少量相关摘要，再按需展开。

能做到的是让灵知道有哪些事情、准确找到资料、分批处理和留下续接信息；不能承诺模型在某一刻同时理解所有历史。

### 尚未确定

- 第一版记忆块由谁创建、何时创建，是否需要所有者确认。
- 记忆块与原始记录的关联方式，以及原始记录移动或删除后的行为。
- 检索优先使用关键词、语义还是混合方式；中文、别称和时间表达需要实际验证。
- “忘记”是停止召回，还是删除原始记录。
- 是否需要把记忆块做成独立服务，还是先使用本地文件和现有数据库。

## 五、四个设想的组合流程

以 QQ 收到一条消息为例：

1. QQ 服务收到消息，保存原始聊天记录。
2. 服务判断这件事值得提醒，向 Nexus 的统一唤醒入口提交简短事件。
3. Nexus 排队，并在合适的时候让灵处理；灵仍使用 Nexus 中的身份和会话。
4. 灵可以建立一个分支处理这段 QQ 对话，主干继续与所有者交流。
5. 分支查看消息、决定回复或暂不回复；需要时调用 QQ 工具发送。
6. 分支结束，留下结果、承诺、未完成事项和原始记录引用。
7. 主干收到结果；需要长期保留的经历整理成事件记忆块。
8. 以后需要回忆时，先找记忆块，再按引用展开原文或直接搜索原始记录。

这条流程中，QQ 是工具，唤醒是入口，分支是活动形式，记忆块是经历的可追溯索引。

## 六、当前不做的部分

- 自动修改人设或让灵自行进化；
- 提交、推送或重启日常实例。

以后开始实现时，应另立当前需求和验收范围，按最小可用闭环推进，不因为本文列出的候选方案就提前引入框架或防御体系。

## 七、需要所有者决定的问题

这些问题会影响第一版范围，暂不替所有者决定：

1. QQ 先使用个人账号协议端，还是官方机器人身份。
2. 第一版是否必须包含“新消息自动唤醒”，还是先只做灵主动查看和发送。
3. 分支由系统自动创建，还是先由灵或所有者明确要求。
4. 哪些 QQ 会话可以提醒灵，哪些只保存不打扰。
5. 记忆块何时生成，是否需要所有者确认后才长期保留。
6. 分支之间是否需要主动通信，还是只通过主干汇合。
7. “忘记”和删除历史的具体含义。
