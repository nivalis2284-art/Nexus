# 任务管理、长期交代与结果反馈

日期：2026-10-22。范围为所有者批准的持续性下一步计划，按任务管理展示、长期交代、结果反馈的顺序整合。

## 使用方式

任务列表展示标题、进展或等待理由、状态和安排。进入任务可继续查看原有对话、过程记录和交互，并按当前状态开始、暂停、恢复或取消；一次性安排可以单独取消。没有进展摘要时直接说明，页面不调用模型补写。

在“长期交代”页面新建、修改内容，或直接对灵说：

> 持续关注这个项目的界面反馈，发现需要处理的问题就调查，准备修改后告诉我。

你与灵使用同一份交代簿；页面标明由用户还是灵创建。灵也可以自主添加交代。相关项目、网站、要求写在正文里即可，不需要额外填一套来源表格。创建来源在之后修改时保留。

页面保存只保存内容，不启动模型。通过聊天提出要求时，灵可结合当次要求立即处理。长期交代不会单独创建定时规则；灵在现有定时、每日规划和监听变化唤醒时考虑活跃交代，决定开展工作、继续已有工作或等待。要特殊时间或监听目标，仍使用现有定时与监听功能。

| 操作 | 交代与具体工作的行为 |
|---|---|
| 暂停交代 | 不继续维护，暂停关联的执行中或排队工作；关联任务的定时恢复暂不启动 |
| 恢复交代 | 重新参与后续唤醒；灵可决定是否恢复此次随交代暂停的工作，不立即批量启动 |
| 结束交代 | 不再开展后续维护；正在执行的工作可以做完，已挂起的工作保持原状态 |
| 单独暂停任务 | 不因交代之后恢复而被灵视为可自动恢复 |
| 一次任务完成 | 保存结果，长期交代仍可保持启用 |

一条交代可以关联多个任务，每个任务至多关联一条交代。旧任务继续可用，不自动猜测它们属于哪条交代。关联任务可从交代页面打开。

## 工作结果如何回来

任务完成、模型主动挂起、真实运行错误或中断、等待回答或批准时，结果进入已有唤醒队列。灵读取任务引用与实际结果后，决定如何回应和处理。它收到挂起结果不代表用户要求恢复该任务。

用户自己暂停、取消任务，或暂停交代引起的批量暂停，只更新记录与页面，不额外唤醒灵重复解释。多个待处理结果可以合并到一次唤醒，沿用用户消息优先的原有顺序。

默认灵可回复，也可把本次经历压成一句话保留。明确要求“完成后告诉我”时，灵应在启动工作时保存完成汇报标记，完成后的唤醒必须实际回复。结果反馈不要求开启定时检查；它是已接受工作的后续处理。

页面通知的已读与结果投递分别记录。首次启用不重新广播旧通知；之后从保存的位置继续处理。定时唤醒、主会话、工具权限和 MCP 连接继续复用。

## 实现边界

- 使用现有任务数据库增加交代和工作关联记录，不改变旧任务历史。
- 网页与聊天工具共用交代服务。模型工具为 `responsibility_list/save/control`；`work_start` 可选传入交代编号与完成汇报标记。
- 任务继续使用原有状态和控制器；网页增加说明，不增加一套任务状态。
- 结果使用现有通知和唤醒队列，只增加投递位置及来源说明。
- 后台任务仍由现有单 Worker 执行；没有增加并行任务引擎、长期记忆平台或新的调度服务。
- 本地服务必须运行才能持续推进。页面关闭不等于服务停止；本轮不切换日常运行实例。

本轮没有增加风险评分、多级审批、强制证据、重试配额或固定思考轮次。实际权限请求继续使用现有处理方式。
