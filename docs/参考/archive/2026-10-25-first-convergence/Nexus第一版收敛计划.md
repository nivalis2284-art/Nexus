# Nexus 第一版收敛计划

更新：2026-10-24。

本文记录本次重新确定的发展方向、基础 Bot 能力调研和接下来工作的顺序。当前先确定范围与方案，不据此立即修改代码、停用日常功能或删除资料。后续具体实施以所有者确认的范围为准。

## 一、已确定的方向

LingNexus 按三个大类别理解：

1. **Nexus：** 模型接入、交流、工具和工作执行的底座，可以借鉴成熟 Bot 的路线，按实际需求微调。
2. **自主／进化：** 主动开展活动，并参与自身能力和运行环境的发展。
3. **人格／自我／记忆：** 承载个体特征、自我理解和长期经历的大类别；既有记忆理论是其中一个子集，仍可独立发展。

**当前第一步是精简、优化和打磨 Nexus，让它收敛到基础 Bot 的及格线。** 现有功能数量已经足够，不继续以增加系统和功能为主要开发方式。

接下来的主要手段是：删除不合适的功能、合并重复机制、简化交互，以及在需求成立时用成熟实现替换薄弱实现。任务系统是优先重新审视的对象，不预设必须沿用现有方案，也不以增加更多任务功能代替替换评估。

本阶段“迁出”的含义是：**从当前 Nexus 完整剔除某项功能，允许它暂时缺席，等待寻找更优解。** 不要求先把旧功能搬成插件，更不要求为了维持功能齐全而继续维护旧实现。剔除功能不等于删除所有者的历史资料、研究成果或实验语料。

已有插件系统保留，继续打磨其实际使用和接入能力；不借本轮收敛扩建插件市场、通用工作流平台等新系统。

旧路线图中的“下一阶段”、历史阶段计划和未完成研究，不自动延续为当前开发任务。最新方向以本次要求为准；长期愿景不变。

## 二、调研结论：这里所说的 Bot 及格线

本次查阅了 Hermes、OpenClaw、Dot 和 Grok Bot 的官方资料。没有在这些资料中发现共同采用的一套“Bot 及格认证”。下面的标准是结合公开产品行为和本项目需求所作的归纳，**不是行业标准，也不是把这些产品的全部能力合并为需求**。

这里的 Bot 指能够接收委派并使用工具完成工作的个人助手。第一版的目标可以表达为：

> 我把一项边界清楚的工作交给 Nexus；它能够自行推进和跟踪工作，在需要时让我补充信息或作出决定，允许我干预，最后交回可核对的结果。

关键闭环是：

**收到任务 → 开始执行 → 跟踪实际进度 → 接收补充或处理阻碍 → 交付结果。**

### 官方案例支持了什么

| 参考 | 已核对的公开行为 | 对本阶段的启发 |
| --- | --- | --- |
| [Hermes：Background Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/cli#background-sessions) | 可以启动独立后台会话，前台继续使用；后台结束后显示结果，失败则显示错误通知。 | 任务应真正执行并交回结果，不能只回复一份计划；实现时要核实后台生命周期，不能把这一功能直接当成跨重启运行保证。 |
| [Hermes：Quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart) | 建议先验证正常交流，再叠加网关、定时、语音或路由等能力。 | 基础闭环优先；成熟产品拥有的其他功能不自动成为第一版前提。 |
| [Dot：Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory) | 工作可以跨交流继续；任务有自己的上下文，也能交给后台 Agent。 | 接受任务之后应能够持续推进；单次任务上下文与长期个体记忆可以分开讨论。 |
| [Dot：Controls](https://learn.chatgpt.com/docs/dots/controls) | 可查看任务进展、文件、结果及等待处理的请求；主体暂停、委派任务停止与取消定时安排含义不同。 | 用户要能看懂工作状态，并明确地干预自己要干预的对象。无需照搬其全部审核制度。 |
| [OpenClaw：Command queue](https://docs.openclaw.ai/concepts/queue) | 对运行中到来的消息明确区分补充、后续排队、合并和中断等处理方式。 | 运行中收到新消息不能含糊；第一版选好符合需求的行为即可，不必实现所有模式。 |
| [Grok Bot：Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration) | 对话中可见工具活动和产物，也能在工作中补充方向或停止；停止不撤销已完成的操作。 | 应当可观察、可纠正、可停止；实际行动和普通文字回复需要区分。 |

公开说明只证明相应产品公开提供这些行为，不证明内部实现相同、所有场景可靠或某个技术方案最优。本次未部署和实测这些参考产品。

## 三、第一版基础能力建议

以下是收敛时的检查标准，不代表每一项都需要新写功能；已有能力符合标准就保留或简化。具体交互与替换方案在后续逐项确定。

| 能力 | 达到及格线时的表现 | 不要求什么 |
| --- | --- | --- |
| 接收工作 | 清楚显示请求是否接收、是否开始；只在确实缺少必要信息时提问。 | 不要求每个任务先走复杂立项或审批流程。 |
| 自主执行 | 在已给定目标、工具和权限内，自己决定下一步并实际行动，不需要用户反复发送“继续”。 | 不要求自己产生长期目标或自行改造宿主。 |
| 后台推进 | 对已接受的后台工作，关闭页面不应直接终止执行；运行环境需要保持在线。 | 不要求电脑关机后仍工作，也不要求云电脑。 |
| 跟踪进度 | 用户能看懂正在做什么、已得到什么、为什么等待；进度来自实际行动和结果。 | 不要求虚构百分比、持续播报或为了更新状态反复调用模型。 |
| 补充和控制 | 工作中能接收补充要求，并有明确的停止和后续继续方式；显示实际状态。 | 不要求撤销已完成的外部操作；排队、暂停和取消不必混成同一动作。 |
| 处理阻碍 | 缺信息、权限或运行失败时说明原因和下一步；需要人处理时明确提出。 | 不要求无限重试、吞掉错误后假装继续，或为假想问题引入整套防御框架。 |
| 交付结果 | 完成后给出成果、位置或可核对的说明，区分已完成、未完成和未验证。 | 不把“模型这一轮说完了”直接当成任务已经完成。 |
| 基本运行记录 | 任务目标、状态、必要输入和结果不因刷新丢失；重启后能说明哪些工作中断及如何继续。 | 不要求恢复旧进程或盲目重放操作；是否自动恢复留待方案确定。 |
| 扩展接入 | 现有 MCP、Skill、插件能按约定接入、使用、查看问题和停用；插件可使用所需上下文、事件、状态及页面入口。 | 不要求本轮增加市场、远程分发或适配所有外部协议。 |

模型、工具、文件和附件、必要上下文容量管理、现有操作权限等属于上述行为的基础。它们不因“删除记忆和持续性”而全部删除；是否保留某个具体实现，以实际用途为准。

任务自主执行不等于零监督或保证所有任务成功。第一版应在选定的真实场景中能够完成闭环，遇到能力边界时如实说明。

## 四、两处必须分清的边界

### 1. 自主完成任务，与自主／进化系统分开

“我交代以后，它自己执行和跟进”属于基础 Bot 的任务能力，本阶段保留并打磨。

“没有当前交代时，它主动寻找事情、形成长期活动并改善自身”属于另一个大系统。本阶段不要求补齐，也不以它作为 Nexus 第一版通过条件。

### 2. 任务接续，与个体持续性分开

执行工作仍需要知道目标是什么、做到了哪里、在等待什么。必要的会话和任务记录应继续存在。

人格、自我理解、长期记忆、主干与分支身份、经历如何构成同一个“灵”等属于个体持续性研究，可以暂时退出 Nexus。保留任务状态不等于保留整套旧持续性业务。

## 五、精简与剔除方向

| 内容 | 当前处理方向 |
| --- | --- |
| 现有人设管理、专门的人设注入及编辑业务 | 可从第一版 Nexus 剔除，等待人格／自我／记忆系统的更优方案；不必先插件化保存旧方案。 |
| 静态长期记忆原型及其默认接管 | 可退出第一版日常底座和验收范围；独立理论、研究与实验资产保留，是否另存为独立项目后续确定。 |
| 以“灵”为特定持续个体绑定的专门业务 | 逐项识别并剔除；原交流入口中的可靠收消息、后台工作和结果反馈等通用能力需要保留或由替换方案承接。 |
| 自由唤醒、每日自我回顾、静默经历、身份延续等专门行为 | 不作为基础 Bot 必需项；与普通任务必要的执行和反馈分开，不为保全旧功能而留下宿主特例。 |
| 长期交代、定时活动及监听 | 区分明确任务的实际需要与旧自主业务；没有当前需要的可以退出，是否保留某项安排能力单独判断。 |
| 插件系统 | 保留并打磨。保留插件框架不代表默认保留、启用所有旧插件。 |
| 模型接入、工具执行、普通交流、任务记录、附件及必要上下文处理 | 按基础 Bot 用途保留、简化或替换，不机械地全部插件化。 |

这是功能范围方向，不是已经执行的删除清单。具体剔除时需要识别混在同一功能中的通用能力，避免把“能交代并完成工作”一起删除；资料保留方式在实际实施前明确。

## 六、接下来要做的事

### 第一步：收敛 Nexus

按以下顺序推进，不预先指定新的框架、任务引擎或存储技术：

1. **确定保留、简化、替换、剔除清单。** 从用户实际使用方式出发，明确每项内容为什么存在；不因旧文档写过、已有代码或已投入成本而默认保留。
2. **优先重新审视任务系统。** 先确定委派、执行、跟进、补充、停止和结果的用户体验，再比较成熟方案。评估部分替换、复用成熟 Agent 执行底座或更大范围替换的实际成本，不默认继续扩建现有任务系统。
3. **选择能够减少自维护负担的方案。** 比较成熟度、与当前模型及工具的适配、Windows 实际可用性、可观察与控制能力、替换后的总复杂度，以及是否能承接现有插件需要。候选产品不等于已选型；不为使用一个框架而引入更多不需要的组件。
4. **剔除已明确退出的业务，并完成必要替换与界面简化。** 用户应能直接理解如何派工作、看进度、补充、停止和拿结果；不把内部机制转化成额外操作负担。
5. **打磨保留的插件系统。** 重点核对加载、停用、重载、工具调用、上下文、事件、状态读取和功能页的真实闭环，处理已证实的问题；旧业务专属例外不自动成为插件公共规则。
6. **用少量代表性任务验收第一版。** 完成实际闭环和必要故障处理检查，不以费时的全量回归或压力测试替代日常体验，也不以单个模拟测试通过宣称所有能力成熟。

这一步完成之前，不将另外两大系统的完整建设混入 Nexus 收敛；也不以“将来有用”为理由补齐所有成熟 Bot 的功能。

### 后续工作

自主／进化系统与人格／自我／记忆系统继续按各自理论发展。具体何时建设、如何接入、采用什么实现，待 Nexus 收敛及真实需求明确后再确定；本文件不提前安排第二步开发任务。

## 七、第一版的代表性验收场景

下列场景是研究建议，实施前选定具体任务、模型、工具和成功条件。它们关注行为结果，不强制保留现有任务页面或内部结构。

| 场景 | 应看到的结果 |
| --- | --- |
| 派发一项可执行工作，例如处理给定文件或完成限定调查 | Nexus 接收后开始做事，自行推进到成果或明确阻碍，而非只给建议和计划。 |
| 一项工作需要等待后台操作 | 能了解操作是否仍在运行，结果出现后接续处理，不需要用户反复提醒。 |
| 执行期间补充要求 | 补充没有丢失，知道何时会被采用；不会无说明地取消原工作或另起重复工作。 |
| 页面关闭后再打开 | 已接受的后台工作状态、必要记录和结果仍可查看。 |
| 缺少关键资料或某个工具真实失败 | 清楚说明等待或失败原因，用户能补充并继续；没有把失败伪装成完成。 |
| 停止或取消工作 | 后续安排按相应语义停止，仍在收尾的操作如实显示，不承诺撤销已发生的效果。 |
| 服务重启 | 已保存的目标、状态和结果仍在；中断工作可识别，后续如何继续清楚，不要求无条件自动恢复。 |
| 一个简单插件参与工作并随后停用 | 工具、材料或页面能正确参与；停用后停止安排新工作，在途处理和资料状态可理解。 |

验收不以任务数量、功能数量或模型自评为依据，也暂不规定统一成功率、延迟或费用指标。先验证真实代表性任务，再据实际问题确定必要指标。

## 八、尚未确定、需要在方案阶段解决的事项

- 第一版主要使用本机网页，还是确有手机／站外联系需求；没有新需求就不自动扩充入口。
- 任务系统采用哪个成熟方案、替换到什么程度；单任务、串行排队或有限并行以实际场景判断，不因未来集群设想直接建设集群平台。
- 现有持续交流入口与普通会话如何精简合并，以及剔除哪些身份绑定行为。
- 哪些旧插件退出默认交付，哪些普通任务安排仍有真实用途。
- 旧功能退出后的代码和资料如何保存。明确保留所有者数据，不在本轮文档工作中进行删除或迁移。

这些问题不影响当前确定“先精简、替换和打磨”的方向，也不意味着要现在逐项增加功能。
