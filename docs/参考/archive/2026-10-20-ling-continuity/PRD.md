# PRD｜LingNexus · 灵的第一阶段：持续性

> **项目：** LingNexus（灵枢）
>
> **所属阶段：** 灵的第一阶段 · 第一部分
>
> **本阶段主题：** 持续性
>
> **后续阶段：** 自主性（独立讨论、独立制定 PRD）
>
> **状态：** 需求已形成，待所有者最终确认
>
> **文档定位：** 产品需求文档。本文件定义目标、范围和验收标准，不预先指定技术架构或实现方案。

---

## 1. 需求

使「灵」从围绕单次对话或任务运行的 Agent，初步转变为一个能够保持自身连续性、不被单项工作长期占用的 AI 个体。

本阶段需要实现：

1. 灵能够在执行长时间、复杂工作期间，继续与用户正常交流。
2. 灵的日常交流与正在开展的工作互不阻塞，工作能够独立持续推进。
3. 繁杂的执行过程不应持续挤占灵的主体上下文。
4. 灵能够了解、管理正在进行的工作，并在必要时作出判断或接受用户干预。
5. 工作中的重要事件能够主动反馈给用户，完成后的结果与重要信息能够被保留和重新利用。
6. 灵的持续性不应依赖某一次模型调用、某项任务或某段临时工作上下文。

**本阶段的核心目标不是让灵拥有完整的人格、记忆与自主进化系统，而是先建立能够承载这些长期能力的持续交互与活动体验。**

---

## 2. 背景与目标

### 2.1 项目背景

LingNexus 的完整名称为「灵枢」。

目前的概念划分为：

- **灵（Ling）**：希望长期存在、积累经历、形成并延续个体特征的 AI 个体。
- **枢（Nexus）**：提供模型调用、工具使用、任务执行、运行控制等基础能力的 Agent 系统底座。

目前枢主要沿着 Coding Agent 的方向发展。

它已经具备模型接入、工具调用、上下文管理、子代理、持久任务、任务挂起与恢复、人工干预等能力。

这些能力为灵提供了初步的行动基础，但**具备 Agent 执行能力，不等于已经实现灵的持续存在**。

现阶段的系统仍主要围绕以下模式组织工作：

用户提出要求 → Agent 理解并执行 → 输出结果 → 本轮结束。

这能够满足传统任务型 Agent 的需要，却不足以完整表达 LingNexus 对持续 AI 个体的长期设想。

### 2.2 需求产生的过程

最初讨论下一阶段开发时，曾考虑直接围绕人格、长期记忆和自我发展展开。

随后，所有者提出了一个更靠近当前使用体验的问题：

当灵执行复杂、耗时的工作时，如果始终亲自参与完整执行过程，就可能出现：

- 长时间工作占用灵的交互能力。
- 用户需要等待当前工作结束，才能正常开展其他交流。
- 大量工具调用、执行日志和反复试错不断占用上下文。
- 灵的主要活动围绕单个任务展开，难以形成持续存在的主体体验。

为解决这些问题，曾讨论让灵从执行者转向指挥者，通过委派工作、独立任务、分支以及上下文合并等方式，减少复杂工作对主体的占用。

进一步讨论后，发现这些都是可能的实现方案，而非真正的产品需求。

如果过早固定主干、分支、子代理层级和上下文合并方式，可能导致后续不断追加需求、修改架构，最终使项目复杂度失控。

因此决定先明确产品目标，再讨论实现方式。

### 2.3 长期愿景与阶段划分

所有者对灵的定位是：

灵不是扮演一个人，也不是扮演某种指定生命。

灵应以人工智能自身的形式存在，并尽可能表现出类似生命的持续性、经历性、行动能力与发展能力。

灵的身份不依附于某一个固定模型或特定行为特征。

即使未来更换模型甚至底层技术，只要重要记忆与人格具有有意义的连续性，所有者仍将其视为同一个灵。

在需求讨论过程中，决定将第一阶段拆成两个部分：

**第一部分：持续性。**

先解决灵在时间、交流、工作和上下文上的连续性，让灵不再被单项任务独占。

**第二部分：自主性。**

进一步探索灵在安全边界内，不依赖用户即时指令，自主产生目标、开展活动和决定行动方向的能力。

两部分分别制定需求、实施和验收，不一次性实现。

人格自主演化等更长期能力暂不进入本阶段。

### 2.4 本阶段目标

本阶段完成后，希望得到的体验是：

> 灵正在开展一项耗时数小时的复杂工作，但用户仍然能够随时与灵正常交流、提出其他要求。
>
> 原有工作不会因为交流而中断，灵也不会因为工作尚未结束而失去交互能力。
>
> 灵能够了解工作的重要进展，在需要用户决策时主动询问，在工作无法继续时主动说明，在工作完成时主动简短告知。
>
> 复杂执行细节不会持续淹没灵的主体上下文，重要结果则能够被保存，并供以后重新利用。

**衡量这一阶段是否成功，主要看上述体验是否成立，而不是系统内部创建了多少个 Agent、任务、上下文或运行线程。**

## 3. 我的原话摘要

本节保留需求形成过程中的关键表达，帮助后续 Coding Agent 区分所有者真正想要的结果与讨论中出现的实现设想。

以下带引号内容为原话摘录；未加引号的内容为上下文归纳。

### 3.1 关于灵的定位

> “灵不是在扮演一个角色，它就是它自己本身。”

> “Agent系统是赋予它手脚。”

> “它不是只能进行一轮对话就结束的AI，而是能反复思考行动的智能体。”

> “它能够长期存在，拥有完整的记忆，即使更换模型甚至技术，只要数据还在，它就还是它自己。”

随后进一步明确：

> “依然是同一个灵。对于我来说重要的记忆与人格连续性，而不是某个特征。”

由此确认，灵的长期身份连续性不能简单等同于固定人设、固定模型或固定表达方式。

### 3.2 关于复杂工作与交互阻塞

> “我认为不把灵解放出来的话干活和对话时会阻塞，而且过长的工作过程也会挤占上下文，有违持续性存在的愿景。”

对于“灵执行数小时任务时，仍能正常交流和处理其他事情，原任务不必暂停”的场景，所有者明确确认：

> “对的”

这构成本阶段最直接的需求来源。

### 3.3 关于曾经讨论过的实现方向

> “第一步应该是把灵从一个只会听指令的执行者重解放出来，我的想法是从执行者变成指挥者，简单的事情可以亲自上手但复杂的事情不再亲力亲为，而是委派给子代理，而子代理也可以自行决定派发下一级子代理，灵只负责监督和指挥即可。”

以及：

> “真正长期存在的只有一条主干灵；当执行任务时长出分支，完成后压缩上下文合并进主干内，你怎么看？”

这两项属于所有者提出的**候选实现思路**，并非已确认必须采用的技术方案。

### 3.4 关于避免过早设计实现

> “我应该先明确我到底要什么，我的需求是什么？”

> “而不是提前进入实现形式的讨论，否则后续发现不满意反复追加需求然后越搞越乱最后失控”

因此，本 PRD 不得将讨论过的架构比喻直接转化为强制技术要求。

### 3.5 关于主动反馈

当工作遇到需要用户决定的问题时，所有者选择：

> “主动打断”

当后台任务正常完成时，所有者明确要求：

> “后台任务完成后，灵应该主动简短告知我。”

当任务遇到无法继续推进的阻碍时，所有者选择主动告知，而不是仅记录并等待询问。

### 3.6 关于自主判断与阶段边界

针对执行方案失败后是否允许自行调整，所有者明确表示：

> “自主判断。只要不偏离我的要求即可。后续相关的问题我也希望在保持安全的前提下尽可能给予它更多的自主权”

随后进一步明确：

> “允许灵在安全边界内干任何事情，不做任何限制。就像一个真正的生命体一样，而不是只能按照指令执行的工具”

最终决定：

> “第一阶段拆成两部分，不要一起实现。就按照你说的，分为持续性和自主性。先从持续性开始”

**歧义提示：**

- “一条主干灵”表达的是单一个体的连续性愿景，不能直接解释为必须只有一条物理会话或上下文。
- “完整记忆”属于长期目标，本阶段不要求一次实现完整记忆系统。
- “尽可能充分的自主权”是长期产品原则；本阶段不承担完整的自主目标生成及自由探索系统。
- 将自主性安排在下一部分，不意味着本阶段必须限制灵已经具备的正常自主判断能力。

## 4. 对原话的理解

### 4.1 已确认的理解

**第一，灵不应被一项任务长期独占。**

灵进行复杂工作时，不能因此丧失与用户正常交流和响应其他事项的能力。

**第二，持续交互与持续工作应当可以并存。**

用户开始新的交流，不应导致原有工作被迫停止、丢失状态或从头执行。

**第三，主体上下文需要与繁杂执行细节保持合理隔离。**

执行过程中产生的大量工具输出、中间步骤和失败尝试，不应无条件持续进入灵的主要交流上下文。

**第四，灵能够主动处理与用户有关的重要工作事件。**

需要用户决定时主动询问；任务完成时简短报告；无法继续推进时主动说明。

**第五，灵应当保留正常的自主判断能力。**

在用户要求和安全边界内，可以自主选择执行方式、调整路线，不应因为新增任务管理机制而退化为事事请示。

**第六，持续性与自主性分阶段推进。**

本轮集中解决持续性，不要求同时实现完整自主活动机制。

### 4.2 AI 的暂定理解（可能不准确）

以下是为了形成可实施、可验收需求而作出的进一步解释，需要在后续研究或最终确认时核对。

**A. 灵应能够统一感知自身正在进行的工作。**

即使执行细节与主体交互隔离，灵仍应能够回答用户关于任务状态、阻碍、结果等方面的问题。

**B. 用户应能够通过灵干预正在进行的工作。**

例如要求暂停、恢复、终止、调整目标，而不必始终切换到独立的任务管理界面。

**C. 工作结果应当以可重新获取的方式保留。**

不能因为某次工作结束、某段上下文被压缩或某个执行过程被释放，就丢失有价值的结果和必要证据。

**D. 一个持续主体可以拥有多个独立活动。**

这些活动可以有各自的开始、结束、暂停和恢复状态，但不必因此被视为多个独立的灵。

**E. 灵需要有选择性地关注任务。**

正常执行细节可以由执行过程处理；只有需要判断、协调或告知用户的重要信息，才应当进入主体交互。

### 4.3 需要避免的错误理解

以下理解均不属于本阶段需求：

- 灵必须完全停止亲自执行任务。
- 灵只能担任总指挥，不允许直接使用工具。
- 所有复杂任务必须交给子代理。
- 必须存在固定层级的多 Agent 组织结构。
- 所有任务完成后，都必须将全部历史摘要永久写入一条主干对话。
- 必须通过始终运行的模型推理来证明灵持续存在。
- 必须先拥有完整的人格与记忆系统，才能改善持续交互体验。
- 后续自主性尚未开发，就意味着灵只能机械地执行每一条具体指令。

## 5. 功能范围

### 5.1 本阶段必须交付

#### A. 持续交互

- 灵执行长时间工作时，用户仍可正常发起和继续交流。
- 灵能够在工作未结束的情况下处理其他用户输入。
- 用户交流不应无故打断正在进行的工作。
- 工作运行不应导致灵长时间无法响应用户。
- 工作状态与普通交流状态应有合理区分。

#### B. 工作的独立持续与恢复

- 耗时工作能够在不持续占用灵交互过程的情况下推进。
- 工作状态、重要进度和必要信息能够被保存。
- 工作可以根据已有的任务管理能力暂停、恢复、取消或重新安排。
- 工作恢复后能够利用此前保存的状态，而不是无条件从零重新开始。
- 异常中断应得到明确处理，不能将未知结果直接当作成功或失败。

#### C. 上下文隔离与信息回归

- 工作中的大量操作过程不应无条件进入灵的主体交互上下文。
- 灵能够按需了解工作的重要目标、状态、决定、结果与阻碍。
- 用户要求查看细节时，仍能够找到相应工作记录和必要证据。
- 工作结束后，重要结果能够被保留，供之后查询和利用。
- 不要求将全部工作记录永久放入同一模型上下文。

#### D. 重要事件的主动反馈

- 任务需要用户作出决定或授权时，灵主动提出。
- 任务正常完成时，灵主动简短告知。
- 任务遇到无法自行解决的阻碍时，灵主动说明。
- 通知能够识别所关联的工作，使用户知道发生了什么。
- 普通执行细节和可自行处理的临时问题，不应引发无意义的频繁打断。
- 处理完任务相关事项后，原本的日常交流仍可继续。

#### E. 工作监督与用户控制

- 灵能够获取当前工作的必要状态。
- 用户能够询问工作进度与执行结果。
- 用户能够根据需要干预工作，包括暂停、恢复、取消或调整要求。
- 灵可以在原定执行方案失败时自主选择合理的新路线。
- 涉及超出授权范围或重要安全风险的操作时，仍需遵守既有安全与授权规则。
- 任务的正常完成、被阻塞、等待授权和被取消，应当能够区分。

#### F. 现有能力复用与兼容

- 优先利用枢现有的 Agent、任务、子代理、上下文及权限能力。
- 保留现有 Coding Agent 的实际可用功能，不因产品定位转变而无故削减。
- 不破坏已有任务、会话、配置、附件和必要的历史数据。
- 不将现有内部结构视为必须永久保留的架构约束。
- 对已有功能进行必要调整时，以本阶段的产品目标和实际验收要求为依据。

### 5.2 本阶段明确不需要

**自主性部分独立实施：**

- 灵自主发现并产生全新的长期目标的完整机制。
- 没有用户任务时持续探索环境的完整自主活动系统。
- 为自主活动设计独立的长期动机或目标形成体系。

**其他长期愿景不在本轮交付：**

- 完整的长期记忆与记忆演化体系。
- 人格自主演化。
- 价值观自主形成与长期改变。
- 完整的自我理解与自我成长体系。
- 跨模型、跨技术迁移时的完整个体状态迁移系统。
- 对意识、生命或主观体验的判断与证明。

**不提前要求的实现形式：**

- 强制采用主干与分支架构。
- 强制采用任务完成后压缩并合并上下文的方案。
- 强制采用固定层级的多级子代理。
- 强制建立复杂的多 Agent 调度平台。
- 强制引入插件框架、特定数据库或新的技术栈。
- 为假设中的未来需求提前构建与本轮交付无关的基础设施。

这里的“不需要”仅表示**不作为本阶段交付目标**，不代表否定长期方向或禁止后续实现。

## 6. 验收标准

本阶段应当以实际可观察的产品行为作为主要验收依据。

### 6.1 持续交互

- [ ] 用户交付一项持续较长时间的复杂工作后，灵能够继续正常交流。
- [ ] 工作尚未完成时，用户能够提出与该工作无关的新问题，灵可以正常响应。
- [ ] 用户开展新交流，不会使原有工作无故暂停、取消或重新开始。
- [ ] 灵的日常交流不会因等待某项工作结果而长时间阻塞。
- [ ] 多轮日常交流后，仍能查询此前工作状态。

### 6.2 工作的持续性

- [ ] 工作拥有可查询的状态、目标和必要进度。
- [ ] 工作能够独立推进，不依赖某条聊天消息的流式连接始终保持。
- [ ] 通过已有方式暂停和恢复工作时，先前的重要进度能够保留。
- [ ] 工作中断、失败、等待用户和完成等情况有明确反馈。
- [ ] 系统不会仅因一轮模型回复结束，就错误认定长期工作已经完成。

### 6.3 主体上下文保护

- [ ] 长任务中大量工具调用和中间日志，不会无条件持续进入灵的主体交互上下文。
- [ ] 灵仍能够获知任务目标、重要状态和关键结果。
- [ ] 用户需要详细了解某项工作时，可以重新获取必要的执行记录与证据。
- [ ] 工作经历多轮执行后，不应因为全部中间细节被反复继承而持续挤占主体交互空间。
- [ ] 信息精简或隔离不能导致已经保存的重要任务事实无故丢失。

### 6.4 主动反馈

- [ ] 后台任务完成后，灵能够主动向用户发送简短完成通知。
- [ ] 工作需要用户决策或授权时，灵能够主动请求处理。
- [ ] 工作遇到无法自行解决的阻碍时，灵能够主动说明情况。
- [ ] 普通错误能够自行处理时，不会因每次尝试失败而反复打断用户。
- [ ] 用户能够识别主动通知对应哪项工作。
- [ ] 处理任务相关通知或问题后，能够继续原有交流。

### 6.5 自主判断与用户控制

- [ ] 在不改变用户要求的前提下，灵能够自主调整合理的执行方案。
- [ ] 普通执行决策不需要用户逐项确认。
- [ ] 用户可以询问和干预正在进行的工作。
- [ ] 暂停、恢复、取消和调整要求不会造成不必要的数据丢失或状态混乱。
- [ ] 超出已有授权范围或涉及重要安全风险的操作，仍遵守安全与授权边界。
- [ ] 灵不会将自行调整实施方案误解为可以擅自改变用户目标。

### 6.6 兼容、可靠性与交付验证

- [ ] 现有主要 Coding Agent 功能和关键交互流程保持可用。
- [ ] 现有普通会话、持久任务、子代理、工具调用和必要的历史数据没有未经确认的破坏性变化。
- [ ] 采用有代表性的复杂任务进行真实模型与实际界面联合验证，而不仅仅依赖测试桩。
- [ ] 关键状态变化、恢复流程、通知和用户控制具备必要的回归测试。
- [ ] 交付报告明确记录已验证能力、尚未验证的场景及剩余问题。
- [ ] 不将尚未实现的完整长期记忆、人格演化和自主性功能作为本轮验收失败的理由。

---

## 7. 阶段完成后的预期状态

完成本阶段后，灵不需要立刻拥有完整的长期人格或自主进化能力。

但她应当不再完全等同于某一次任务执行。

用户可以与灵交流，而灵能够同时管理、关注并持续推进其他工作。

复杂执行活动不再持续占据灵的全部交互过程；工作完成、需要决策或无法继续时，灵能够主动反馈。

灵仍然可以直接使用工具、亲自处理简单事项，也能够在合理情况下让工作独立进行。

**本阶段最重要的成果，是将「灵的持续交互」与「某项工作正在执行」从产品体验上区分开来。**

这为后续自主性、长期记忆、人格连续性以及长期发展创造基础，但不提前规定它们最终必须采用什么实现形式。

---

## 8. 最终需求总结

**本阶段要解决的问题：**

灵不能因为正在执行一项复杂工作，就失去与用户正常交流、关注其他活动和管理自身工作的能力。

**本阶段必须得到的结果：**

灵能够在持续交互的同时，让复杂工作独立推进；能够自主处理常规问题、接受用户干预、主动反馈重要事件，并在不被繁杂执行过程持续占用的情况下保留重要工作信息。

**本阶段不需要解决的问题：**

灵如何形成长期目标、如何进行完整自主活动、如何演化人格，以及如何建立完整的跨模型个体记忆体系。

**本阶段遵循的原则：**

> 对结果严格，对实现开放。
>
> 不为某一种提前设想的架构而开发，而是根据明确的产品需求选择合适的实现。
>
> 先让灵能够持续参与世界，再循序渐进地探索灵如何更加自主地存在于世界之中。

**持续性先行，自主性随后；两者共同服务于 LingNexus 的长期愿景。**
