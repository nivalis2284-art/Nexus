# PRD｜LingNexus 自主性雏形：方案 A 深化与可替换能力补充

> **状态：** 草案，待所有者确认；本次已明确的方向不等于架构细节已被批准。
> **定位：** 与 [当前自主性主 PRD](PRD.md) **并存**的补充需求，不覆盖、不替代主 PRD。主 PRD 约束第一版最终自主体验；本文明确新方向、补充交付要求和阶段 4A 的深入研究问题。发生冲突时，优先复核用户最新明确意思，不凭本文擅自修改最高愿景。
> **关联：** [现阶段研究](RESEARCH.md)（方案 A/B）、[产品定位](PRODUCT.md)、[路线图](ROADMAP.md)、[最高愿景](../../../愿景/01-概念与原则.md)、[抽象需求](../../../愿景/02-具象理想.md)。旧预研保留在 [archive/2026-10-20-autonomy-prestudy/](../2026-10-20-autonomy-prestudy/)。
> **后续工作流：** Coding Agent 先进行阶段 4A **深化研究与架构取舍**；用户确认关键取舍后进入 4B 内置计划，再正式开发。此补充 PRD 不授权提前改业务代码或开展付费实验。

## 1. 需求

**以原研究的方案 A 为当前优先方向，将“有界自主审议＋跨次状态与真实反馈＋一个灵主 Agent”的方向深化为足以供正式实现规划的可落地候选，同时保证关键技术能力未来可以替换。**

在主 PRD 的“自主联系”和“经历产生目标并因结果改变后续行为”两条验收闭环之外，进一步明确：

- **三种思考机会共存：** 时间保底触发、真实变化触发、灵自主规划未来思考机会。触发只是一次重新考虑的机会，不强制启动工作或发送消息。
- **自主观察变化：** 研究灵是否可自行创建、修改、暂停和终止监听；客观变化如何被检测、解释并关联原目标；什么变化值得唤起灵重新思考；包括 Jev 辅助筛选的可行性和漏判风险。
- **实现方式与替换边界：** 深化方案 A 的各项实际接入问题，区分 Nexus 必须持有的长期保障和可由 MCP、Skill、Agent 工具或未来技术替换的能力；在不提前建设完整插件系统的前提下，为真实有价值的替换保留位置。

## 2. 背景与目标

上一轮 [4A 研究](RESEARCH.md) 推荐方案 A：唯一灵主 Agent 在独立、有界的内部审议中回顾真实经历，自主形成候选目标、取舍行动/等待/放弃，调用现有持久任务取得证据，并在有理由时正式联系所有者。所有者**倾向方案 A**，认为深入理解过去经历的高级记忆能力可以留待后续独立的记忆阶段，但本版不能因此丧失目标来源、结果和判断的最低连续性。

随后补充了三源触发设想：固定保底避免长期沉寂；变化触发保证灵活反应；灵可在一天中的某个时段，自主考虑未来一段时间何时需要再次思考、观察或检查结果，可修改安排，也可选择不安排额外活动。

对于变化触发，所有者进一步提出：灵通过 Agent 工具或 MCP 自行管理监听规则或脚本，外部状态变化后可先由 Jev 判断是否值得唤醒主 Agent。又提出监听能力可优先独立成 MCP 服务，避免将各种外部数据源的具体实现塞进 Nexus 核心；MCP、Skill、Agent 工具是当前可考虑的扩展手段。

最后，所有者重新强调最高愿景的**长期演进与未来替换权**：当前技术不是永恒架构，未来更好的模型、记忆、决策、监听或 Agent 技术出现时，应该尽可能替换局部实现而不重构整个平台，更不能丢失属于灵的重要经历与目标。参考本地部署的 DSH（DeepSeek Harness）插件架构和外部成熟案例，但不要求完全照搬。

**本补充阶段的目标是为正式落地选型与 4B 规划做好充分准备，而非无限期泛研究或提前实现通用插件平台。**

## 3. 我的原话摘要

以下忠实概括本轮所有者的表达，保留“倾向、或许、可不可行”等不确定性，不将建议伪装成已确认技术要求：

- “我倾向于方案A”，而如何正确重新理解经历的问题，“可以在后续的记忆系统一起解决”。
- 希望第三种触发：灵可以在一天某个时间段自己规划未来一天的时间，决定何时触发；**时间保底、变化触发、自主规划可以共存**，分别保证不断档、及时性和更多自主性。
- 变化需要定义；提出由灵自行创建监听脚本或规则，发现事件变化后先由 Jev 判断重要性，高于某个阈值再触发的**候选想法**，并非 Jev 或固定阈值已被证明可靠。
- 进一步设想把监听做成独立 MCP，允许灵修改监听规则，未来按需扩展其他观察方式。
- 认为自主性大部分能力也许能成为可替换插件，Nexus 不应承担太多具体技术；希望参考 MCP＋Skill＋Agent 工具，以及本地 DSH 插件化结构。
- 最新要求是**额外创建一份补充 PRD，与既有 PRD 并存**；补充的核心是方案 A 的方向确认、第三种触发、监听触发可行性、A 到底怎样实现、插件化准备与非核心能力外置的取舍；参考本地 DSH 和外部资料，不预设 DSH 最优。

**尚未明确指定：** 自主规划的固定时段与时间粒度、监听规则/脚本形式、MCP 推送或轮询方式、Jev 是否采用及其阈值、哪些状态和机制归 Nexus、插件统一规范、外部插件运行边界、具体接口设计。不得将这些填成所有者已批准要求。

## 4. 对原话的理解

**已确认的方向**

- 当前以 **方案 A** 为优先深化对象，保持一个灵主 Agent 和主 PRD 的最终用户体验，不再把 Flash 常驻自由联想作为此版前提；Jev 是可选候选。
- 三种触发机会在产品层面**应能协同共存**。其中自主规划是灵自主决定何时值得再考虑，不等于到点必思考、必执行或必联系；遇到新证据、用户撤回和状态变化，旧安排应能被合理修订。
- 当前阶段优先证明行为真实有效、逻辑连贯、最终体验达标，而非追求最低调用费用或堆叠模型数量。
- 长期重要经历、正式消息、决策依据和用户控制不能因为更换某个辅助能力而失去归属。

**AI 的暂定理解（必须交由 Coding Agent 调查和比较）**

- MCP 可能适合外部监听来源、规则管理及获取变化事件；内部已有任务结果、暂停和撤回等未必需要绕行 MCP。**MCP 只是接入协议，不自动具备长期监听、推送、可靠存储或独立安全边界。**
- 规则型监听可能比任意自生成脚本更适合第一版；但应由工程研究比较在真实观察目标下的适用性，不得作为未经验证的技术禁令。
- “Jev 高于某个分数就唤醒”是可比较假设，而非已经校准的可靠概率。重要确定性事件是否绕开模型，低置信事件如何复核、被过滤的事件如何追溯，需研究实证。
- 可替换的关键不仅是卸载/安装，还包括状态归属、可迁移数据、版本兼容及替换失败时的恢复；但不能因未来不确定性，提前建设复杂的万能插件框架。

**尚待确认的方案取舍**

- 哪些能力可以直接用已有 MCP/Skill/Agent 工具实现，哪些必须有独立后台服务或 Nexus 的小型稳定边界？
- 能否实现监听状态持续存在、真实变化进入统一自主审议入口、触发冲突去重、暂停后不重新启动、替换监听实现时保留关注事项？
- 若 DSH 的插件树、服务/事件、可撤销注册与替换机制适用，应吸收哪些原则？采用完整 Cordis 或其他宿主体系是否反而超出当前需求？

## 5. 功能范围

**本补充对第一版最终交付提出的增量要求**

1. **自主规划触发：** 灵可以根据当前关注与经历安排未来一段时间的回顾或检查机会，允许留空、延后、修改和取消；时间保底、变化触发、自主规划触发可同时存在，但对同一事项不应造成重复自主任务或反复主动消息。
2. **有来源的变化响应：** 重要的外部或内部变化能够关联到原关注事项并触发重新考虑；变化的原始依据、重复/过期和判断结果应可核查。哪些事件需要主 Agent 复核、哪些无需、哪些应保持沉默，不由一条未经验证的分数线武断决定。
3. **自主可管理的观察能力：** 在明确许可的对象、工具和资源范围内，灵能按自身目标管理至少一种实际可工作的监听/观察方式，接收真实变化，并能按新认识修改或撤销关注；**不要求第一版支持任意网站、任意脚本或全部外部服务**。
4. **替换准备：** 尽可能让监听、筛选、规划策略或其他非必要专用机制通过可替换能力实现；如果某个能力替换、停用或失效，已有正式消息、重要目标、来源和用户暂停/撤回状态不能无声丢失或被越权恢复。
5. **深入可实施性：** 方案 A 进入正式计划前，需要明确真实运行入口、内外部事件与三源触发如何协调、唯一主 Agent 的审议与正常聊天怎样互不干扰、关注状态如何跨次保存、成果如何反馈、消息如何正式交付、权限与恢复如何一致。实现细节应在 4A 比较后由 4B 决定。

**本轮 4A 深化研究必须交付（不是软件已经实现的证明）**

- 阅读主 PRD、现有 4A RESEARCH、愿景及实际 Nexus 源码；检查**用户本地部署的 DSH**（先定位版本与源码/配置，无法访问时如实说明，并使用可核实的 DSH 官方公开资料作为补充），以及其他至少一种有价值的插件/运行能力架构。
- 给出**至少一个完整、可执行的方案 A 实现候选**，说清楚用户最终看到什么、各项能力由谁承担、现有 Nexus 实际可复用什么、必须新增什么、哪些可以替换、替换后的状态如何保留；有竞争方案时比较取舍，只有一项可行也要解释其理由。
- 单独分析三源触发、监听事件“什么叫变化/什么值得触发”、规则/脚本/MCP 取舍、Jev 的必要性与漏判风险，形成可以被真实工程验证或否定的判断，而不是只画抽象架构图。
- 研究 DSH 及外部架构的真实机制和局限：插件装配/卸载、能力与服务边界、状态归属、运行生命周期、故障隔离与扩展接口；**既不默认照搬 DSH，也不因为当前 Nexus 能写在内部就拒绝外置**。指出现在值得投入的最小扩展边界与暂不实现的未来机制。
- 形成单独的补充研究文档，例如 `docs/RESEARCH-AUTONOMY-ARCHITECTURE.md`，明确推荐选型、替代方案及其缺点、开放问题、可验收的最小纵向样例和 4B 规划前需要所有者确认的产品分歧。与原 `docs/RESEARCH.md` 并存，不覆盖旧结论；如需修改核心产品范围，应先向所有者提出而不是擅改主 PRD。

**本轮明确不做**

- 不直接开发自主性或监听 MCP，不重构 Nexus，不引入完整插件框架/市场/热插拔系统，不因“未来或许用得上”而建设复杂兼容层。
- 不预先规定 Cordis、DSH、某种插件 SDK、MCP 传输、Jev、具体阈值或运行语言是必选项；不要求所有功能都必须拆成独立进程或以 MCP 实现。
- 不把高级记忆系统、完整人格演化、持续推理模型或其他远期能力作为第一版前置条件；当前闭环仍须可靠保留最小真实经历与来源。
- 不改动受保护愿景文件，不覆盖原 PRD、原 4A RESEARCH 或归档材料；无明确许可不开展付费实验或业务编码。

## 6. 验收标准

- [ ] **文档并存：** `docs/PRD.md` 及当前 `docs/RESEARCH.md` 完整保留；补充 PRD 有独立路径，后续补充研究也使用独立文档。
- [ ] **方向与体验明确：** 说明如何维持主 PRD 两条自主行为闭环，并加入三源触发；给出至少一个能体现灵**自主安排未来考虑机会**且能因真实变化调整的用户场景。
- [ ] **监听闭环可核查：** 提供至少一条从灵自主选定观察目标、建立监听、检测真实变化、判断是否审议、更新目标/监听的完整路径；区分已验证事实、技术推导及仍需实验。
- [ ] **判断机制有取舍：** 对普通变化、重要变化、无法判断及不应交给模型过滤的确定性控制事件给出可测试处理方式；不把 Jev 数值评分视作天然可靠的概率。
- [ ] **可替换性有边界：** 对拟保留 Nexus 内部及拟外置的各能力解释原因、替代/停用影响、重要资料所有权与最低迁移路径；至少通过设计审查说明替换某个监听实现时重要目标和用户撤回状态如何保持。
- [ ] **参考研究可信：** 分别标明本地 DSH 实测/源码事实、官方公开项目资料、其他参考方案、推测与未验证结论；不能把 DSH “一切都是插件”的口号直接当成适配 Nexus 的证据。
- [ ] **可进入正式规划：** 至少有一个面向当前代码、工程代价和真实验收的推荐实现候选，关键风险与备选退路已明确，足以支撑后续 4B 而非继续漫无目的研究。
- [ ] **严格阶段边界：** 本次只确认补充需求、开展后续 4A 研究与方案比较；研究报告完成不等于功能实现或获准开发，最终用户体验仍依据主 PRD 及本补充 PRD 独立验收。

**本补充 PRD 的价值是让 Astra 有明确的成果责任与架构探索空间：约束最终应实现的自主体验、可替换边界及必须解释的取舍，而不提前替它写实施计划。**
