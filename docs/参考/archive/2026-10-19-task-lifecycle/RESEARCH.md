# Nexus 任务生命周期、失败止损与持续恢复：需求复核及技术研究

研究日期：2026-10-19（Asia/Tokyo）。源码基线：`0ae52e0af9a2ce8f8bb49504ac00df660f084db6`；其中业务代码仍为 `9414586` 交付版本。需求：[PRD.md](PRD.md)。方向背景：[EXECUTION-RESEARCH.md](EXECUTION-RESEARCH.md)。

**状态：阶段四 A 研究成果，未正式开发，未制定详细实施计划。** 本文中的方案是技术建议；本轮实测仅覆盖现有代码与隔离技术探针，不表示新需求已实现或通过验收。

## 1. 结论与需求纠偏

**推荐方向：保留现有 Agent/工具/网页技术基础，增加真正持久的任务对象、服务内单执行通道、可核对的任务工作状态和操作证据；按钮、自然语言、定时触发统一进入同一任务控制。** ①任务状态、②失败止损、④持久挂起/恢复与延后执行必须联动，不能以“先做一个任务列表”代替三项交付。

存储方面，当前更倾向于**标准库 SQLite 承载新增任务的状态、关键事件、待处理交互和安排**，保留既有 JSONL 对话读取。理由是本轮已经有明确的多对象一致更新、定时触发认领及重启恢复需求；不是为了性能或未来规模预先上数据库。应保证新任务只有一个权威状态来源，不能在 JSONL、任务快照和 UI 中各维护一份可独立修改的进度。

调度方面，当前只有**每任务一次性延后执行**的明确需求。推荐从服务内到期检查与串行派发满足需求，比较后暂不引入通用工作流引擎或完整调度框架。无论采用何种库，任务开始/恢复的资格、权限、用户挂起和到期安排都必须在同一控制边界复核。

### 1.1 与上一轮研究的关系

- 之前的开放方向预研没有确定开发目标；这份新 PRD 已明确选定①②④，跨任务经验学习与多 Agent 扩展暂缓，不能继续把它们列为本轮候选范围。
- “长期保留”指应用重启后任务对象和进度仍在，不要求后台永远在线，不要求恢复任意外部进程或隐藏思考。
- “无需重新探索现场”应理解为**继承已确认的目标、决定、证据和下一步，只核查相关变化与未知结果**；不能解释为永久信任已经变化的文件、工具状态或权限。
- “完成”需要有目标层面的依据；没有通用裁判能证明任意开放任务成功。不确定或主观部分应说明边界并支持用户纠正，不以所有步骤勾选、工具 ok 或模型回复替代验证。
- 任务可以预先创建而不发起工作；普通问答仍可保持现有聊天入口，不强制所有消息创建详细任务计划。

### 1.3 本会话已经确认的产品边界

下列“已确认”来自用户本轮直接回答，优先于技术推荐和参考项目默认行为：

| 边界 | 已确认行为 | 含义 |
|---|---|---|
| 默认安排 | 无限期保留，用户手动开始/恢复 | 没有明确安排的任务不因启动或其他任务到期而执行 |
| 错过时间 | Nexus 关闭期间错过计划时间，下次启动进入等待用户确认 | 不自动补执行，不静默丢弃 |
| 多任务到期 | 串行排队，不打断当前任务；按计划时间、同时间按创建顺序排列 | 多任务持有不是多 Agent 并行；等待任务要能看到排队原因 |
| 自动触发运行条件 | Nexus 服务运行即可触发，网页关闭也可执行 | 页面连接不再是任务执行生命周期；不增加系统常驻、自启或唤醒 |
| 人工交互 | 自动运行遇到现有权限确认或提问，转为等待用户处理，保留原授权规则 | “允许到时启动”不是“允许所有工具”；用户尚未回答不得继续相关动作 |
| 新任务挂起与后台命令 | 挂起时停止该任务的后台命令，保留已收集输出 | 恢复逻辑任务，不恢复旧进程；不回滚已生效操作。普通聊天原有停止语义可保持 |
| 既有后台任务退出语义 | 服务退出时结束，不跨重启恢复进程 | 新任务恢复不推翻这一边界 |
| 重启时已排队未开始 | 已确认转为等待用户确认，保留安排与排队原因 | 不把未启动队列误认为运行中断；不自动补跑 |
| 等待审批/提问时后台命令 | 已确认允许其完成，期间保留执行容量；显示仍在运行的命令 | 与手动挂起时停止后台命令不同；不得说成完全空闲 |

“取消/删除/归档”、时区表示、具体任务和会话的关联方式等尚有局部语义需要细化，见第 9 节；当前已足够开展后续方案讨论，但不能把其中建议写成用户已确认。

## 2. 当前项目现状与实际差距

### 2.1 现有链路

```text
网页 app.js → POST /api/chat → 全局 BUSY 锁
  → Handler._run_turn 装配 Agent、权限、Skill、MCP、会话 JobRegistry
  → 模型流 → 串行工具 → 结果回灌 → 再请求模型
  → NDJSON 直接写本次 HTTP 连接
  → finally 保存本轮消息至 sessions/*.jsonl

停止：设置当前 run 的 Event，唤醒内存审批等待
断开连接：停止当前 Agent
退出服务：设置停止、清理会话后台进程、关闭 MCP
```

当前没有独立的任务对象、持久安排、持久人工等待或任务恢复入口。已有全局单运行约束可以复用为容量边界，但不能只把其全局变量改个名字就获得任务生命周期。

### 2.2 源码事实与 PRD 的对应关系

以下为当前源码事实；测试或本轮探针支持的部分另作注明。

| PRD 结果 | 可复用基础 | 实际差距与位置 |
|---|---|---|
| 提前创建任务、多个任务独立保留 | JSONL 会话有独立 ID，可创建空会话 | [SessionStore](../../../../nexus/session/store.py) 只有会话/消息，没有目标、任务状态、安排和工作上下文；空会话不是待执行任务 |
| 进度与证据参与后续执行 | [Agent.run](../../../../nexus/core/agent.py) 回灌工具结果；[todo.write](../../../../nexus/tools/todo.py) 可写步骤列表 | [ToolContext](../../../../nexus/tools/__init__.py) 每次 build 的 todos 为空，网页每轮重建；没有权威任务进度或其恢复。完成/验证仍由对话解释 |
| 可信完成状态 | 工具 `ok/error`、每轮结束原因、测试工具都可用 | 无 tool call 就返回 `complete`；子代理 `max_steps` 仍可能映射为工具 ok。它们都不是任务整体完成的证明 |
| 失败止损 | [retry](../../../../nexus/core/retry.py) 有请求级有限退避；提示规则要求失败后调整 | 没有任务内的尝试原因、相关前提、排除路线或持久停滞判定。接口错误与任务策略错误不能直接共用重试计数 |
| 挂起/继续 | 停止 Event、前台命令取消、子代理共享取消已有集成覆盖 | [server._abort](../../../../nexus/web/server.py) 只影响当前 run，无挂起对象；不是按目标任务 ID 控制，也没有恢复按钮/自然语言状态命令 |
| 关闭网页仍可定时执行 | 服务是独立 Python 进程，HTTP 服务本身可无浏览器运行 | `_run_turn` 的 emit 直接写请求连接；断连停止 Agent。当前不是可后台驱动并可重新订阅的任务运行器 |
| 跨重启直接继续 | JSONL 原始历史保留；[compaction](../../../../nexus/core/compaction.py) 已有结构化摘要与工具配对 | 摘要仅在当前 run 使用，未保存为可复用任务 checkpoint；重开仍从历史组装，没有明确下一步/未知操作清单 |
| 意外中断后核查副作用 | 文件工具的 hash、调用 ID、结构化错误和取消检查可复用 | 本轮记录直到 `_run_turn` 的 finally 才落盘；`close_pending_calls` 用 interrupted 修复协议配对，没有可靠的已派发/未派发业务状态区分 |
| 持久人工等待 | Approvals 有令牌与唤醒、权限规则已有实现 | 等待是进程内 Event，最长 600 秒，回答/断连/停止后清除；不能持久保存待审批动作或跨重启回答 |
| 按任务正确环境恢复 | Workspace、Skill、MCP 配置已有 | 工作目录、模型选择、活动 MCP 连接主要是全局配置；恢复 A 不能误用用户正在浏览 B 时的全局目录/模型 |
| 自然语言控制，运行中可挂起 | ask_user、聊天框和现有 HTTP 控制端点 | [app.js::send](../../../../nexus/web/app.js) 在 `state.running` 时直接返回；把生命周期操作只做成普通模型工具，无法覆盖运行中自然语言停止 |
| 挂起停止任务后台命令 | [JobRegistry](../../../../nexus/tools/_jobs.py) 已能清理进程树并保留运行期输出 | 当前注册表按会话保留；普通 Agent 停止不会杀后台 job；`close_all` 关闭后不能再接收任务，恢复需新活动资源与旧输出记录分开 |
| 一次性安排及修改/取消 | 标准库有时钟、线程和 SQLite，无新外部服务必要 | 当前无调度器/安排存储。手动、定时和取消之间需要一致派发，不能各自启动一份 Agent |

|---|---|---|

| SQLite 环境 | 标准库可用，SQLite **3.53.1**，`threadsafety=3` | 新增本地事务存储不需要外部数据库服务；连接使用规则仍要遵守 |
| 临时数据库，子进程写事务未 commit 就 `os._exit(17)` | 重开值仍为原值 0 | 该本地条件下未提交事务回滚；不是系统断电或任务恢复验收 |
| 两个线程各持连接，对同一未认领记录做条件写 | 两次影响行数为 `[0,1]` | 事务和条件更新可用于竞争认领；不是完整调度器的幂等性证明 |

SQLite 探针首次把连接 context manager 误当成关闭连接，触发 Windows 临时文件占用；依据官方说明改为显式关闭后重测通过，前次临时文件也已清理。这是探针资源管理问题，不是 Nexus 业务缺陷。官方明确说明 `with connection` 不关闭连接。[Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html#how-to-use-the-connection-context-manager)

## 3. 语义模型：需要保存什么，不能混为什么

本节是推荐的概念边界，不是数据库表结构或状态枚举的最终设计。

### 3.1 区分任务、一次运行、步骤与操作结果

| 概念 | 负责回答 | 不应承载 |
|---|---|---|
| 任务 | 用户目标与约束是什么；当前整体进度、剩余工作与继续条件是什么 | 一次 HTTP 请求是否还在线 |
| 一次运行 | 为什么开始、执行到哪里、为什么结束/等待、用了什么配置 | 用户目标是否必然已达成 |
| 步骤/里程碑 | 哪部分未做、尝试过、有产物、已验证或受阻 | 全部原始工具输出 |
| 操作及观察 | 哪个工具实际可能执行了什么，结果明确还是未知 | 直接给整个任务判完成 |
| 验证证据 | 针对哪个产物/目标版本做过哪项核对，结果和限制是什么 | 模型无依据的“已验证”声明 |
| 失败尝试 | 观察、相关前提、已排除假设、下一次值得尝试的依据 | 跨任务长期经验库 |
| 执行安排 | 哪个任务何时以自动/确认模式触发，是否被修改/消费/取消 | 绕过该任务的运行条件和工具权限 |

任务生命周期可以简明地表达“待执行、运行中、正在挂起、已挂起、等待用户、已完成、已取消”；等待原因、排队和安排另作属性。**步骤的“已操作/未验证/已验证/未知”和任务生命周期是不同维度**，不宜把所有组合做成一长串互斥状态。

“挂起请求已接受”与“已停止后续工作且必要状态已保存”要区分。工具不能瞬间取消时先显示正在挂起，保留真实活动状态，不提前报告已经安静。

### 3.2 任务与聊天、todo 的关系

推荐本轮采用简单的“任务有主要关联会话”语义，普通历史聊天保持独立。用户可以在任务入口创建目标并暂不运行；进入任务后聊天与自然语言控制都有明确任务锚点。旧会话可讨论显式建立任务的入口，但不把全部旧聊天自动迁移成任务，也不让模型凭空推断旧会话已完成程度。

任务状态是权威，todo 是其步骤视图/更新入口之一。任务模式下调用 `todo_write` 应修改同一份工作进度，UI 修正也经同一控制边界进入；普通聊天原有 todo 可保留。**旧 todo 仅有 content/status，不能自动生成验证依据**，更不能把 completed 的每个步骤直接标为 verified。

控制修改应有版本/先后关系：用户新目标、纠正和暂停优先于旧模型输出。当前轮模型携带旧状态时，不能在下一步将用户修正写回覆盖；审批和时间触发也要对应有效任务/安排版本。这里只需要解决当前并发写者的实际竞争，不需要建设通用协作编辑框架。

### 3.3 可信进度与完成

推荐保留：原始及最新有效目标/约束、关键决定及理由、主要步骤、产物位置、验证对象与结果、错误和排除路线、未解决事项、明确下一步、等待/恢复所需信息。事实应尽量关联工具观察或用户确认；模型解释要与实际观察分开。

例如，“补丁应用成功”只支持代码已改；“某个测试通过”只支持它覆盖的行为；用户路径还未检查时应显示未验证部分。目标版本或有关产物改变后，应标注相关证据可能失效，避免把旧测试结论套给新版本；不需要无差别废弃所有历史成果。

模型可以提出完成判断并给出目标覆盖及证据，系统检查是否仍有明确未完成/未知项、证据引用是否存在。可直接验证的部分执行实际核对；主观或不可访问的部分保留限制、接受用户确认。**通用 Harness 不能凭一个布尔字段证明任意任务完成，也不宜让同一模型无限自审直到宣布成功。** 用户手动修正状态可作为用户陈述保留，但不能伪装成新运行过的测试。

## 4. 运行控制与持久恢复的候选方案

### 4.1 执行必须独立于页面连接

| 路线 | 能力与成本 | 研究判断 |
|---|---|---|
| 保留请求拥有运行，只新增任务记录 | 变更少，但网页关闭会停止，定时无连接执行与持久等待难成立 | **不能满足已确认需求**，不能作为最终交付 |
| 服务内运行控制持有唯一执行通道；HTTP 只提交控制/订阅状态 | 复用 Agent、同步工具和 stdlib HTTP；需持久状态与事件回放，处理启动/关闭/等待 | **推荐**；研究重点是职责和生命周期，不预设线程/asyncio 接口布局 |
| 每任务独立工作进程 | 进程退出边界清楚，但模型/MCP/审批/配置需跨进程协作与协议 | 本轮未有收益证据，不优先 |
| 整体迁移 LangGraph/OpenHands 等框架 | 提供成熟持久运行机制，但仍需任务产品语义、工具适配和权限集成 | 可参考机制，当前不建议为这些需求更换整个 Harness |

唯一执行通道可继续限制全局只有一个 Agent run，排队不预占执行资源。运行前按任务保存的工作目录/模型引用重建所需环境，复用当前工具；切换工作目录需正确装配 Skill/MCP。凭据从现有配置解析，不存入 checkpoint；引用失效时显示具体阻塞，不能悄悄用另一个目录或模型继续。

页面重新打开时应能读取当前任务快照、未处理人工交互和必要运行事件。沿用 NDJSON 加事件序号、有限增量读取/轮询，已经足以作为候选；没有依据要求换前端框架或必用 WebSocket。浏览器不可见不影响服务内工作，浏览器打开也不等于已有工具授权。

### 4.2 存储路线比较

| 路线 | 优点 | 本需求的具体成本 | 结论 |
|---|---|---|---|
| 在原会话 JSONL 增加任务事件并回放 | 格式已有、可审阅，旧消息继续读取 | 任务、安排、活动运行与审批需统一顺序；改名/删除/列表与任务更新需重审；多个文件之间不能天然原子更新 | 可行，但不能假定“已有 fsync”就已经解决任务一致性 |
| 每任务 JSON 快照 + JSONL 操作日志 | 可直接加载工作状态，便于文件查看 | 需解决快照/日志偏移、安排与操作结果的崩溃窗口、原子替换和重放版本 | 作为备选；本轮一致性要求已使自建协议成本变明显 |
| SQLite 保存新增任务状态与关键事件 | 条件更新、唯一约束和事务能将状态转换/安排消费/记录关联一起提交；stdlib 已有 | 需要清楚的数据归属、显式连接/事务生命周期、迁移及导出；外部副作用仍不在事务内 | **推荐作为新增任务的权威存储**，无需 ORM 或外部服务 |
| 外部数据库/分布式队列 | 提供跨服务能力 | 当前单服务、单执行通道无此需求，部署与恢复成本大 | 不采用 |

SQLite 能保证数据库内提交的原子性，不把文件写入、MCP 或网络操作变成可回滚事务。官方也说明写事务只有一个；要短事务提交事实，不在持有数据库写锁时等待模型、工具或用户。[SQLite Transactions](https://www.sqlite.org/lang_transaction.html)、[Atomic Commit](https://www.sqlite.org/atomiccommit.html)

**避免双真相：** 旧聊天继续读原 JSONL；新增任务的状态与关键运行事实从任务存储读取。若为了复用既有聊天展示生成 JSONL/历史视图，它只能是可重建投影，以稳定事件关联去重，不能和任务库同时接受独立的权威进度写入。另一种可行做法是直接把任务事件投影成现有展示形状，不持久化第二份原始事实。具体适配方式留给后续计划，不在本轮确定表结构。

### 4.3 检查点不应只在暂停时由模型总结

推荐在有意义的边界逐步保存：用户目标/状态修正、运行开始与结束、关键决定、准备派发的有副作用操作、操作结果、验证结论、重要失败/排除路线、人工等待与安排变化。不能等用户按暂停后再依赖一次可能失败的模型摘要来补齐全部状态。

任务 checkpoint 应包含直接继续所需的结构化工作状态与精炼上下文，并关联保留的调用/产物证据；模型总结只能帮助整理，不能覆盖原事实。已有 compaction 模板可以复用一部分内容，但它是上下文压缩，不天然具备用户修正优先、证据/操作关联或未知动作恢复语义。

无需每个 token 都同步落盘；文本流可有界批量保存，关键副作用边界应独立提交。核心记录保存失败时要停止派发新的副作用、保留可见错误，不能显示“已安全挂起”后继续执行。

### 4.4 恢复协议必须区分“未执行”和“未知”

| 持久证据 | 恢复时的合理判断与行动 |
|---|---|
| 意图记录存在，能证明未派发 | 可以在当前版本/权限下重新判断是否派发，不编造成功或失败 |
| 已进入可能派发边界，但没有确认结果 | **结果未知**；先检查对应文件/产物、远端状态或任务输出，不能直接重放 |
| 已有操作成功结果，但目标尚未验证 | 从验证/下一步继续，不重复成功操作 |
| 已有目标对应的验证与有效下一步 | 直接沿用；只核查会影响下一步的真实变化 |
| 后台进程随退出结束 | 保留已收集输出、停止原因与未完成状态；不能凭旧 PID/句柄宣称进程恢复 |
| 旧 run 留在 running/pausing，当前进程没有该运行 | 标记中断并保存未知项，转为可手动继续/待核查；不因 running 记录自行重启 |

准备执行的持久标记即使写在工具体之前，崩溃仍可能发生在实际调用前后；因此只能缩小未知范围，不能承诺 exactly-once。若工具提供幂等键或状态查询，可以利用；不可查询且后果重要时，向用户说明具体未知点。

正常退出应先停止接收新派发、请求活动任务挂起、保存已知状态与必要输出、清理既有资源；异常退出依靠已提交关键记录恢复。当前 daemon 请求线程及 MCP 同步等待不能作为可恢复工作上下文，需明确管理关闭边界。已有文件写入保护、进程树清理和父子停止信号继续复用。

### 4.5 持久人工等待与安全暂停

审批等待不应以一个跨数小时的内存 Event/工作线程持有整个执行通道。推荐保存待处理交互、对应任务/运行/动作、精确参数和有效版本，将 run 结束为“等待用户”；新网页或重启后能看到并处理。用户回答后，在有效任务状态和当前权限下继续该明确动作/后续工作。任务改变、取消或等待过期后，旧回答不能授权新动作。

“到时确认是否开始”与“批准一个具体工具操作”是不同交互；确认前者不能自动回答后者。也不能把没有回答记成“用户拒绝”让模型尝试替代方式。用户真正拒绝则保留该约束，禁止换工具绕过。

持久任务事件可以保留尚未决的工具调用，但发送给模型的工作历史仍须保持调用/结果合法配对。不能直接沿用 `close_pending_calls` 把待审批或未知动作补成普通失败，再让模型自行重试。恢复时先处理有效的待决动作或核查结果，再构造完整模型输入；同一批尚未执行的后续调用也要受最新目标、挂起和权限约束，不能机械重放整批。

手动挂起优先阻止后续派发，唤醒/结束等待，停止任务所属后台命令和可取消前台命令、子代理；保存已知输出和执行结果。正在原子写入文件时允许安全收尾，不承诺撤销。MCP 当前同步等待有超时但没有统一取消接入；即便等待超时，远端操作也可能仍生效，需保存未知状态，而非声称外部工作都已终止。取消 asyncio await 也不能被等同于杀死同步工具线程。[Python asyncio](https://docs.python.org/3.12/library/asyncio-task.html)

普通聊天已有“停止 Agent、后台 job 可继续”的行为保留；任务模式按用户本轮明确选择停止所属后台命令。后台输出在内存中有界保留，跨重启要保存必要尾部/结果信息并标明裁剪，不承诺恢复从未落盘的全部日志。任务等待用户期间如仍有实际运行资源，必须显示，不能用一个等待标签掩盖；切换执行通道前先妥善收束，避免把“单 Agent”误当成“无残留工具活动”。

## 5. 定时恢复与自然语言控制

### 5.1 调度候选

| 方案 | 能提供什么 | 局限/取舍 | 判断 |
|---|---|---|---|
| 服务内轻量到期检查 + 持久安排 + 唯一执行通道 | 覆盖一次性时间、串行等待、修改/取消和本次已确认规则 | 需要自行处理认领、重启、时区和状态变化，但这些领域判断使用库也不能省 | **本轮首选**；不是只创建一个长寿命 `sleep` |
| APScheduler 3.x 的 date trigger + BackgroundScheduler | 成熟日期触发、任务 store、misfire 与事件机制 | 仍需任务层全局串行和权限/等待；额外依赖及持久 job 序列化，不宜保存 Agent 实例 | 可选；若实际实现表明时钟管理复杂，再据证据选择 |
| 操作系统计划任务/常驻服务/云调度 | 可在应用未运行时启动程序 | 改变部署和授权边界，PRD 明确未要求 | 不采用 |

APScheduler 的 `max_instances=1` 是**每个 job**，不是 Nexus 所有任务的全局单执行容量；它的暂停调度也不是暂停正在执行的 Agent。misfire、coalescing 机制可借鉴，但不能让库默认补执行覆盖用户“错过后确认”的选择。本轮只参考 3.x 文档，不混用 master/4.x 的接口。[3.x User Guide](https://apscheduler.readthedocs.io/en/3.x/userguide.html)、[DateTrigger](https://apscheduler.readthedocs.io/en/3.x/modules/triggers/date.html)

### 5.2 一致的到期与竞争语义

| 情形 | 已确认行为 / 技术建议 |
|---|---|
| 手动模式，无时间 | 已确认：一直等待，不自动执行 |
| 服务运行，自动安排到期且执行通道空闲 | 已确认：该任务可启动/恢复；仍需检查有效状态、环境与权限 |
| 服务运行，到期时有其他任务执行 | 已确认：进入串行队列，不抢占；按时间及创建顺序派发 |
| 到时确认模式 | 已确认：持久记录待确认，只提示；用户确认后才获得开始资格 |
| 服务关闭期间错过 | 已确认：重开后等待确认，不自动补跑；不得一启动就将这些安排作为普通到期自动运行 |
| 时间或模式被修改/取消 | 建议：更新安排版本，旧计时回调/排队项失效；实际派发前再次核对 |
| 手动开始与定时恰好相撞 | 建议：同一任务/安排只能产生一个有效运行资格；后到请求返回当前真实状态 |
| 已完成/已取消/已删除任务的旧安排到期 | 建议：不执行；终态变更同步失效未消费安排 |
| 定时任务因审批/提问等待 | 已确认：转等待用户；保存待办交互，不能反复定时启动同一任务来“重试” |
| 意外退出时已有触发/运行认领 | 建议：按中断结果处理，保留本次认领；不把未完成 run 当成新的待到期安排再次派发 |

最重要的原子关系是：有效任务/安排状态检查、触发认领及运行身份关联。启动模型前后仍可能进程退出，所以“同一触发只认领一次”与“副作用只发生一次”是不同保证。手动挂起、取消和安排修改必须能使已排队的旧触发失效。

对于休眠、长时间停顿和系统时钟跳变，建议沿用“未能在有效服务期间正常触发则展示延误并等待确认”的产品原则；已经正常认领、只是等待执行通道的任务继续属于队列，不应混为关机错过。精确容忍窗口与界面措辞待局部细化，不承诺毫秒级准点，也不引入唤醒能力。

### 5.3 时间表示与本机约束

建议每次明确显示**完整日期、时间、时区/UTC offset 和模式**，持久保存对应 UTC 时刻及用户选择的时区表示，避免只存“明天八点”或裸 `datetime-local`。自然语言缺少日期/时区而产生实际歧义时先澄清，不替用户选择自动执行时间。

一次性确定时刻可以用明确 offset 转 UTC；如果支持 IANA 时区名，Python `zoneinfo` 需有时区数据。本机实测缺少 `tzdata` 且 `Asia/Tokyo` 不可加载；采用 IANA 路线时补 `tzdata` 是当前 Windows 需求的必要依赖候选，不是预先投资。固定 offset 路线依赖更少，但不能把 offset 当成永久的地区夏令时规则。[Python zoneinfo](https://docs.python.org/3.12/library/zoneinfo.html)

持久时间使用墙上时钟对应的 UTC，单次等待/退避使用单调时钟并重新核对到期条件；不能把一次很长的 monotonic deadline 保存后跨进程使用。重启、时钟改变或休眠后需从持久安排重新判断。[Python time](https://docs.python.org/3.12/library/time.html)

本轮 PRD 没有周期计划、cron、依赖任务链或自动重新安排的要求；暂按一次性安排研究，不顺手扩展。

### 5.4 按钮与自然语言作用于同一状态

推荐所有入口最终提交同一种有目标任务 ID 的控制意图，例如创建但不执行、开始/恢复、挂起、取消、修正状态、修改/取消安排。意图必须经过同一任务状态校验、版本与运行容量判断；不能按钮改数据库、自然语言只追加一段“我暂停了”。

明确的当前任务控制可直接执行，不为已经明确授权的普通动作多加确认。存在多个相似任务时，先以当前任务锚点、精确 ID/候选列表确定对象；仍有歧义则澄清，不按“最近一项”猜测。引用文档中的“删除任务”或讨论某条命令，不应当作用户在下达操作。

运行中自然语言挂起需要独立于当前模型 run 的控制通道：现有聊天 send 在运行时直接返回，不能只加一个模型工具就满足验收。复杂意图可由受限解释调用提出候选，但只有已解析、已验证的控制请求才能改变状态；创建草稿不应顺便触发工作 Agent，且按钮创建不应依赖已配置模型或密钥。

前端可复用现有侧栏和会话区域，增加简明任务列表/详情及控制、安排与人工待办。显示当前目标、步骤证据状态、阻塞、下一步、安排/排队原因即可，不建设大型项目管理界面。

## 6. 失败止损与任务状态联动

### 6.1 值得持久保存的尝试信息

至少能回答：发生了什么失败、当时哪些前提相关、尝试了什么、观察到什么新事实、排除了哪个假设、还不知道什么、为什么下一步值得做。记录应关联当前任务/步骤与实际调用；不存每一行重复日志，不扩成跨任务知识库。

系统可以可靠产生调用、参数、退出码、timeout/取消、观察变化；“根因是什么、是否应换策略”仍需模型结合任务解释。模型推测必须标明未证实，不应以一句“缺少依赖”覆盖实际错误，也不把工具通用 `execution_failed` 直接当成根因。

| 失败/观察 | 处理方向 | 必须避免 |
|---|---|---|
| 参数或工具选择错误 | 阅读 schema/接口、修正输入后再试 | 相同错误参数反复调用 |
| 环境条件不足 | 核实真实环境，查询官方/本地参考，再选择有依据的替代 | 无线索换版本/工具盲试 |
| 权限被拒绝 | 保留拒绝与允许范围，必要时报告阻塞 | 换工具完成同一被拒操作 |
| 暂时性模型/传输故障 | 沿用有限退避与已产生输出不重放的限制 | 将其计成任务策略已被反证 |
| 工具超时、输出截断或没有新输出 | 区分操作失败与观察不完整，查询实际状态 | 将未知当失败，直接再次发副作用 |
| 有新错误线索、修改了相关代码/前提 | 记录变化后允许有依据的验证重试 | 只按次数阻断合理调试 |
| 正常后台轮询 | 看 job 状态、cursor/输出与等待条件；观察未变不是一次失败 | 把连续相同 job 查询一律视为死循环 |
| 验证失败 | 对照目标和产物定位差距 | 用另一个不相关成功测试宣布完成 |

### 6.2 候选止损机制

| 路线 | 优点 | 局限 | 取舍 |
|---|---|---|---|
| 只强化系统提示 | 成本低，保留模型灵活性 | 不能稳定限制反复失败；重启也缺排除路线 | 作为基础，不能单独交付② |
| 固定调用次数/相同参数强停 | 简单、可解释 | 误伤轮询与有效重试，漏掉换拼写的同一死路 | 仅作候选信号，不直接作为通用判定 |
| 任务内尝试记录 + 轻量重复信号 + 模型原因/变化判断 + 受控止损 | 能关联实际前提和新信息，恢复后可继续使用 | 需约束模型泛称“换一种办法”，并验证不误伤 | **推荐**，无需自动诊断引擎 |
| 独立 critic/自动诊断代理 | 可额外分析 | 成本/相关错误增加，本轮不扩多 Agent | 暂不采用 |

推荐在同类失败、同类动作、相关前提未变化时提示已尝试与排除路线，要求下一次行动明确新的信息来源或可区分假设的检查；如果仍重复无依据动作，停止该分支并挂起/报告阻塞。允许查可靠资料、指定本地实现和最小诊断，不让模型用换命令拼写绕过。

触发计数可以作为局部参数，但 PRD 验收重点是无新信息时真的停止无效路线、合理重试仍可继续。任务内尝试记录要被恢复上下文实际读取；只有数据库里一段失败日志或 UI 卡片仍不满足②。

### 6.3 可核对的参考机制

OpenCode 官方 `doom_loop` 以相同输入重复三次作为权限信号，适合参考简洁的信号入口，不足以判断所有停滞。OpenHands SDK `v1.55.1` 的 stuck detector 区分重复 action/observation、action/error，并在某些连续错误时先给纠偏提示。这些实现说明“先提示再判断/结束”可工程化，但参数不应照搬成 Nexus 验收定义。[OpenCode permissions](https://opencode.ai/docs/permissions/)、[OpenHands stuck detector](https://github.com/OpenHands/software-agent-sdk/blob/v1.55.1/openhands-sdk/openhands/sdk/conversation/stuck_detector.py)

## 8. 如何验证后续成果，避免形式完成

下表是需要取得的证据与现有复用基础，**不是实施排期或新增测试文件计划**。应使用模拟工具/可控时钟验证确定性边界，再用真实界面、重启和目标模型任务验证用户结果；不能相互替代。

| 验收主题 | 应观察到的实际结果 | 关键对照/异常 |
|---|---|---|
| 先创建而不执行 | 未配置模型时也可用按钮保留任务；重启后仍在，无模型/工具调用 | 普通问答不强制产生复杂任务；自然语言创建暂不执行不会顺便开工作 run |
| 多任务独立 | 三任务不同目标、进度、失败与安排；恢复 A 使用 A 的目录/上下文 | 名称相似、当前页面切换、全局配置改变不串线 |
| ①进度和完成 | 可显示产物已产生但未验证、已验证、阻塞与下一步；模型下一步引用最新状态 | 工具 ok 但目标未达成、用户纠正后不回写旧清单、证据引用缺失 |
| ②止损与恢复 | 同前提无新信息失败后换调查/方案或挂起；重启后记得已排除路线 | 正常 job 轮询、有限暂时故障、新证据验证仍可进行；拒绝授权不被绕过 |
| 手动挂起 | 很快阻止新动作；正在挂起和完成挂起有真实区分；所属后台进程结束且输出可查看 | 前台命令/子代理/审批/MCP 等待中暂停；不声称回滚或任意远端立即停止 |
| ④跨重启直接继续 | 已保存目标、决定、验证及下一步；按钮和自然语言都可从已知位置推进 | 正常退出与强制结束分开；没有模型可用时仍可查看/管理状态 |
| 未知副作用 | 构造“操作生效、结果尚未记录”中断，恢复先查询目标对象而非重复操作 | “明确未派发”和“可能派发”分别验证；协议 interrupted 不冒充真实失败 |
| 自动与确认安排 | 只执行显式安排的 A；C 到时待确认；B 不执行；页面关闭仍按规则运行 | 改时间、取消、重复回调、同刻手动恢复、已有任务运行、多个同时间任务 |
| 错过安排 | 服务关闭时到期，启动后进入待确认，先不执行 | 已经在线认领并排队与关机错过分别验证；休眠/时钟变化按约定行为 |
| 持久人工待办 | 自动任务遇审批/提问后等待，重开仍可处理，其他无关任务状态不丢 | 过期令牌/任务已改/已取消后迟到答案不得执行旧动作 |
| 兼容 | 现有三协议、旧 JSONL、权限、Skill、MCP、串行子代理仍正常 | 新任务挂起与普通聊天停止区别清楚；任务/会话删除不留下活跃安排 |

真实目标模型需要验证两类行为：恢复时确实使用 checkpoint 中的计划/失败记录，而非重新全面扫描；止损时确实利用新信息，而非单靠固定阈值截断。应记录实际调用轨迹、产物和用户路径，不把测试桩按既定答案输出当成模型质量证据。

已有 `tests/test_web_runtime.py`、`test_context_integrity.py`、`test_approval_cancel.py`、`test_jobs_runtime.py`、`test_session_atomicity.py` 等可以作为行为基线。新成果仍需独立验收；本轮没有新任务 UI、持久任务或定时运行的实测成绩。

## 9. 风险、建议语义与后续需要细化的问题

### 9.1 关键技术风险及控制方向

- **保存了状态，却不参与行动：** 恢复输入应显式包含最新目标/决定、有效步骤/证据、失败路线与下一步；需要用轨迹证明。只读完整历史或一张卡片不足以交付。
- **关键记录与副作用顺序错误：** 操作意图先保存，结果后保存；失败保存阻止后续副作用；未知状态不自动重放。数据库只解决内部一致性。
- **任务状态相互覆盖：** 用户修正、模型更新、计时回调、迟到审批共同写入，应检查任务/安排版本；不能简单 last write wins。
- **暂停名义化：** 有尚未收束的线程/进程/远端动作就保留活动或未知说明；不能为了释放界面先伪造“已停止”。
- **调度意外重新激活：** 手动挂起/取消、终态、旧安排版本和已消费触发要在派发前复核，不能每次轮询重复启动。
- **恢复错环境或扩大权限：** 使用任务工作目录与有效模型引用，重查权限/工具可用性；不保存密钥、不恢复旧临时授权为永久规则，也不悄悄切到别的模型。
- **摘要失真或过度重查：** 事实与总结分离、引用证据，恢复只核查相关差异；不承诺所有事实永远无需重查。
- **按 tool ok 判断任务成功：** 显式区别操作、产物、验证与整体目标；后台启动成功不是进程最终成功，子代理报告不是独立验收。

### 9.2 已有选择下仍需细化的产品语义

以下是局部建议，不是尚未获得答复的四项已确认问题；也不应被包装成技术阻塞。

| 问题 | 建议起点及理由 |
|---|---|
| 任务与会话的关联 | 本轮一任务关联专属消息记录；普通聊天继续独立，避免先建多对多会话系统。界面统一显示任务消息与状态。实现阶段确定该关系并写入 `docs/PROGRESS.md`。 |
| 单次时间与时区 | 先支持一次性时刻，显示完整日期/时区/模式；采用 IANA 时区时补 Windows tzdata。用户有明确地区偏好则遵循，不默认 UTC 输入 |
| 手动挂起与既有时间安排 | 已确认：普通挂起保留尚未到期的显式未来安排，同时取消已到期/排队的旧触发；用户表达“不要自动继续”时取消安排。界面显示未来时间。 |
| 等待期间释放执行通道 | 保存待处理动作，不用阻塞线程占用唯一 Agent 通道；先显示并收束实际工具资源，不能把有后台活动说成完全空闲 |
| 任务目标/范围被重大修改后的自动安排 | 不把旧的自动安排默认为对新范围的授权；提示重新核对安排，避免扩大自动执行内容 |
| 取消后能否再继续 | 已确认：取消保留记录并失效安排；通过单独的“重新启用”恢复为挂起，普通“继续”不恢复已取消任务。重新启用不恢复旧安排。 |
| 删除与关联会话 | 已确认：永久删除任务时一并删除其专属消息和执行记录，不删除工作区文件；删除前说明并确认。普通聊天记录独立保留。 |
| 休眠及较长调度延误 | 错过后进入等待确认；在线正常认领、仅等执行容量的任务保持串行排队。运行条件与任务开始顺序此前已确认。 |

如果用户对这些局部建议有不同预期，应在正式计划前说明具体行为差异；不能凭实现便利削减定时确认、自然语言、失败继承或跨重启恢复。

### 9.3 当前推荐取舍与本轮不做

**建议保留现有技术栈，采用服务内单执行通道、独立任务状态/关键证据、SQLite 新增任务存储、简明一次性安排与统一控制入口。** 轻量调度和 APScheduler 仍保留备选比较；所有选择应以三项能力真实联动和兼容成本评估。

不做跨任务经验学习、向量检索、多 Agent 并行、通用诊断引擎、OS 自启/唤醒、云服务、任意外部动作回滚或 exactly-once。新增持久人工等待、运行与连接分离、任务内失败证据属于本轮交付所必需，不能以“避免复杂度”为由省掉。

本阶段没有要求用户批准具体框架或数据库 schema；当前没有必须通过业务代码试错才能继续研究的关键阻塞。四项关键运行语义已确认，后续可在本会话继续细化产品交互与总体设计，再进入计划/实施。
