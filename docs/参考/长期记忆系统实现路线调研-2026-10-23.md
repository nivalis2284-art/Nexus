# 长期记忆系统实现路线调研：从 RAG 到经历、认识与技能

研究日期：2026-10-23，Asia/Tokyo。

**性质：研究报告与候选比较，不是选型决定或开发任务。** 本轮只阅读本地资料、查询官方文档与论文、读取公开仓库元数据；不安装服务、不运行候选、不调用付费模型、不修改 Nexus 实现。另一个会话正在推进插件系统落地，本报告不推断其完成状态，也不向其发送消息。

本文侧重回答“有哪些实现形式、成熟到什么程度、能复用什么”，与[人设、自我与长期记忆调研](PERSONA-MEMORY-RESEARCH.md)互补。旧报告保留其当时语境；本次涉及项目现状的判断重新查证，不能把旧报告中的版本和候选顺序视为今天已定案。产品目标参考[记忆块设想](外部接入-分支与记忆设想.md)，接入关系参考[插件系统理论](../理论/02-插件系统理论.md)。

## 一、先读结论

**目前最有现成工程可复用的路线，集中在外部持久记忆：原始资料与来源可追溯，少量当前认识常驻，详细经历按需查找，并在写入时提取、关联或整理。** 这是本次对不同项目共同机制的综合判断，不是统一市场份额统计，也不表示存在一个包办所有需求的行业标准。

“RAG”不是长期记忆的一种固定数据库。它描述取回材料来辅助生成的方式，检索也不必只用向量。记忆系统还需要决定记什么、怎样更新、如何保留变化、何时使用，以及能否纠正和删除。许多新系统继续使用 RAG，新增价值主要来自记忆形成与演变，而非完全取消检索。

对灵最值得比较的三条完整候选是：

1. **可读文件与事件笔记：**以 Basic Memory 等复用文件、索引和工具，自己确定经历与当前认识的含义。适合重视直接查看、修改和长期迁移。
2. **经历整理服务：**重点看 Hindsight 的事实、经历、综合认识与召回能力。适合希望复用较完整的记忆处理流程。
3. **文件与后台整理结合：**把当前 EverOS 纳入重点比较；它将经历、用户认识与 Agent 案例／技能组织在可读文件和索引中。与记忆块方向接近，但其自动派生和整理行为需要实际验证。

以上不是已经选定的前三名。若主要需求是事实与偏好，可比较 Mem0；若主要需求是人物关系和时间变化，可比较 Graphiti；若主要需求是研究资料和知识联系，可比较 Cognee；MemOS 的本地插件核心也有较多可复用机制。具体差异见后文。

较新的方向主要有：**关联笔记、持续整理的知识库、经历整合、经验／技能学习、多模态经历，以及模型内部的神经或隐状态记忆。** 前几类可以在外部 API 模型周围构建；Titans、MemGen 等内部路线通常需要控制训练或推理过程，当前不能像 MCP 服务一样直接挂到任意模型上。

## 二、研究方法与“成熟”的含义

本轮拆分核查外部记忆服务、文件与框架、研究架构，主代理负责方法分类、当前版本复核、公开热度采样、评测与 Nexus 适配判断。部分研究方向的并行初查证据不足，由主代理补查作者论文和仓库。

主要采用论文原文、作者仓库、项目官方文档、模型发布者的模型卡、GitHub 公共 API。没有用营销榜单拼性能排名。论文重点核对方法和限制；少数远期路线只核对摘要及公开训练／推理入口，不声称完成所有源码审计。

| 判断维度 | 本文怎样使用 | 不代表什么 |
| --- | --- | --- |
| 基础组件成熟 | 全文搜索、关系存储、向量索引等已有清晰机制与文档 | 组合起来就能自动形成好记忆 |
| 工程化记忆系统 | 有安装、接口、持久化、部署或集成文档 | 已在 Nexus 的 Windows、中文日常交流中实测稳定 |
| 研究实现 | 作者提供方法与实验代码，可研究或改造 | 已具备完善产品生命周期和运维能力 |
| 热度 | 当前仓库关注数量，作为筛查参考 | 效果、可靠性、中文质量或适配程度 |

“本地运行”也要拆开看：资料存在本机、程序在本机、抽取与向量模型是否也在本机，是三个问题。支持本地数据库不等于不调用外部模型。下文的部署代价是相对工程判断，不是实测内存、速度或费用承诺。

## 三、先把容易混淆的概念分开

### 3.1 RAG 负责取用，记忆覆盖完整过程

一个可以长期工作的记忆过程可表示为：

```text
真实消息、观察、工具结果
        ↓
保存来源与原始记录
        ↓
挑选、分段、抽取经历或事实
        ↓
关联、纠正、形成当前认识与经验
        ↓
按当前问题查找或主动提供必要背景
        ↓
交给灵理解和行动，再留下新的实际记录
```

普通向量 RAG 主要覆盖“索引—查找—送入请求”。采用事实抽取、知识图、文件 Wiki 或反思，并不意味着不再有这一步。

### 3.2 按三个角度观察，比只说长短期更清楚

| 角度 | 可选形式 | 大白话 |
| --- | --- | --- |
| 记忆保存在哪里 | 外部文字／结构、模型参数、隐状态 | 放在可读资料中，还是放进模型内部 |
| 记忆在做什么 | 事实、经历与经验、当前工作材料 | 记住信息、从过去学方法、维持眼前处理现场 |
| 记忆怎样变化 | 新增、整理、关联、纠正、取用 | 形成、演变和召回分别做了什么 |

这一观察方式参考综述 [Memory in the Age of AI Agents](https://arxiv.org/abs/2512.13564)。本文后面的路线是方便选型的工作分类，彼此可以组合，不是宣称每个项目只能归一类。

### 3.3 记忆系统与上下文编排的边界

记忆实现负责保存、索引、检索与自己的整理算法；上下文编排负责在一次模型请求前取得适当材料，安排容量、位置和来源。MCP 可以承载主动查询，也可以被宿主程序调用，但接入 MCP 不自动完成自动召回。

用户所设想的“原文—事件记忆块—当前认识”，可以同时使用文件、关键词、向量与关联关系；没有必要在“记忆块”与“RAG”之间二选一。

## 四、实现形式全景

| 路线 | 核心变化 | 代表 | 当前复用层次 | 与外部 API 模型的关系 |
| --- | --- | --- | --- | --- |
| 混合检索型记忆 | 关键词、语义、时间、重排共同找材料 | SQLite FTS5、Qdrant、pgvector | 基础组件成熟 | 直接在模型外使用 |
| 事实与偏好管理 | 写入时抽取有效信息并维护关系 | Mem0 | 有现成库与服务 | 可外接；需要抽取／向量模型 |
| 分层可编辑记忆 | 少量核心常驻，大量档案按需访问 | MemGPT／Letta、MemoryOS | 方法成熟，有不同工程形态 | 可外接，但完整 harness 会重叠 Nexus 职责 |
| 关系与时态图记忆 | 明确谁与谁、何时成立、后来怎样变 | Graphiti、Cognee；GraphRAG 作对照 | 图组件成熟，记忆引擎需适配 | 外接，通常需要抽取模型 |
| 关联笔记与 Wiki | 记忆形成链接与持续修订的文档 | A-MEM、Basic Memory、memU | 从研究实现到现成工具均有 | 可外接；部分整理由原 Agent 执行 |
| 经历整合与认识生成 | 从多段经历形成可更新的认识 | Hindsight、EverOS、MemOS | 已有工程化方案 | 可外接，但整理会产生额外调用 |
| 经验与技能记忆 | 保存可复用做法、适用条件与失败教训 | ACE、MemRL，部分文件记忆平台 | 有开源方法和部分产品能力 | 外部文字型经验可复用，不必训练主模型 |
| 多模态／多类型记忆 | 将画面、资料与不同记忆用途一起组织 | MIRIX | 有完整项目，链路更长 | 可用多模态 API，需单独处理原始媒体 |
| 参数化与隐记忆 | 让参数或内部连续表示承载记忆 | Titans、MemGen、持续微调 | 研究与模型工程路线 | 一般不能通过普通聊天 API 注入 |

### 4.1 混合检索：成熟底座仍然很有价值

普通向量相似度适合找“意思相近”的内容；精确人名、编号、项目名、否定条件和日期，往往需要关键词或结构条件配合。重排则在取回候选后，再判断哪些最有帮助。

可复用机制包括全文索引、向量索引、时间／来源过滤、多路结果融合与按需重排。Qdrant 提供混合查询和融合接口；PostgreSQL 的 pgvector 可与数据库已有能力组合。两者都不替应用定义“哪些经历值得长期记住”。[Qdrant 混合查询](https://qdrant.tech/documentation/search/hybrid-queries/)、[pgvector](https://github.com/pgvector/pgvector)

对灵而言，这适合支撑原文搜索与记忆块召回。它应成为可比较的基础路线，不能因为有新名词就默认效果更差。中文分词、别称、混合中英文仍需用实际材料验证。

### 4.2 事实与偏好管理：重点是写入，而不只是搜索

这一类会把冗长对话提炼成“偏好是什么、发生了什么、以后可能有用的事实是什么”。相比直接切片，它可以减少无关话语，但抽取时也可能漏掉当下不显眼、以后有意义的细节。

Mem0 是代表之一。需要核实所用版本怎样处理旧新事实，而不是看到项目支持记忆就假定它会准确覆盖过期认识。归档事实与原始聊天仍应分别保留，详见项目比较。

适合灵的用途是用户偏好、人物资料、常见事实；单独使用它，通常还不足以表达“那次为什么这样决定”“我后来怎样改变理解”。

### 4.3 分层可编辑记忆：核心常在，细节可展开

这类方法把少量关键资料放在当前可见范围，把大部分记录放在外部，再由工具查找、替换和写回。它不要求把所有历史一直塞进请求。MemGPT 是重要方法来源；MemoryOS 进一步按短期、中期、长期组织资料。[MemGPT](https://arxiv.org/abs/2310.08560)、[MemoryOS 作者仓库](https://github.com/BAI-LAB/MemoryOS)

对灵可直接借鉴：少量身份与当前关键认识常驻，事件记忆块按需进入，原文再展开。分层是取用策略，不要求建设多个数据库，也不等于简单把旧聊天压缩后删除。

MemoryOS、MemTensor 的 MemOS、EverMind 的 EverOS 是三个不同项目；“Memory OS”是架构比喻，不能凭名字推断能力相同。

### 4.4 图记忆：关系与变化成为可查询的对象

它适合回答：“当时谁负责这个项目？”“小明换工作前后有什么变化？”“这次决定与哪几次讨论有关？”图关系可以补足仅按语义相似取片段的不足。

也要区别两种常被混称的 GraphRAG：微软 GraphRAG 对语料抽实体、关系及社区摘要，支持局部与全局问题；Graphiti 更强调持续进入的事件和随时间变化的关系。采用图结构并不自动具备时间失效处理。[微软 GraphRAG](https://microsoft.github.io/graphrag/)、[Graphiti](https://github.com/getzep/graphiti)

对灵，简单的“后续、纠正、支持、履约”链接可以先借鉴；是否值得使用完整图引擎，要看跨人物、跨事件查询是否真的经常发生。图中的关系如果来自模型推断，也需要与原文明确表达的关系分清。

### 4.5 关联笔记与 Wiki：把过去整理成可持续阅读的资料

A-MEM 借鉴卡片笔记法：为记忆生成描述和关联，新记忆到来时调整记忆组织。它保留检索，改变的是被检索资料之间的联系。[A-MEM 论文](https://arxiv.org/abs/2502.12110)、[作者实现](https://github.com/agiresearch/A-mem)

文件路线则将记忆保存为能直接阅读和编辑的笔记，结合索引和关系导航。Basic Memory 属于这类现成实现；当前 memU 也强调跨会话、跨 Agent 的 Wiki 与可复用技能，但具体整理分工不同。

优点是可读、可改、便于跨模型迁移；代价是需要管理主题重复、旧结论修订和文档增长。文件本身不是召回算法，能打开文件也不等于模型会恰好读到它。

2026 年的 AgentRunbook-C 还探索让 Agent 像研究者一样搜索文件、检查轨迹、选取证据。这说明“主动翻资料”是一条有效研究方向，但作者同时报告延迟代价，不能推广成文件一定胜过向量。[LongMemEval-V2 方法与实验](https://arxiv.org/html/2605.12493v1)

### 4.6 经历整合：从事件形成当前认识

经历记忆保存一次实际过程；整合则从多段记录中形成较稳定、又允许改变的认识。例如，多次交流支持“所有者希望先讨论再开发”，以后新的交代可以补充适用范围。

Hindsight 有事实、经历、综合观察和预先整理的认识；EverOS 有事件、用户资料和 Agent 案例／技能等不同内容；MemOS 也提供更新、反馈与多种记忆管理。它们是在不同组织方式下实现“写入后继续加工”，不能仅按是否有向量库比较。[Hindsight 机制](https://docs.hindsight.vectorize.io/enterprise/how-hindsight-works/)、[EverOS 记忆过程](https://github.com/EverMind-AI/EverOS/blob/main/docs/how-memory-works.md)

对灵很有价值，但需要保留“发生过的事”与“从中形成的理解”的区别。后台总结会调用模型、可能晚于原始记录可用；“资料写入成功”“索引可搜”“派生认识已更新”不一定同时发生。

### 4.7 经验与技能：让过去改善做事的方法

它记录的重点不是用户喜欢什么，而是：“什么条件下，这种做法有效？”例如一次部署失败，可以留下环境条件、失败原因和后来有效的步骤，再在类似任务中取用。

**ACE** 将上下文当作持续积累的操作手册，通过生成、反思和整理进行局部增量更新。可借鉴有条件的经验条目、保留细节和小范围修改；不必整体照搬其执行框架。其有效性仍依赖整理者能否从结果中提炼有用经验。[ACE 论文](https://arxiv.org/html/2510.04618v3)、[作者代码](https://github.com/ace-agent/ace)

**MemRL** 先查语义相关经历，再利用实际反馈学习哪些经验更有用；学习发生在记忆选择上，不更新主模型权重。它仍然使用检索。论文也列出长期反馈噪声、多条经验的贡献难以分摊、任务不相似时收益下降等限制。[MemRL 方法与限制](https://arxiv.org/html/2601.03192v2)、[作者代码](https://github.com/MemTensor/MemRL)

对灵，可以先复用文字经验与技能结构。是否使用分数、强化学习或自动技能演化，应由实际任务反馈决定；不能把一次成功推广成普遍规律，也不将任务反馈分数直接当成人格成长。

### 4.8 多模态与多类型记忆：把看到的东西也纳入经历

MIRIX 将核心、事件、语义、程序、资源和知识库分工管理，原始方向包括屏幕观察与自然交流。当前作者项目有客户端、后台与界面，也有不同记忆类型的整理入口。[MIRIX 论文](https://arxiv.org/abs/2507.07957)、[当前仓库](https://github.com/Mirix-AI/MIRIX)

适合未来图片、屏幕活动和工具经历丰富的场景。代价包括媒体解析、模型调用、存储与多步骤处理。多模态记忆不能只留一段图片描述就宣称保留了全部视觉细节；要精确展开时，仍需关联原始图片、页面或音视频位置。

“分六类”不是每个系统都需要遵守的标准。灵可以先采用有实际用途的分类，避免为了复现名称而拆出多套 Agent。

### 4.9 参数化、测试时神经记忆与隐状态记忆

这类才更接近“把记忆放进模型里面”，但内部又有不同机制：

| 方式 | 记忆载体 | 复用条件 | 对灵当前路线的意义 |
| --- | --- | --- | --- |
| 持续微调／适配器 | 模型参数或附加参数 | 数据、训练和模型发布控制权 | 可研究稳定技能与倾向，不适合作为精确私人事件的唯一档案 |
| Titans | 在测试时学习的神经长期记忆模块 | 对架构、状态与推理过程有控制 | 是模型架构研究，不能通过普通 MCP 给任意模型加装 |
| MemGen | 触发器与生成器产生的隐记忆序列 | 训练相应模块并接入模型内部表示 | 有作者代码和训练脚本，但不是普通聊天接口可读写的事件库 |

Titans 的 arXiv 初次提交日期为 **2024-12-31**，编号属于 2501；论文讨论长期神经记忆与注意力的配合。此处核对论文架构，没有确认可供 Nexus 直接部署的作者独立记忆服务，也不把同名第三方 MCP 当作论文实现。[Titans 论文](https://arxiv.org/abs/2501.00663)

MemGen 于 2025-09 初次提交；作者仓库当前可访问，并提供特定开源模型的训练、推理脚本和检查点入口，部分环境仍列为待发布。即使主推理模型保持冻结，隐表示的插入仍需要模型内部接口。训练出的隐记忆也不能自动等同于“今天所有新经历都已永久学会”。[MemGen 论文](https://arxiv.org/html/2509.24704v1)、[当前作者仓库](https://github.com/bingreeky/MemGen)

这些方向值得跟踪，但对目前通过外部 API 使用模型、又希望能回查原文和跨模型迁移的 Nexus，直接接入条件明显不同。外部记忆与内部记忆可以长期互补，当前无需为尝试记忆块而更换模型底座。

## 五、不能混作长期记忆的相邻技术

| 技术 | 解决什么 | 与长期记忆的区别 |
| --- | --- | --- |
| 更长上下文 | 一次请求可以读更多材料 | 不自动决定多年历史怎样保存、更新和选取 |
| 对话压缩 | 把当前现场缩到可处理范围 | 摘要丢掉的原文不能靠再次总结恢复 |
| KV／提示缓存 | 减少重复计算与部分请求成本 | 不自动新增可搜索、可纠正的私人历史 |
| 工作流检查点 | 暂停后恢复程序状态 | 恢复现场与跨活动形成经验是不同用途 |
| 人设／Skill 文本 | 告诉灵身份、原则或做法 | 有文本不等于已实现经历存储、召回和自动更新 |

因此，“原文全部保留”“有向量数据库”“有一个常驻摘要”“能跨重启恢复”都可以是组成部分，单独拿出来不能证明长期记忆闭环已经完成。

## 六、现成项目与复用边界

本节按当前交付形态比较，不把同一品牌的论文、开源库、云服务和宿主插件合并成一项能力。工程部署与来源展开条件均需在最终候选上实际验证。

### 6.1 概览

### 6.2 Mem0：必须区别自动抽取与显式更新

官方 v3 迁移说明的 ADD-only 指自动抽取新增事实，不再由这一抽取步骤自动决定旧行的 UPDATE／DELETE；公开的显式 update、delete 和单条 memory history 仍然存在。不能写成“Mem0 无法修改或删除”。当前 OSS 移除的是外部图存储集成；实体匹配仍可用于检索排序。[迁移说明](https://docs.mem0.ai/migration/oss-v2-to-v3)

官方矩阵将核心 CRUD 与部分专有能力区分：Platform 另有图记忆、Dream、衰减和时间推理等。不能把托管成绩或能力全部计入本地开源 SDK。[Platform 与 OSS 比较](https://docs.mem0.ai/platform/platform-vs-oss)

官方通用 MCP 入口由 Mem0 托管，需要 Platform 账号；这不等于开源 SDK 在本机自带同一个服务。面向特定宿主的本地插件也须单独核对，不能据其存在就宣称任意 Nexus 都能免适配接入。[Mem0 MCP](https://docs.mem0.ai/platform/mem0-mcp)

原文方面，当前 OSS 的 history 保存的是事实文本的 old／new 变化；本地消息表只保留每个 scope 最近十条，属于近期抽取上下文，不能当作完整会话档案。因此记忆块若采用 Mem0，应另保留完整来源，metadata 关联消息或事件。[存储源码](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py)

### 6.3 Hindsight：整理能力与原档保存分别检查

官方提供 retain、recall、reflect 及内置 MCP；可只复用前两者，让灵根据取回材料自行形成判断。reflect 返回的是另一轮模型综合结果，不是原文。[MCP 接入](https://hindsight.vectorize.io/developer/mcp-server)、[安装形态](https://hindsight.vectorize.io/developer/installation)

本次核到的当前配置默认开启原文文本保存，可保留 document 和 chunk 文本；API 提供文档访问。但同一个 document_id 再写入，默认更新／替换内容，而不是自动建立永久可展开的全文版本史。[配置源码](https://github.com/vectorize-io/hindsight/blob/main/hindsight-api-slim/hindsight_api/config.py)、[Documents API](https://hindsight.vectorize.io/developer/api/documents)

有些概述页面仍用“抽取而不保存对话”描述产品，不能据此断言当前版本不存任何原文，也不能反过来保证所有配置永远保留旧原文。若灵需要回到每个历史版本，仍应明确原档归属、文档编号与替换策略。部署文档的 PostgreSQL 版本要求也存在页面差异，实施前按选定版本核对。

### 6.4 Graphiti：适合时态关系，MCP 目前仍标实验性

核心库保存 episode，并抽取实体与关系；关系能表达有效时间与失效时间。当前源码的 EpisodicNode.content 用于保存摄入的 episode 原文，但前提是应用确实把需要的全文交给它。不是只传一个摘要后，就能展开从未传入的聊天。[节点源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/nodes.py)

官方 MCP 文档明确标为 experimental，目前列出 FalkorDB 和 Neo4j；不能从核心库支持的所有驱动推断 MCP 支持范围。精确读取某一段原文的工具路径也需验证。[官方 MCP 文档](https://help.getzep.com/graphiti/getting-started/mcp-server)

Graphiti 的开源代码与 Zep 托管产品分别比较。Zep 的管理、治理和云端上下文功能不自动成为 Graphiti 本地库的一部分。[官方产品边界](https://help.getzep.com/graphiti/getting-started/overview)

### 6.5 EverOS：本次新增的重点比较对象

旧 EverMind-AI/EverMemOS 地址当前重定向 EverMind-AI/EverOS。当前 README 描述 Markdown 为可读内容，SQLite 与 LanceDB 支撑管理和检索，不能继续沿用旧教程中较重的依赖组合来估计今天的安装成本。[当前 README](https://github.com/EverMind-AI/EverOS)

其细节文档区分事件、原子事实、用户资料、Agent 案例与技能；事件提取后，部分派生内容异步形成，文件更新再同步到检索索引。值得借鉴的是来源、派生与可搜索状态分别表达，而不是照搬它的全部类别和后台策略。[记忆过程](https://github.com/EverMind-AI/EverOS/blob/main/docs/how-memory-works.md)

作者另有 EverOS-MCP，支持指向自托管服务。由此具备作为外部候选的接入条件，但不能据此保证 Nexus 的自动召回已经完成。将它升级为重点候选是本轮判断，不是已通过实测的新首选。[EverOS-MCP](https://github.com/EverMind-AI/EverOS-MCP)

### 6.6 memU：当前版本把整理工作交给原 Agent

当前 README 强调 Wiki 与从历史提炼可复用技能：原 Agent 阅读切片记录并写出 Markdown，MemoryService 负责保存、向量化和检索，不在其中另做聊天模型调用。这里“服务不调用 LLM”不代表整条流程不花模型计算；整理只是发生在宿主 Agent 一侧。[当前 README](https://github.com/NevaMind-AI/memU)

现成宿主适配主要用记录桥接与指令提示触发检索。Nexus 已有自己的插件约定，不宜照搬修改其他宿主指令文件的安装办法。可复用其存储和技能取用分工，自动参与时机仍按 Nexus 契约实现。

### 6.7 MemOS：要选具体交付形态

当前主仓库同时介绍完整开源 API、本地插件与云插件。完整服务示例需要 Neo4j、Qdrant 等；本地插件则有 SQLite、FTS5 加向量、经验到技能的组织。两者的依赖、接口和适用宿主分别检查。[当前部署比较](https://github.com/MemTensor/MemOS)

因此不能笼统断言“MemOS 一定太重”，也不能因专用插件可直接安装就认为 Nexus 已经受到支持。可优先研究本地核心是否能独立调用，再比较整体服务的收益。论文中的统一记忆抽象，也不代表当前某个安装形态已支持所有参数化或 KV 记忆功能。

### 6.8 Basic Memory：文件可读，但自动参与仍需宿主接入

核心服务用 Markdown 表达笔记，通过 MCP 的读写、搜索和上下文构建工具访问；笔记地址、permalink 和检索片段有助于定位资料。但保存一份整理笔记，不等于自动存下它所依据的全部会话。完整原档与笔记之间仍需明确引用。[知识格式](https://docs.basicmemory.com/concepts/knowledge-format)、[MCP 工具](https://docs.basicmemory.com/reference/mcp-tools-reference)

普通 MCP 调用与宿主生命周期接入分别看。官方 Claude Code 插件有会话简报和压缩前检查点等行为，但这不代表 Nexus 仅连接 MCP 就会得到同样的自动召回。[官方插件说明](https://github.com/basicmachines-co/basic-memory/blob/main/plugins/claude-code/README.md)

核心项目的 pyproject 标识 AGPL-3.0-or-later，宿主插件包可能采用另一许可证。本文只记录这一边界；复用具体版本前检查对应组件，不能把插件的 MIT 标识扩大到整个核心。[项目配置](https://github.com/basicmachines-co/basic-memory/blob/main/pyproject.toml)

### 6.9 Letta：完整 Agent 底座与记忆机制分别借鉴

当前 letta-ai/letta 的 README 指向 letta-code 作为活跃源码，旧 V1 API 服务保留在 archive 分支。因此 MemGPT、旧 Letta API 和当前 Letta Code 属于同一发展谱系，但不能混作同一个可安装记忆服务。[当前入口](https://github.com/letta-ai/letta)、[Letta Code](https://github.com/letta-ai/letta-code)

当前 MemFS 使用 Git 管理记忆文件：根目录关键资料每轮进入系统提示，带目录索引的详细资料按需读取，修改保留版本。默认不带语义／向量索引，需要相应搜索扩展。[MemFS](https://docs.letta.com/concepts/memfs/index.md)

对灵可以借鉴可读记忆、目录引导与版本历史。直接接入完整 Letta Agent 则会多一套身份、执行循环和状态管理；若只是增加记忆，应先寻找可单独使用的接口，不把“能通过 MCP 与另一个 Agent 对话”解释成获得轻量记忆后端。

### 6.10 LangMem：可复用处理函数，不必迁入完整编排框架

LangMem 的核心记忆管理器、提示词优化器可以接收材料并产生更新结果，处理函数不绑定某个存储；其有状态工具集成则使用 LangGraph 的存储接口。它适合作为自定义记忆插件中的处理部件，不能仅安装库就认为已有常驻服务和每轮自动召回。[LangMem 核心概念](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)、[仓库](https://github.com/langchain-ai/langmem)

提示词优化意味着从轨迹和反馈调整指导文字，与保存事件、形成可安装技能包分别看。对 Nexus，可只复用明确的抽取或更新过程；持久化、来源、参与时机及最终行为仍由已确定的系统边界组织。LangGraph 的检查点也不自动等于跨活动长期记忆。

### 6.11 Cognee：既有独立 MCP，也有共享服务部署

官方 MCP 文档明确区分独立模式和连接 REST API 的模式。独立模式包含完整库，默认可用 SQLite、LanceDB 和嵌入式图存储；多客户端共享同一后端时再采用 API 模式。不能一概说必须部署外部图数据库集群。[MCP 架构](https://docs.cognee.ai/cognee-mcp/mcp-overview.md)

来源返回也依赖所选查询方式和配置。include_references 可以增加证据内容，部分查询类型支持结构化 metadata.evidence，并非所有查询默认返回同一种证据格式。应验证所选调用能否定位原文，而不是只看产品宣称可追溯。[recall API](https://docs.cognee.ai/python-api/recall.md)

官方还展示 session 蒸馏、技能召回和改写提案。它值得作为知识积累与程序经验的候选，但这些结果怎样影响灵、何时自动运行，仍需 Nexus 插件接入；“记忆查询返回综合答案”与“返回原始证据”应分别选择。[会话蒸馏](https://docs.cognee.ai/guides/session-distillation.md)、[技能示例](https://docs.cognee.ai/examples/self-improving-skills.md)

### 6.12 Claude-Mem：高关注度的宿主记录与渐进检索案例

当前项目通过宿主钩子采集工具活动，形成观察和摘要；本地 worker 提供接口与查看页面，SQLite 保存会话与观察，结合向量搜索。它还提供先搜小索引、再看时间线、最后展开选中观察的 MCP 查询方式。[作者仓库](https://github.com/thedotmack/claude-mem)

这很适合借鉴记忆块的“先摘要、后细节”交互，以及自动记录和召回如何挂在宿主运行时机上。需要区分展开的是完整观察还是未经处理的会话原文；同时，其已有宿主适配不等于 Nexus 原生兼容。它与完整知识库或人格发展系统的目标也不同。

## 八、可以直接复用哪些技术

### 8.1 复用完整记忆引擎

可以通过 MCP、HTTP 或库接口复用保存、检索、整理等现成能力。重点候选是 Hindsight、EverOS，以及针对不同需求的 Mem0、Graphiti、Cognee。Nexus 仍负责当前活动、模型请求准备和插件生命周期；外部引擎的认识生成并不自动成为灵的最终判断。

原始记录能否完整展开要逐项验证。引擎返回一个事实、一句支持摘录或一个编号，不代表已经保存原始聊天的全部上下文。对记忆块设想，必须保有可靠的原档或可读原文的引用。

### 8.2 复用文件与索引层

Basic Memory 提供可读笔记与工具；EverOS 也可提供文件和派生整理的组合。若只需要一小部分处理能力，SQLite 全文搜索加适当向量组件也可以构成底层。这里“复用组件”与“自己定义记忆业务”要分清，不能称为完全零开发。

### 8.3 按角色复用基础组件

| 角色 | 可复用技术 | 帮灵做什么 | 仍需自己确定 |
| --- | --- | --- | --- |
| 原文／关键词搜索 | [SQLite FTS5](https://www.sqlite.org/fts5.html) | 找名字、原话、编号与上下文片段 | 中文分词／子串策略、范围和排序 |
| 本地向量搜索 | [sqlite-vec](https://github.com/asg017/sqlite-vec) | 在 SQLite 周围增加语义查询能力 | 当前扩展兼容、规模与速度；不把它等同于成熟记忆业务 |
| 服务型混合检索 | [Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/) | 语义、稀疏表示和条件过滤的组合 | 哪些内容索引、来源与时态含义 |
| 已有 PostgreSQL 的向量能力 | [pgvector](https://github.com/pgvector/pgvector) | 在关系数据旁保存和搜索向量 | 不必仅为少量记忆立即增加数据库服务 |
| 多语言 embedding | [BGE-M3 模型卡](https://huggingface.co/BAAI/bge-m3) | 将文字转换为可比较的表示，供检索使用 | 用灵的中文／别称测试；不宣称它是今天最优模型 |
| 关联与时态 | [Graphiti](https://github.com/getzep/graphiti) | 管理人物、关系和事实演变 | 需要哪些关系、抽取是否准确 |
| 文字经验整理 | [ACE](https://github.com/ace-agent/ace)、[LangMem](https://github.com/langchain-ai/langmem) | 从记录形成经验或改进提示的机制 | 怎样判断经验有效，哪些变化允许生效 |
| 简单持久事实工具基线 | [MCP Memory 参考实现](https://github.com/modelcontextprotocol/servers/tree/main/src/memory) | 实体、观察、关系的基本读写查询 | 没有因此得到完整时间理解、语义召回或自动整理 |

本地向量索引和模型都可替换，但不同 embedding 模型产生的向量通常不能直接混查；更换时要考虑重新计算索引。保留原文和稳定来源，比保住某一套向量文件更符合长期迁移目标。

### 8.4 可复用算法，不必复用整套运行时

可以借鉴 A-MEM 的关联、MemoryOS 的分层、ACE 的增量更新、MemRL 的反馈选取。方法借鉴不等于立即引入它的所有 Agent、计分规则和后台活动。

对于现成库，应先看输入输出是否能单独调用。如果安装一套 Agent 框架只为获得几个记忆函数，还需要重写 Nexus 的执行过程，复用收益就可能被迁移代价抵消。这是面向本项目的工程判断，不是对这些框架通用价值的评价。

## 九、怎样比较效果，避免被榜单误导

### 9.1 至少拆开三层结果

1. **写入：**该保留的内容是否真的保存了？来源、时间、主体有没有弄错？
2. **召回：**正确材料存在时，当前问题能否找到？有没有被旧认识和噪声压下去？
3. **使用：**材料已经交给模型，它是否正确理解并用于回答或行动？

EvalMem 专门区分编码、取回、生成的缺陷，适合借鉴这种诊断方式。本轮没有复现其评测或采用其收益数字。[EvalMem](https://arxiv.org/abs/2609.22231)

### 9.2 评测各测什么

| 资料 | 可以借鉴 | 不能替代什么 |
| --- | --- | --- |
| [LongMemEval](https://arxiv.org/abs/2410.10813) | 信息提取、跨会话、时间、更新、资料不足时承认未知 | 灵多月的实际使用体验 |
| [LoCoMo](https://aclanthology.org/2024.acl-long.747/) | 长跨度对话中的人物、事件与推理 | 真正的行动效果、人格与关系连续性 |
| [LoCoMo-Plus，2026](https://arxiv.org/abs/2602.10715) | 之后没有明确问到旧事时，仍能运用相关约束 | 对全部现实任务有效的保证 |
| [LongMemEval-V2，2026，Work in Progress](https://arxiv.org/abs/2605.12493) | 从操作轨迹学习环境状态、工作流程与常见陷阱 | 与原 LongMemEval 同题同配置的可比成绩 |

本轮不制作性能排行榜。不同论文或产品可能使用不同模型、历史切片、查询预算、评分器以及“仅检索”或“最终回答”指标。作者自测、托管服务成绩、开源代码成绩也须分别说明。

### 9.3 面向灵的建议检查集

以下是以后试用候选时的比较方法，不是本轮已运行的测试，也不自动成为实施清单。

| 场景 | 希望看到的行为 |
| --- | --- |
| 精确原话 | 找到真实原文和前后文，不能从摘要重编 |
| 同义与别称 | 换一种中文说法、夹英文项目名仍能找回 |
| 过去与现在 | 分清以前偏好、后来修正及当前适用范围 |
| 事件与得知时间 | 今天获知上月事件时，不把它记成今天发生 |
| 说话人与行动者 | 他人转述、灵计划执行、工具确认执行分别表达 |
| 跨事件解释 | 能连起几次讨论，说明决定形成的过程 |
| 未明确提旧事 | 相关交代仍能适当地影响当前回答 |
| 资料缺失 | 承认没找到足够依据，不断言从未发生 |
| 纠正与删除 | 更正后不继续用旧结论，删除后派生资料按预期处理 |
| 新记录与后台整理 | 能说明原档已保存但认识／索引是否尚未更新 |
| 方法迁移 | 经验用于相似任务时保留适用条件，不照搬无关做法 |
| 更换模型／后端 | 原文、事件块、来源与关键认识仍能导出和理解 |

同时记录写入、查询、整理各自的模型调用、等待时间和存储量。支持本地不等于没有计算成本；后台整理可能把费用从提问时移到事后。不能只看最终请求少了多少 token。

## 十、与记忆块设想怎样结合

建议保留现有设想的三个基础：事件摘要、直接搜索原始记录、按引用展开。对完整系统再补上当前认识与可复用经验，但把它们理解为同份历史的不同产物。

```text
Nexus 与外部服务的原始记录
    ├─ 可直接搜索、展开的原档
    └─ 有来源的事件记忆块
          ├─ 后续、纠正、支持等联系
          ├─ 人物／项目的当前认识
          └─ 有适用条件的经验与技能

当前交流 → 少量相关背景自动带入
灵主动查询 → 查事件、查原文、比较变化
```

其中需要共同保留的含义是：

- 原始记录是当时留下的资料；摘要是加工结果；认识是理解；技能是建议做法。
- 灵亲自做过、别人说过、模型推测和任务尚未执行，不因整理成记忆而混为一谈。
- 旧经历可以继续保留，当前认识能够更新；对某个旧结论停止使用，不必等同于抹除整段历史。
- 对当前工作状态，查询相应任务或外部事实来源；记忆解释先前决定，不另建一份会漂移的任务权威状态。
- 记忆的内容与含义尽量不绑定某个模型或后端；检索索引可以重建，重要原档和引用不能只存在于一个不可解释的索引里。

这套组织可以由一个主记忆后端配合宿主原档实现，不建议第一版同时接多个引擎、叠加多份自动总结。独立记忆服务也不需要主动唤醒才能完成普通召回；写入与整理可使用插件系统约定的参与时机。

## 十一、后续候选比较建议

### 11.1 优先对照三条路线，先确认记忆行为

| 路线 | 建议候选 | 适合的侧重 | 必须付出的工作 |
| --- | --- | --- | --- |
| 可读事件与笔记 | Basic Memory，辅以明确原档与事件规则 | 最重视看得懂、能纠正、能迁移 | 定义事件、当前认识、来源及自动召回；索引不能代替业务 |
| 现成经历整理 | Hindsight | 希望复用较完整的保存、混合召回和综合认识 | 配置原文、更新与派生规则，验证服务和模型代价 |
| 可读资料加派生整理 | EverOS | 希望事件、当前资料与 Agent 经验有现成组合 | 核实异步可见性、默认整理行为、完整来源及 Windows 支持 |

这是与当前记忆块目标最直接的比较集合，不是要求同时集成三套引擎。MemOS 本地核心可作为同类补充候选；如果需求更偏事实、时态关系或知识库，再分别加入 Mem0、Graphiti、Cognee，避免无目的地部署所有热门项目。

### 11.2 对旧报告候选的修正

保留旧报告“可读记忆”和“Hindsight”两条主要方向，补入当前 EverOS，扩大可复用范围。本次不因原先优先可读本地方案，就预先排除现成整理服务。

同时修正几个表达：Mem0 自动 ADD-only 不等于显式不可修改；Hindsight 当前有可配置的原文保存路径；Graphiti MCP 被官方标为实验性；MemoryOS、MemOS、EverOS 不混称。旧报告中的硬件、安装和接口判断，实施时仍以选定版本为准。

### 11.3 真正需要先确认的记忆需求

后续讨论优先确定：

1. 记忆主要服务于回顾经历、维持当前认识，还是积累做事技能；可以组合，但先说明侧重。
2. 一段事件怎样划分、何时记录，哪些普通交流也值得保留。
3. 原始资料、事件摘要和当前理解分别由谁维护，哪些允许自动变化。
4. 纠正、失效与删除各自意味着什么，怎样影响已有派生内容。
5. 自动背景提供与灵主动查询如何配合，以及可以接受多少整理等待和额外模型调用。

把这些行为带入同一组中文样例比较，比先选向量库、图数据库或“记忆 OS”名称更能判断适合程度。

### 11.4 本轮的技术建议

采用可替换的外部记忆路线，保留原文与稳定来源，以事件块承载经历，以可修正的当前认识承载理解，以有适用条件的经验承载方法。底层检索和整理尽可能复用现成组件或一个主引擎。

这是一套可持续演进的方向，不要求只做演示，也不要求第一步实现内部神经记忆、复杂多 Agent 记忆平台或所有类别。Titans、MemGen、MemRL 等分别留作模型内部与经验选择的研究参考，按实际需求再判断是否值得投入。
