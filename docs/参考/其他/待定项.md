## 一、LSP 能力

### 所有者原话

> 目前来看不需要LSP，未来暂且不知道。

### 我的理解

LSP（Language Server Protocol）让工具通过语言服务器理解代码结构，而不只是字符串匹配。最有用的两个操作是**跳转定义**和**查找引用**。

**为什么曾经想到它**：我上一轮把"缺 LSP"列为 Nexus 与成熟 Agent 的差距。这个判断后来被证据推翻了：

| 参照 | 有没有 LSP |
|---|---|
| DSH（308 个包，最成熟的参照） | **没有**。只有一个 6KB 的 `dsh-util-code-language`，那是扩展名到语言名的映射表，用于语法高亮 |
| Codex | 没有 |
| opencode | 有，但**标记为实验性**，且需要显式设置 `OPENCODE_EXPERIMENTAL_LSP_TOOL=true` 才出现 |

也就是说：最成熟的实现不做它，做了的那个自己标了实验性。我当初把 opencode 的实验性功能当成行业标配，是**拿参照物的清单当标准，而没有看它是否真的必要**。

**判断它可能不需要的理由**：

- 收益和语言强绑定。Python / TypeScript / Java / Go 这类强类型语言收益大；Markdown、配置、脚本类收益接近零。
- 需要为每种语言配置并启动一个语言服务器（`pyright`、`tsserver`、`gopls`……），每个都有装不上、版本不符、卡死的可能。为一个收益不确定的能力引入 N 个外部依赖。
- 现有 `grep` + `read_file` 已覆盖大部分场景；`edit_file` 失败时也已能报候选行号。

**将来什么时候会需要**：当真实出现"因为搜不到调用方而改漏了代码"的实例时。那时候会有具体案例、具体语言，做起来比现在凭想象设计要准。

**将来也可能永远不做**：如果 Nexus 的长期用途不是处理大型强类型代码库，那它就一直不需要。

## 二、插件系统

### 所有者原话

> 补齐：插件化不是强制要求，有的话最好，没有也没关系，但是任何业务都不应该完全绑死，至少确保可被维护，不会牵一发动全身

以及：

> 后续如果引入插件系统的话可以学一学DSH，看看哪些是值得插件化的。

### 我的理解

"插件化"被明确为**非强制**。真正的要求是可维护、不牵一发动全身。

因此当前路线是：**留接缝，不建平台**。已有的接缝（`tools/` 的清单驱动装配、`ToolSpec.requires` 的条件注册）已经满足"改一处不影响别处"。再加接口层、DI 容器、插件运行时，都是为一个不存在的第三方扩展需求提前投资。

将来若真要做，DSH 的 Cordis 内核值得读：它用 `inject` 声明依赖，依赖不满足插件根本不加载——这个思路 Nexus 已经在 `ToolSpec.requires` 上用了一部分。

**可能永远不做**：如果所有扩展都由自己写，清单驱动已经够了。
