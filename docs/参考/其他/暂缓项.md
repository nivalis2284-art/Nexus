## 一、沙箱分级

### 所有者原话

> 关于第一档，暂缓，因为我还无法确定能够让Agent修改的边界在哪，提前引入沙箱后面不方便修改。

### 我的理解

Codex 的模型把两件事分开：`sandbox_mode`（技术上能不能做，`read-only` / `workspace-write` / `danger-full-access`）和 `approval_policy`（要不要问人，`untrusted` / `on-request` / `never`）。

Nexus 目前**只有后者**：靠"写文件前弹窗问一句"。技术上没有任何强制约束——`shell.py` 里的 Windows Job Object 只限制内存、进程数、CPU 时间，防的是把机器跑崩，不是防改错东西。

暂缓的理由是：**边界还没想清楚时引入沙箱，等于用不成熟的理解去固化限制**，以后想放宽或收紧都要动底层。

代价要清楚：现在 `yolo` 模式就是完全放手，没有中间档。

恢复条件：等"Agent 该被允许碰什么"有了明确答案再设计。没有这个答案之前，任何沙箱实现都只是猜。

## 二、多会话与相关管理

### 所有者原话

> 我不准备开多个会话，毕竟我需要的不是一个coding Agent，我需要的是一个能够持续存在的Agent，类似于角色扮演，但比角色扮演更深入，具体参照愿景文档。所有反而不需要过多的独立会话，所以会话命名有没有问题不大，允许我手动重命名即可。

### 我的理解

如果长期只有一个持续会话，那么**为"很多会话"设计的功能都是错的投入**：自动生成标题、全文搜索、批量导出，它们存在的理由都是"会话太多管不过来"。

暂缓：LLM 生成标题、会话搜索、会话导出。

**不暂缓的**：手动重命名（已列入当前开发计划）。

这条暂缓同时说明了一件更重要的事：会话模型本身以后可能不是"多个平级会话"，而是"一个持续主体 + 某些分支"。真到那一步，现在这些设计都要重想。

## 三、计划模式

### 所有者原话

> 关于计划模式，DSH似乎是以插件形式存在的？可以作为参考，后续如果引入插件系统的话可以学一学DSH，看看哪些是值得插件化的。

### 我的理解

先纠正一个事实：我查了 DSH 的 `dsh-plan-mode` 源码，它的核心是「激活时在每次模型请求里插入一段指导文字，`exit_plan_mode` 把完成的计划交给用户审阅，`/plan off` 直接退出」。**它本身和插件系统没有必然关系**——它恰好是插件包，但功能不依赖 Cordis。

所以暂缓的真实原因不是"等插件系统"，而是：**现在没有明确的计划模式需求**。所有者原话里说的是"如果引入插件系统可以学一学"，属于可选参考，不是承诺要做。

暂缓的是"现在做一个计划模式"。将来若需要，DSH 的实现值得读（尤其是它把计划和沙箱/审批明确解耦这一点）。

## 四、会话格式版本化、遥测、崩溃恢复

### 所有者原话

> 第四档，同样会话方面可有可无，其他按照你的建议来。

### 我的理解

DSH 有 `session-format-v0-to-v1` 到 `v3-to-v4` 四代迁移、`session-telemetry-otel`、`spill`（溢出与恢复）三个系列。

这些解决的是"会话格式变了以后旧数据怎么办""要观测运行状况""进程崩溃后怎么恢复"。Nexus 现在只有 JSONL，格式简单且未变过。

所有者说"可有可无"，我理解为：**方向上是需要的，但时间上不急**。所以归入暂缓而非待定。

恢复条件：会话格式第一次发生不兼容变更时补迁移；真正需要观测线上问题时补遥测。崩溃恢复同理——等出现"跑长任务被打断很痛"的实例再说。
