> 本文保留开发前的调查快照。正式开发的修复、验证和当前限制见 [PROGRESS.md](../../PROGRESS.md)，当前功能关系见 [BUSINESS-MAP.html](../../BUSINESS-MAP.html)。下文“本轮”均指研究阶段。本文与对应 PRD 于新一轮需求同步时一并归档；仅调整归档后的链接，原调查结论保持不变。

研究日期：2026-10-19（Asia/Tokyo）。源码基线：`6c3729f`。需求来源：[PRD.md](PRD.md) 与当前会话明确指令。

本文是研究结论，不是实施计划或完成验收。本轮只同步需求、调查、验证及记录；未修改业务代码、测试代码或启动脚本，未制作最终 `BUSINESS-MAP.html`。

## 1. 需求理解与已确认边界

最终目标是整理现有系统、改善有证据的工程问题，并让非技术人员看懂当前功能如何协作。优化成效应由行为正确性、维护问题是否消除及测量结果判断，不以代码行数、模块数或技术栈变化判断。

- 用户本轮要求优先于附件中的阶段性措辞：PRD 的代码优化、回归和 HTML 图是后续产品交付目标；本轮产出为需求同步及研究文档，不代表现在开始开发。
- “业务路线图”按 PRD 理解为当前功能和业务关系图，包含调用、数据流和依赖；不是日期排期图。HTML 是文档交付物，不要求加入 Nexus 产品导航。
- 不增加记忆、人格、LSP、插件系统、计划模式或多会话并行等能力。历史材料中的愿望不自动进入本轮范围。
- 保持现有使用路径、配置、数据和三类模型协议的兼容；修复错误行为可以改变错误结果。数据格式迁移、权限体验的重大改变仍需另行讨论。
- **用户已确认（当前会话）：后台任务按会话归属，同一会话跨轮可查看、停止，服务退出时结束。** 这不是所有会话共用任务表，也不要求服务重启后恢复任务。子代理启动的任务建议归属父会话，作为技术建议记录。

上传 PRD 已逐字节同步为 `docs/PRD.md`。仓库原先没有 `docs/PRD.md` 或其他明确对应本次优化目标的旧版需求文档；`docs/愿景/` 和 `docs/参考/` 的内容分别属于长期方向及历史记录，未删除或替换。后续确认先记于本文，避免悄悄改写上传原文。

## 2. 项目实际结构与功能边界

### 2.1 当前主链路

```text
浏览器 app.js
  ├─ 配置、提供商、模型、思考强度、工作目录、会话管理 → HTTP API
  └─ 文字/图片输入 → POST /api/chat
       → server.Handler：加载会话与配置、持有单运行锁、装配 Agent
       → core.Agent：上下文处理 → 协议请求 → 模型事件
           ├─ 无工具调用 → 回答与完成
           └─ 有工具调用 → 权限判断/人工确认 → Registry.execute
                → 文件/命令/任务/补丁/待办/提问/Skill/子代理/可选网络工具
                → 结果写回运行历史 → 下一轮模型请求
       → NDJSON 事件返回网页；结束后保存 JSONL 会话
```

这是源码中的预期链路；下面列出的装配缺陷意味着部分分支尚不能标为端到端可用。

| 业务能力 | 实现与关键连接 | 当前证据及限制 |
|---|---|---|
| 提供商、模型、思考强度、配置与凭据 | `core/config.py`、`core/effort.py`、网页配置 API | 配置与协议映射测试通过；未调用真实服务 |
| 三协议模型流 | `core/protocol.py` → `model/gateway.py` → `_sse.py`、`_parsers.py` | Anthropic Messages、Chat Completions、Responses；流与异常 fixture 测试通过 |
| Agent 多轮工具循环 | `core/agent.py` → `tools/registry.py` | 有循环、重试和检查点式停止；停止不是立即终止所有子操作 |
| 文件读取、写入、编辑、查找、补丁 | `tools/files.py`、`patch.py`、`_paths.py` | 已有 hash 并发检查、补丁匹配等测试，值得复用 |
| 前台命令、后台任务 | `shell.py`、`_process.py`、`_jobobject.py`；`jobs.py`、`_jobs.py` | 前后台分别实现进程管理，能力不一致；任务跨轮归属有缺陷 |
| 待办、向用户提问、人工授权 | `todo.py`、`ask.py`、`core/permission.py`、`web/server.py::Approvals` | 人工交互与取消测试通过；权限工具覆盖、子代理授权仍有缺口 |
| 会话创建、读取、删除、重命名 | `session/store.py`、HTTP API、网页会话列表 | JSONL 存储可复用；长对话压缩后保存边界有缺陷 |
| 上下文预算、工具结果裁剪、模型摘要 | `core/prompt.py`、`compaction.py`、`Agent._fold` | 纯函数和 Agent 分支已有测试；预算与保存链路仍有集成缺口 |
| 图片输入、思考过程、工具过程、用量显示 | `web/app.js`、`web/server.py`、协议适配 | 后端有图片接收及适配，网页发送链路丢图；显示不能等同于持久化正确 |
| Skill | `skills.py` → 工具上下文、提示清单、`read_skill` | 项目目录优先，正文按工具读取；切换工作目录后清单未重新加载 |
| 子代理 | `tools/subagent_tool.py` → `server.py` 中工厂 → `core/subagent.py` | 支持独立任务运行；父子授权、停止传播等装配不完整 |
| MCP | `mcp.py` → `tools/mcp_tools.py` → Registry | stdio 客户端与 stub 交互测试通过；网页启动及注册链路断开 |
| 可选网络抓取与搜索 | `tools/web.py`、`tools.build` 的配置过滤 | 默认不注册，需配置域名/搜索端点；未做真实外网工具验收 |

系统使用 Python 3.12、标准库 `ThreadingHTTPServer`、无构建步骤的 HTML/CSS/JS。直接运行依赖为 HTTPX 与 Pydantic。没有证据表明必须换成 Web 框架、SPA 框架、数据库或 Agent 框架。

## 4. 有证据的问题与改善方向

以下编号用于追溯研究发现，不是排期或必须全部重写的清单。“实测”指本文描述的受控验证；“源码确认”不冒充完整操作验收。

### R1. 压缩会导致新回答未持久化（实测，应优先处理）

依据：`core/agent.py:233` 的 `messages[:] = folded`，以及 `web/server.py:656` 的旧长度记录和 `:787` 的 `history[before:]`。

网页保存依赖“运行历史只追加”的前提，Agent 摘要压缩却会原地缩短这个列表。探针建立 10 条旧消息，将 `_fold` 的模型摘要边界替换为确定性的 2 条消息，保持真实 Agent 循环和 `_run_turn` 保存路径：模拟模型正常返回 `new final answer`，流中有 `delta`、`done`，重载 JSONL 后仍只有 10 条旧消息，找不到新回答。

这是持久化边界缺陷的复现；没有宣称实测了真实模型生成摘要的质量。压缩事件也未被网页事件转发器处理。下一轮仍从完整 JSONL 重建历史，没有持久保存摘要状态，可能重复摘要，实际请求成本未测。

建议明确区分展示/审计用完整会话、新增消息记录、发送模型的压缩上下文；保存本轮产出不能依赖会被压缩改变的旧下标。优先考虑显式记录本轮新增消息或结果，保留 JSONL 外部兼容；若选择持久摘要，应另行说明怎样保留原始会话及恢复语义，不能直接覆盖原始记录。

### R2. 网页 MCP 存在三个独立断点（实测及源码确认）

1. `web/server.py:848` 使用 `mcp_tools.config_problems`，文件没有导入 `mcp_tools`。给 `_start_mcp` 提供非空服务器配置，立即得到 `NameError`，尚未进入服务器启动步骤。
2. `serve` 保存了 `STATE['mcp']`，但 `_run_turn` 未将它注入父工具上下文。`tools.build` 又在返回前按 `context.mcp` 生成工具声明，因此仅在 build 后赋值也不够。对子代理的赋值同样晚于注册阶段，且当前拿到的是父上下文中的 `None`。受控运行网页装配两轮，父、子上下文均显示 `mcp_connected=False`、MCP 工具数为 0。
3. `tools/mcp_tools.py::specs_for` 未向 `ToolSpec.schema()` 提供服务端 `input_schema`。一个声明必填 `text: string` 的 echo 工具，被发布成 `properties: {}`、`additionalProperties: true`，必填字段丢失。仅修复连接还不能解决参数声明问题。

建议沿用现有 stdio 客户端、分页和关闭逻辑，在工具注册前完成依赖注入，并让动态工具保留原生 JSON Schema；本地参数透传与向模型展示完整参数结构是两件事。没有必要为此引入插件框架或把任意 JSON Schema 翻译成 Pydantic 类型。MCP 官方明确将 `inputSchema` 作为工具参数定义。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

### R3. 网页发送链路丢失图片（执行前端函数复现）

`web/app.js:451` 清空 `pendingImages`，`:503` 再使用它构造请求，因此请求总是 `images: []`。仅图片输入还会被后端视为空消息。`server.py::_transcript` 也未返回已存用户图片，`nodeFor` 只渲染用户文字。

探针用 Node VM 执行源码中原始 `send` 函数，替换 DOM、fetch 和刷新函数，放入 1 个模拟图片附件。捕获结果：`selected: 1, sent: 0`。这是函数级行为验证，未做完整浏览器上传、缩略图及刷新验收。

建议先固定本次发送的附件快照，再清空编辑区；会话响应与渲染保留对应附件。继续复用已有后端图片校验和三协议映射，不新增媒体系统。

### R4. 后台任务状态归属和进程管理不完整（跨轮装配实测，其余源码确认）

- `web/server.py::_run_turn` 每轮新建 ToolContext，`tools/jobs.py::_registry` 将登记表挂在该上下文。用网页原始装配路径运行两轮，在第一轮上下文启动短任务，第二轮 `job_list` 返回空列表。任务仍可执行，用户却失去后续查询入口。
- `Job.read` 使用当前缓冲区相对下标作为 cursor，环形裁剪后外部 cursor 没有相应更新。实测读取到 200000，再追加 `NEW` 触发裁剪，用旧 cursor 读取得到空字符串，虽然缓冲尾部有 `NEW`。
- `_pump` 按行迭代管道，长时间不换行的输出不能及时呈现；保留字符串上限不等于读取端也有同样上限。
- `_jobs.py::kill` 只终止直接子进程；Windows 未使用 Job Object，POSIX 虽建新会话却未按进程组终止。模块注释声称能终止整个进程树，与实现不一致。`close_all` 没有业务调用点。

用户已确认按会话跨轮保留、服务退出时结束。建议由现有运行装配处持有会话任务登记表；显式 cursor 使用单调位置，分块读取并增量解码。进程树清理优先复用仓库现有 `_process.py`、`_jobobject.py` 能力，按任务生命周期适配，不直接把有总超时的前台执行器套给后台任务。

微软 Job Object 提供进程组管理及 kill-on-close 机制；Python 的 Windows `Popen.terminate()` 作用于指定子进程，不能据其名称推断自动清理整棵树。[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[Python subprocess](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen.terminate)

### R5. 默认 ask 权限覆盖不一致（策略实测）

`core/permission.py::default_policy` 默认只列 `write_file`、`edit_file`、`bash`。直接查询同一策略得到：前三类需要 ask，`apply_patch`、`bash_background` 为 allow。补丁同样写文件，后台命令同样执行命令，当前差异有真实代码依据。

建议统一同类操作的既有确认语义，并核对自定义规则和 yolo 行为。使用现有授权通道即可；不引入 OS 沙箱、全新权限体系或额外审批层。若后续考虑把原来允许的其他工具整体改为默认确认，需要单独说明用户体验变化。

### R6. 上下文预算与工具交互边界不一致（纯函数实测）

- Agent 保存的工具调用形状是 `{id, name, arguments}`；`prompt._text_of`、`compaction._text_of` 却主要读取嵌套 `function.name/arguments`。构造含 30000 字符 arguments 的真实内部形状，文本估计仅为 1 token，compaction 估计总计 8，而参数本身约需万级估算 token。这里是估算漏项，不是提供商精确计数。
- `prompt.select` 按单条消息从后向前截取，未按工具交互组保持完整。受控样本成本分别为 `[9,343,11]`，可用消息预算 354 时，结果角色为 `['tool','user']`，对应 assistant 工具调用被丢弃。
- `compaction.split_for_summary` 有工具配对逻辑，但 `select` 不复用它；两份文本提取、token 估算及摘要编排也容易产生差异。

建议以当前内部消息结构为准统一必要的文本/图片估算，按完整工具交互保留上下文。继续用明确标注的估计值，不为本轮引入全协议精确 tokenizer。还应验证取消发生在多工具响应之间时留下未完成调用的行为；该分支本轮未动态验证。

### R7. 父子运行控制及工作目录切换的装配缺口（部分实测）

网页父 Agent 有 approve 回调，`:712` 构造子 Agent 未传该回调。受控装配捕获结果为父 `approve=True`、子 `approve=False`。因此在 ask 模式下，子代理遇到需要确认的写文件/前台命令时，会返回 `needs_approval`，不能走现有人工确认流程。

源码还显示：停止端点只操作父 Agent；子运行没有共享停止信号；子工具上下文没有继续注入 spawn 工厂，不能将深度常量解读为网页实际支持多层委派。`_workspace` 只保存工作目录，而 Skill 在启动时发现一次；切换后项目 Skill 可能仍属于旧目录。后两类尚未端到端实测。

建议统一父子运行必要的授权、停止信号及资源归属；Skill 随实际工作目录刷新。MCP 连接的 cwd 和重新启动行为需明确处理，不能直接套用 Skill 重载。保持子代理独立上下文、只回传报告的现有意图，不借此增加并行调度或多层代理产品功能。

### R8. 工具结果状态在流、保存、重载之间不一致（源码确认）

`Agent._invoke` 得到结构化 `ToolResult`，但历史工具消息只留下 content。`server.py::_persist` 再靠三类错误文本前缀推断 ok；其他错误可能重载后显示成功，工具参数也没有完整保存到对应工具展示记录。`Registry.execute` 对正常返回的 payload 默认产生 `ToolResult(True,...)`，即使命令 payload 内有 `ok=False` 或 MCP payload 有 `mcp_error=True`。

建议区分“工具调用成功完成”与“被执行的命令/远端工具返回失败”，保留结构化状态和调用 id/参数用于关联，避免靠自然语言错误文案推断。字段扩展应能读取旧 JSONL，不要求历史数据迁移。此处是源码确认，未把所有错误类型逐一动态验收。

### R9. 架构守卫测试目前未提取任何依赖（实测）

`tests/test_architecture.py::_module_edges` 从绝对文件路径拼 Python 模块名，之后要求目标以 `nexus` 开头。相对导入因此没有被正确识别；执行该函数得到 `edges=[]`。现有基于依赖边的断言事实上空遍历，不能用其通过声称架构符合分层。

建议先让测试从仓库相对模块名计算导入，并用一个真实依赖或小样例证明守卫能发现边和违规。不能把修复测试后出现的既有依赖问题伪装成新引入，也不应为满足硬编码层次而强拆合理职责。

### R10. 启动环境失效与低风险清理候选

`start.bat` 仅检查 `.venv\Scripts\python.exe` 文件存在，不检查它能否运行；本机恰好满足“文件存在、基础解释器失效”，所以无法自动准备环境。脚本直接安装未限定版本的 httpx/pydantic，也未按 `pyproject.toml` 安装项目声明依赖。Python 官方明确说明虚拟环境通常应在新位置重建，不能依赖复制后的环境继续运行。[venv 文档](https://docs.python.org/3.12/library/venv.html)

建议启动时识别失效环境并给出明确可执行的恢复路径，依赖安装与项目声明一致。不在没有讨论的情况下删除用户已有虚拟环境；本轮未修复或重建它。

可顺带核对的债务包括：`agent.py` 中仅追加、不读取的 `turns` 事件列表；Agent `_fold` 与 `compaction.summarise` 的重复摘要编排；files/patch 的重复 hash 检查；若干旧显示函数及声明字段。前者有明确无效保留，其他项目应先确认行为差异和真实引用，再决定是否合并或删除，不机械去重。

## 5. 性能和资源研究：已测量与未证实

### 5.1 会话列表的受控测量

`SessionStore.list` 每次读取并解析所有 JSONL 会话，`/api/state` 会调用它。探针在临时目录生成每会话 40 条、每条 1000 个 ASCII 字符的消息；预热一次，连续测量 5 次，仅计 `list()`，不计数据生成或网络/UI。

| 会话数 | 五次耗时（ms） | 中位数（ms） |
|---|---|---|
| 10 | 6.50、5.50、4.92、4.81、4.60 | 4.92 |
| 100 | 51.23、58.05、53.49、63.51、61.20 | 58.05 |

这是合成负载下的本机结果，不是用户现有会话规模，不代表端到端延迟，也没有改动前后对照。可以确认重复读取成本随记录增长；**尚不足以决定现在增加数据库、缓存或索引**。若真实会话列表出现可感知等待，再优先考虑轻量元数据读取/缓存，并测其失效正确性。

### 5.2 其他候选项的判断

- **无效事件保留：** `turns` 在每个模型请求中保存全部 ModelEvent，之后不读取。删除此类冗余状态有直接依据；当前未测内存收益，不宣称明显提速。底层 parser 的原生 continuation 有协议测试和实际职责，不能一起按“未用”删除。
- **连接复用：** Agent 已在一轮多步骤循环外创建 AsyncClient，具备轮内连接复用。HTTPX 官方建议避免热循环中反复创建客户端；目前不能据此要求跨轮全局共享，后者还涉及网页每轮不同 asyncio loop 和关闭时机。[HTTPX Async Support](https://www.python-httpx.org/async/)
- **保存开销：** 每次 append 都 flush/fsync 是已确认事实，但本轮没有磁盘耗时证据。不能为追求吞吐直接取消数据落盘保证；合并写入需先验证丢失窗口和失败行为。
- **前端流更新：** 每片段更新全文和滚动位置是潜在成本，尚未取得浏览器性能轨迹，不据此更换框架或宣称页面卡顿。
- **资源正确性优先：** 任务失联、cursor 漏读、进程树清理和不完整停止传播已有具体依据，比微优化更值得处理。

如后续需要量化，标准库 cProfile 可定位 Python CPU 调用成本，tracemalloc 可比较 Python 分配；真实模型等待、首字延迟、页面渲染及 OS 子进程内存需要分别测量，不能用一个数字代替。[cProfile](https://docs.python.org/3.12/library/profile.html)、[tracemalloc](https://docs.python.org/3.12/library/tracemalloc.html)

## 6. 候选方案与技术取舍

### 6.1 系统整理

| 候选方向 | 优点 | 成本与取舍 | 结论 |
|---|---|---|---|
| 保留模块化单体，修复装配、运行状态、上下文与保存边界 | 复用现有模块和 221 项测试，变更与证据直接对应 | 必须补关键集成验证，不能只搬文件 | **推荐** |
| 有限提取网页中的运行装配职责 | 可集中管理父子授权、任务、MCP 与停止信号，减少同类遗漏 | 仅提取已有职责；不发展成通用容器或调度框架 | 随具体修复决定，不先规定新目录和接口 |
| 更换 HTTP/前端/Agent 框架、数据库或全异步进程架构 | 可能提供现成能力 | 当前需求未证明收益，迁移面和回归面大 | 暂不采用 |

已有正确实现优先复用：三协议网关及 fixture、声明式工具目录、Approvals 的等待/取消、JSONL 兼容读取、MCP stub、补丁与写入校验、前台进程的有界分块读取和 Windows Job Object。可维护性问题主要来自这些能力在网页入口组合时的契约不一致，并非缺少一个框架。

### 6.2 HTML 功能业务关系图

| 方案 | 适用性 | 本次取舍 |
|---|---|---|
| 原生 HTML/CSS + 内嵌 SVG + 少量 JS | 固定规模、分组明确、需要业务说明与源码证据的文档 | **首选**；可做成双击打开的单文件，不需要运行 Nexus 或联网 |
| Mermaid 编写，构建时导出 SVG 后嵌入 HTML | 文字维护方便，适合若干流程和依赖图 | 可作为制图工具；CLI 支持 SVG 输出，最终文档可不携带渲染运行时 |
| 页面运行 Mermaid | 图语法维护方便 | 浏览器仍需加载渲染库；采用时需本地打包/内嵌，不能只依赖 CDN |
| Cytoscape.js | 适合大量节点、自动布局、动态过滤及图交互 | 能力成熟，但当前没有重型图探索需求；除非实作证明必要，否则不引入 |

依据：[Mermaid 使用指南](https://mermaid.js.org/intro/getting-started.html)、[mermaid-cli 官方仓库](https://github.com/mermaid-js/mermaid-cli)、[Cytoscape.js 官方文档](https://js.cytoscape.org/)。以上是调查后的适用性判断，未在本轮实现或验收最终图。

建议图的内容组织为：先用“提出任务 → 模型判断 → 工具/人工交互 → 结果回灌 → 完成与保存”说明业务，再展开模型、执行工具、上下文、持久化和扩展能力。每个业务节点提供白话说明、主要子功能和对应源码；连线显式标注调用、事件、数据保存或配置依赖。把 MCP 接线缺陷、图片链路等标为“模块已实现但集成存在缺陷”，不能直接涂成“已完整可用”。

最终覆盖应包含会话与配置管理、三协议/思考强度/流和用量、文件及命令工具、后台任务、补丁、待办、提问与授权、Skill、MCP、子代理、可选网络工具、压缩和停止。按业务建立节点，不把每个类/函数都变成一条业务。愿景能力至多作为明确未实现的说明，不与当前能力混排。

推荐内嵌图数据及资源，源码位置用项目相对路径文字和可选相对链接，外部文档链接允许联网查看；HTML 核心展示无需 CDN 或本地 HTTP 服务。源码追溯应兼顾直接打开文件与仓库阅读，不能只放不可移植的本机绝对路径。后续在常用浏览器验证本地打开、缩放后可读性、连线含义和节点覆盖；这些是交付检查方向，不是本轮已完成事项。

## 7. 结论、风险及待确认事项

**推荐方向：保留现有技术栈和业务范围，以真实集成缺陷为中心进行有限整理；关系图采用独立、可本地打开的 HTML，以业务主链路和分组细节呈现。** 现有结构有足够可复用基础，尚无整库重构或性能基础设施投入的证据。

当前已有充分依据的重点是：回答持久化、图片发送、MCP 装配和 schema、后台任务会话归属及读取/清理、同类工具授权一致性、上下文预算及配对、父子运行控制、结果状态保留和无效架构测试。它们是候选修复范围；后续具体实现仍须按实际收益和回归风险取舍。

已明确的产品问题只有后台任务生命周期，并已获得用户确认。当前没有必须等待回答才能继续研究的产品阻塞。以下是技术研究尚未完成的验证边界，不应伪装成“用户待决”：

- 未连接真实提供商，无法证明真实模型、兼容网关、计费和思考输出在所有服务上可用。
- 未做完整浏览器操作验收，前端丢图仅执行原始函数与模拟 DOM/fetch 复现；图形视觉方案尚未制作。
- 未实测后台任务的整棵子进程树终止、无换行大输出及子代理运行中停止；相关结论分别标注了源码依据。
- 未验收断电恢复、用户实际规模下的性能、会话并发修改与全部权限规则组合；不因此扩大需求。
- 未确定持久摘要策略和取消时未完成工具结果的最终表示；实现时需先保持会话可追溯和三协议请求合法。
- 报告没有宣称实现提速、修复上述问题或完成最终 PRD 验收。正常 `.venv` 启动入口仍需后续处理。

后续若出现配置/JSONL 不兼容迁移、扩大默认确认范围、改变停止语义、增加产品 UI 或新增基础设施等重大行为选择，再呈现具体差异与依据供用户决定；本轮没有将这些选择预先当作授权。
